1. What is Hold Time?

Yesterday we learned about setup time — data must be stable before the clock edge. Today we tackle the other half: hold time (th) — data must remain stable after the clock edge.

어제 우리는 셋업 타임을 배웠습니다 — 데이터가 클럭 에지 이전에 안정되어야 한다는 것이었죠. 오늘은 나머지 반쪽인 홀드 타임 (th)을 다룹니다 — 데이터가 클럭 에지 이후에도 안정되어야 합니다.

📌 Hold Time Definition

Hold time (th) is the minimum time that data must remain stable after the active clock edge for the flip-flop to reliably capture it.

홀드 타임 (th)은 플립플롭이 데이터를 안정적으로 캡처하기 위해 클럭 에지 이후에 데이터가 안정 상태를 유지해야 하는 최소 시간입니다.

Think of it like a camera shutter — even after you press the button, you need to hold still for a brief moment for a clear picture.

카메라 셔터처럼 생각하세요 — 버튼을 누른 후에도 선명한 사진을 위해 잠시 동안 움직이지 않아야 합니다.

CLK ┌──────┐ ┌──────┐ ──────────┘ └──────┘ └────── │ ◄────┤ t_h ►│ │ │ Data ───╋══════╋─── Data can change after this │ HOLD │ clock hold time edge window ends

2. Setup Time vs Hold Time

These two constraints form a timing window around the clock edge where data must be stable:

이 두 가지 제약 조건은 클럭 에지 주변에서 데이터가 안정되어야 하는 타이밍 윈도우를 형성합니다:

When?Before clock edgeAfter clock edge
언제?클럭 에지 이전클럭 에지 이후
Violated by?Data arriving too lateData changing too soon
위반 원인?데이터가 너무 늦게 도착데이터가 너무 빨리 변경
Fixed by?Faster logic or slower clockAdding delay to data path
해결 방법?더 빠른 로직 또는 느린 클럭데이터 경로에 지연 추가
Clock frequency?Can fix by slowing clockClock speed does NOT help!
클럭 주파수?클럭을 늦추면 해결 가능클럭 속도로 해결 불가!

⚠️ Critical Difference!

Setup violations can be fixed by slowing down the clock. Hold violations cannot! Hold time is independent of clock frequency — it only depends on the delay between two flip-flops. This makes hold violations especially dangerous.

셋업 위반은 클럭을 느리게 하면 해결됩니다. 홀드 위반은 불가능합니다! 홀드 타임은 클럭 주파수와 무관하며, 오직 두 플립플롭 사이의 지연에만 의존합니다. 이것이 홀드 위반을 특히 위험하게 만듭니다.

3. What Causes Hold Violations?

A hold violation happens when data at a flip-flop's input changes too quickly after the clock edge — before the flip-flop has finished capturing the old value.

홀드 위반은 플립플롭의 입력 데이터가 클럭 에지 이후 너무 빨리 변경되어, 플립플롭이 이전 값을 캡처하기 전에 바뀌는 경우 발생합니다.

The Hold Time Equation

📌 Hold Check Formula

For the data to be stable long enough after the clock edge:

클럭 에지 이후 데이터가 충분히 오래 안정되려면:

// Hold time check (same clock edge)
t_clk2q + t_comb ≥ t_hold

// Where:
// t_clk2q  = clock-to-output delay of launching FF
// t_comb   = combinational delay between FFs
// t_hold   = hold time requirement of capturing FF

// Slack (positive = good, negative = violation)
hold_slack = (t_clk2q + t_comb) - t_hold

Let's trace through an example:

예시를 따라가 봅시다:

// Example: Two flip-flops with minimal logic between them

//   FF_A ──► (tiny logic) ──► FF_B
//   t_clk2q = 0.2ns
//   t_comb  = 0.1ns  (very short path!)
//   t_hold  = 0.15ns

// Hold slack = (0.2 + 0.1) - 0.15 = +0.15ns ✅ OK

// But what if t_comb = 0?
// Hold slack = (0.2 + 0) - 0.15 = +0.05ns ⚠️ Tight!

// With clock skew making clock arrive early at FF_B:
// Hold slack = (0.2 + 0) - 0.15 - 0.1(skew) = -0.05ns ❌ VIOLATION!

Common Causes

🔍 What Makes Hold Violations Happen?

  1. Very short paths between flip-flops — direct connections or minimal logic
  2. Clock skew — if the capturing FF's clock arrives early, the hold window extends
  3. Fast process corners — gates switch faster than expected
  4. Reset/set paths — synchronous reset can create short paths
  1. 플립플롭 사이의 매우 짧은 경로 — 직접 연결 또는 최소한의 로직
  2. 클럭 스큐 — 캡처 FF의 클럭이 일찍 도착하면 홀드 윈도우가 확장됨
  3. 빠른 프로세스 코너 — 게이트가 예상보다 빨리 스위칭
  4. 리셋/셋 경로 — 동기식 리셋이 짧은 경로를 만들 수 있음

4. Clock Skew Makes It Worse

Clock skew is the #1 contributor to hold violations. If the capturing flip-flop's clock arrives earlier than the launching flip-flop's clock, the hold requirement effectively increases:

클럭 스큐는 홀드 위반의 가장 큰 원인입니다. 캡처 플립플롭의 클럭이 발사 플립플롭의 클럭보다 일찍 도착하면, 홀드 요구 사항이 사실상 증가합니다:

// Hold check WITH clock skew
t_clk2q + t_comb ≥ t_hold + t_skew

// Positive skew = capturing clock arrives EARLIER
// This is the DANGEROUS direction for hold time!

// Example:
//   Launch clock arrives at 0.0ns
//   Capture clock arrives at -0.1ns (skew = 0.1ns early)
//   Data must be held 0.1ns LONGER than normal
Launch CLK ────────┐ ┌────── └─────────┘ ↑ Capture CLK ─────┐ ┌───────── (arrives early) └─────────┘ ↑ │◄─ skew ─►│ │ │ The hold window │ now extends by the skew amount gets LONGER! │ making violations more likely

5. How to Fix Hold Violations

The fix is conceptually simple: add delay to the data path so data doesn't change too quickly.

해결 방법은 개념적으로 간단합니다: 데이터가 너무 빨리 변경되지 않도록 데이터 경로에 지연을 추가합니다.

Fix #1: Buffer Insertion (Most Common)

// The synthesis tool automatically inserts delay buffers
// Before fix:
//   FF_A ──────────────────► FF_B   (too fast!)

// After fix:
//   FF_A ──► [BUF] ──► [BUF] ──► FF_B   (enough delay)

// Each buffer adds ~0.02-0.05ns of delay
// Tool adds just enough buffers to meet hold

💡 Good News

In modern design flows, the synthesis and place-and-route tools automatically fix hold violations by inserting delay buffers. You rarely need to fix them manually. However, understanding the concept is crucial for debugging timing reports and interviews!

현대 설계 흐름에서는 합성 및 배치배선 도구가 지연 버퍼를 삽입하여 자동으로 홀드 위반을 수정합니다. 수동으로 수정할 필요는 거의 없습니다. 하지만 타이밍 보고서 디버깅과 면접을 위해 개념을 이해하는 것이 중요합니다!

Fix #2: Minimize Clock Skew

// Use balanced clock trees (CTS - Clock Tree Synthesis)
// Goal: all flip-flops receive the clock at nearly the same time

//           CLK_SOURCE
//              │
//          ┌───┴───┐
//          │       │
//       ┌──┴──┐ ┌──┴──┐
//       │     │ │     │
//      FF_A  FF_B FF_C FF_D
//
// Balanced tree = equal path length = minimal skew

Fix #3: Add Logic to Short Paths

// If you have a direct FF-to-FF connection, add intentional delay
module hold_fix_example (
    input  logic clk,
    input  logic d_in,
    output logic q_out
);
    logic stage1, stage1_delayed;
    
    // Stage 1 flip-flop
    always_ff @(posedge clk) begin
        stage1 <= d_in;
    end
    
    // Intentional delay (synthesis will honor this)
    // In real design, use: (* dont_touch = "true" *) on buffer
    assign stage1_delayed = stage1;  // Tool adds buffers here
    
    // Stage 2 flip-flop
    always_ff @(posedge clk) begin
        q_out <= stage1_delayed;
    end
endmodule

// Tool would insert 1-2 delay buffers to fix this

7. Practical Insights

🏭 In Industry

  • Hold fixes happen at place-and-route — the tool knows exact wire delays and can insert buffers precisely
  • Hold is checked at the "fast" corner — best-case timing (fastest transistors, lowest temperature, highest voltage)
  • Setup is checked at the "slow" corner — worst-case timing
  • Both must pass simultaneously across all process/voltage/temperature (PVT) corners
  • Hold violations cause functional failures at any clock speed — they're not just "push it'll work at lower freq"
  • 홀드 수정은 배치배선 단계에서 수행 — 도구가 정확한 배선 지연을 알고 있어 버퍼를 정밀하게 삽입
  • 홀드는 "빠른" 코너에서 확인 — 최적 타이밍 (가장 빠른 트랜지스터, 최저 온도, 최고 전압)
  • 셋업은 "느린" 코너에서 확인 — 최악의 타이밍
  • 모든 PVT 코너에서 둘 다 동시에 통과해야 함
  • 홀드 위반은 모든 클럭 속도에서 기능 오류 발생 — "낮은 주파수에서는 작동할 것"이 통하지 않음

⚠️ Interview Alert!

A classic interview question: "Can you fix a hold violation by changing the clock frequency?" The answer is NO! Hold time only depends on the data path delay between flip-flops on the same clock edge. Slowing the clock gives more time between edges but doesn't change what happens right after an edge.

대표적인 면접 질문: "클럭 주파수를 변경하여 홀드 위반을 수정할 수 있나요?" 답은 아니요! 홀드 타임은 같은 클럭 에지에서 플립플롭 간의 데이터 경로 지연에만 의존합니다. 클럭을 느리게 하면 에지 사이 시간은 늘어나지만 에지 직후에 일어나는 일은 변하지 않습니다.

8. Key Takeaways

📝 Today's Summary

  1. Hold time = data must stay stable after the clock edge
  2. Hold check: tclk2q + tcomb ≥ thold + tskew
  3. Cannot fix by slowing clock — this is the key difference from setup
  4. Main causes: short paths, clock skew, fast process corners
  5. Main fix: insert delay buffers (tools do this automatically)
  6. Checked at fast corner (opposite of setup time)
  1. 홀드 타임 = 클럭 에지 이후 데이터가 안정 유지되어야 함
  2. 홀드 체크: tclk2q + tcomb ≥ thold + tskew
  3. 클럭을 느리게 해도 해결 불가 — 셋업과의 핵심 차이점
  4. 주요 원인: 짧은 경로, 클럭 스큐, 빠른 프로세스 코너
  5. 주요 해결: 지연 버퍼 삽입 (도구가 자동으로 수행)
  6. 빠른 코너에서 확인 (셋업 타임과 반대)

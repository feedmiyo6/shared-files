1. The Fundamental Tradeoff

In digital design, area and performance are often at odds. Making a design faster usually requires more hardware (more area), while minimizing area often means sharing resources (slower). This is the most important optimization decision you'll face as a digital designer.

디지털 설계에서 면적과 성능은 종종 상충합니다. 설계를 더 빠르게 만들려면 보통 더 많은 하드웨어(더 많은 면적)가 필요하고, 면적을 최소화하려면 자원을 공유해야 해서 속도가 느려집니다. 이것이 디지털 설계자로서 직면할 가장 중요한 최적화 결정입니다.

🎯 The Core Tension

  • More Area → Higher Performance: Parallel hardware, dedicated units, wider datapaths
  • 면적 증가 → 성능 향상: 병렬 하드웨어, 전용 유닛, 더 넓은 데이터 경로
  • Less Area → Lower Performance: Shared resources, serialized operations, narrower paths
  • 면적 감소 → 성능 저하: 공유 자원, 직렬화된 연산, 좁은 경로
  • Sweet Spot: The designer's job is finding the right balance for the application
  • 최적점: 설계자의 역할은 애플리케이션에 맞는 적절한 균형점을 찾는 것입니다
Optimize ForTechniqueCost
Max PerformanceDedicated hardware per operationLarge area, more power
Min AreaTime-multiplex shared hardwareLower throughput, more control logic
BalancedPipeline + selective sharingModerate area, good throughput

2. Resource Sharing — Trading Performance for Area

Resource sharing is the primary technique for reducing area. Instead of duplicating hardware, you use one unit for multiple operations across different clock cycles.

자원 공유는 면적을 줄이기 위한 주요 기법입니다. 하드웨어를 복제하는 대신, 서로 다른 클록 사이클에서 하나의 유닛을 여러 연산에 사용합니다.

Before: Parallel (High Performance, Large Area)

// 4 separate multipliers — fast but area-expensive
module parallel_compute (
    input  logic [15:0] a, b, c, d,
    input  logic [15:0] w, x, y, z,
    output logic [31:0] p0, p1, p2, p3
);
    // All 4 multiplications happen in ONE cycle
    assign p0 = a * w;  // Multiplier 1
    assign p1 = b * x;  // Multiplier 2
    assign p2 = c * y;  // Multiplier 3
    assign p3 = d * z;  // Multiplier 4
endmodule
// Area: 4 multipliers | Latency: 1 cycle | Throughput: 4 results/cycle

After: Shared (Small Area, Lower Throughput)

// 1 shared multiplier — small but takes 4 cycles
module shared_compute (
    input  logic        clk, rst_n, start,
    input  logic [15:0] operands_a [4],  // 4 pairs of inputs
    input  logic [15:0] operands_b [4],
    output logic [31:0] results [4],
    output logic        done
);
    logic [1:0] idx;
    logic        busy;

    // Single shared multiplier
    wire [31:0] product = operands_a[idx] * operands_b[idx];

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            idx  <= 0;
            busy <= 0;
            done <= 0;
        end else if (start && !busy) begin
            idx  <= 0;
            busy <= 1;
            done <= 0;
        end else if (busy) begin
            results[idx] <= product;
            if (idx == 2'd3) begin
                busy <= 0;
                done <= 1;
            end else
                idx <= idx + 1;
        end
    end
endmodule
// Area: 1 multiplier + control | Latency: 4 cycles | Throughput: 1 result/cycle

💡 When to Share Resources

Share when: (1) the resource is expensive (multipliers, dividers, memories), (2) operations don't need to happen simultaneously, (3) you can afford the extra latency. Don't share: cheap resources like adders or muxes — the control overhead isn't worth it.

공유할 때: (1) 자원이 비쌀 때 (곱셈기, 나눗셈기, 메모리), (2) 연산이 동시에 일어날 필요가 없을 때, (3) 추가 지연을 감당할 수 있을 때. 공유하지 않을 때: 가산기나 먹스 같은 저렴한 자원 — 제어 오버헤드가 가치가 없습니다.

3. Parallelism — Trading Area for Performance

When performance is critical, we duplicate hardware to process multiple data elements simultaneously. This is the opposite of resource sharing.

성능이 중요할 때, 여러 데이터 요소를 동시에 처리하기 위해 하드웨어를 복제합니다. 이는 자원 공유의 반대입니다.

Example: Serial vs Parallel CRC Computation

// SERIAL: 1-bit-at-a-time CRC — minimal area
module crc8_serial (
    input  logic       clk, rst_n,
    input  logic       bit_in,
    input  logic       valid,
    output logic [7:0] crc
);
    logic feedback;
    assign feedback = crc[7] ^ bit_in;

    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n)       crc <= 8'hFF;
        else if (valid)  crc <= {crc[6:0], 1'b0} ^ (feedback ? 8'h07 : 8'h00);
endmodule
// Processes 1 bit/cycle — needs 8 cycles per byte
// PARALLEL: 8-bits-at-a-time CRC — more gates, 8x faster
module crc8_parallel (
    input  logic       clk, rst_n,
    input  logic [7:0] data_in,
    input  logic       valid,
    output logic [7:0] crc
);
    logic [7:0] next_crc;

    // Unrolled XOR tree — processes full byte in 1 cycle
    always_comb begin
        next_crc[0] = crc[0] ^ crc[6] ^ crc[7] ^ data_in[0] ^ data_in[6] ^ data_in[7];
        next_crc[1] = crc[0] ^ crc[1] ^ crc[6] ^ data_in[0] ^ data_in[1] ^ data_in[6];
        next_crc[2] = crc[1] ^ crc[2] ^ crc[7] ^ data_in[1] ^ data_in[2] ^ data_in[7];
        // ... remaining bits follow same pattern
        next_crc[7] = crc[5] ^ crc[6] ^ crc[7] ^ data_in[5] ^ data_in[6] ^ data_in[7];
    end

    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n)      crc <= 8'hFF;
        else if (valid) crc <= next_crc;
endmodule
// Processes 8 bits/cycle — 8x throughput, ~4x more gates

4. Pipelining — The "Best of Both Worlds"

Pipelining doesn't reduce area or increase single-operation speed — it increases throughput by letting multiple operations overlap. It adds area (pipeline registers) but keeps each stage's combinational logic short, enabling higher clock frequencies.

파이프라이닝은 면적을 줄이거나 단일 연산 속도를 높이지 않습니다 — 여러 연산이 겹치게 하여 처리량을 증가시킵니다. 면적(파이프라인 레지스터)이 추가되지만, 각 단계의 조합 논리를 짧게 유지하여 더 높은 클록 주파수를 가능하게 합니다.

Unpipelined vs Pipelined Multiplier-Accumulator

// UNPIPELINED: Long critical path, lower Fmax
module mac_unpipelined (
    input  logic         clk, rst_n,
    input  logic [15:0]  a, b,
    output logic [39:0]  acc
);
    // Multiply + Add in ONE cycle — long path!
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) acc <= '0;
        else        acc <= acc + (a * b);  // Critical path: mult + add
endmodule
// Fmax limited by: multiply delay + add delay
// PIPELINED: Split into 2 stages — higher Fmax
module mac_pipelined (
    input  logic         clk, rst_n,
    input  logic [15:0]  a, b,
    output logic [39:0]  acc
);
    // Stage 1: Multiply only
    logic [31:0] product_reg;
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) product_reg <= '0;
        else        product_reg <= a * b;

    // Stage 2: Accumulate only
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) acc <= '0;
        else        acc <= acc + product_reg;
endmodule
// Fmax limited by: max(multiply delay, add delay) — MUCH better!
// Cost: 32 extra flip-flops + 1 cycle more latency

5. Width Optimization — Bit-Level Area Control

One of the simplest area optimizations: use only as many bits as you need. Every extra bit means extra flip-flops, wider adders, and bigger muxes.

가장 간단한 면적 최적화 중 하나: 필요한 만큼의 비트만 사용하세요. 여분의 비트 하나마다 추가 플립플롭, 더 넓은 가산기, 더 큰 먹스가 필요합니다.

// BAD: Wasteful — 32-bit counter for values 0-99
logic [31:0] counter;  // Uses 32 FFs, only needs 7!

// GOOD: Right-sized — 7 bits covers 0-127
logic [6:0]  counter;  // 7 FFs — saves 25 flip-flops!

// ALSO GOOD: Use typedef for clarity
typedef logic [6:0] count_t;  // Max 127, enough for 0-99
count_t counter;

⚠️ Common Width Mistakes

  • Using int (32-bit) for small counters or state variables
  • 작은 카운터나 상태 변수에 int (32비트) 사용
  • Not truncating intermediate results: a[15:0] * b[15:0] produces 32 bits — do you need all of them?
  • 중간 결과를 잘라내지 않음: a[15:0] * b[15:0]은 32비트를 생성 — 전부 필요한가요?
  • Parameterizing width too generously — match to actual data requirements
  • 폭을 너무 여유있게 파라미터화 — 실제 데이터 요구사항에 맞추세요

6. Memory vs Logic Tradeoff

Sometimes you can replace combinational logic with a lookup table (ROM/memory), or vice versa. Each approach has different area and timing characteristics.

때로는 조합 논리를 룩업 테이블(ROM/메모리)로 대체하거나, 그 반대가 가능합니다. 각 접근 방식은 서로 다른 면적과 타이밍 특성을 가집니다.

// APPROACH 1: Compute with logic — small inputs only
function automatic logic [7:0] sin_lut_logic(input logic [3:0] angle);
    case (angle)
        4'd0:  return 8'd0;
        4'd1:  return 8'd25;
        4'd2:  return 8'd49;
        4'd3:  return 8'd71;
        // ... 16 entries total
        default: return 8'd0;
    endcase
endfunction
// Synthesizes to: combinational mux tree (good for small tables)

// APPROACH 2: Store in ROM — scales to large tables
logic [7:0] sin_rom [256];  // 256-entry ROM
initial $readmemh("sin_table.hex", sin_rom);

assign sin_value = sin_rom[angle];
// Synthesizes to: Block RAM or distributed RAM

7. Real-World Design Decision Framework

When optimizing your design, ask these questions in order:

설계를 최적화할 때, 다음 질문을 순서대로 하세요:

🧭 The Optimization Checklist

  1. What's the constraint? — Is this area-limited (ASIC cost, FPGA size) or performance-limited (timing closure, throughput)?
  2. 제약 조건은 무엇인가? — 면적 제한(ASIC 비용, FPGA 크기)인가 성능 제한(타이밍 클로저, 처리량)인가?
  3. Where's the bottleneck? — Profile first! Don't optimize what doesn't matter.
  4. 병목은 어디인가? — 먼저 프로파일링! 중요하지 않은 것을 최적화하지 마세요.
  5. Can you pipeline? — Often the cheapest way to meet timing (just add registers).
  6. 파이프라이닝이 가능한가? — 종종 타이밍을 맞추는 가장 저렴한 방법 (레지스터만 추가).
  7. Can you share expensive resources? — Multipliers, dividers, memories.
  8. 비싼 자원을 공유할 수 있는가? — 곱셈기, 나눗셈기, 메모리.
  9. Are your bit widths right? — Every unnecessary bit costs area.
  10. 비트 폭이 적절한가? — 불필요한 비트 하나마다 면적이 소모됩니다.
  11. Logic vs memory? — Trade computation for storage or vice versa.
  12. 논리 vs 메모리? — 계산을 저장으로 교환하거나 그 반대로.

💡 Automotive Ethernet Connection

In Minjun's T1 PHY/Switch work: Ethernet MAC/PHY designs face these exact tradeoffs. The CRC-32 engine must be parallel (line-rate processing), while diagnostic registers can be area-optimized (accessed rarely). Pipeline stages in the packet processing path are essential for meeting 100/1000 Mbps timing at the target clock frequency.

Minjun의 T1 PHY/Switch 작업에서: 이더넷 MAC/PHY 설계는 이러한 트레이드오프를 정확히 직면합니다. CRC-32 엔진은 병렬이어야 하고 (라인 레이트 처리), 진단 레지스터는 면적 최적화가 가능합니다 (드물게 접근). 패킷 처리 경로의 파이프라인 단계는 목표 클록 주파수에서 100/1000 Mbps 타이밍을 맞추는 데 필수적입니다.

🔑 Key Takeaways

  • No free lunch — every optimization has a cost somewhere else
  • 공짜 점심은 없다 — 모든 최적화는 다른 곳에서 비용이 발생합니다
  • Resource sharing saves area at the cost of throughput and control complexity
  • 자원 공유는 처리량과 제어 복잡성의 비용으로 면적을 절약합니다
  • Parallelism increases throughput at the cost of area
  • 병렬성은 면적의 비용으로 처리량을 증가시킵니다
  • Pipelining increases Fmax with moderate area cost (pipeline registers)
  • 파이프라이닝은 적당한 면적 비용(파이프라인 레지스터)으로 Fmax를 증가시킵니다
  • Right-size everything — bit widths, memories, resources
  • 모든 것을 적절히 크기 조정 — 비트 폭, 메모리, 자원
  • Profile first, optimize second — know where your bottleneck is
  • 먼저 프로파일링, 나중에 최적화 — 병목이 어디인지 파악하세요

Exercise 1: Resource Sharing — Shared ALU

Convert this parallel design with 3 separate adders into a shared design using 1 adder with a selection FSM. The design computes sum = (a+b) + (c+d) + (e+f).

3개의 별도 가산기가 있는 이 병렬 설계를 선택 FSM을 사용하는 1개의 공유 가산기 설계로 변환하세요. 설계는 sum = (a+b) + (c+d) + (e+f)를 계산합니다.

Starting Code (Parallel — 3 Adders)

module triple_add_parallel (
    input  logic [15:0] a, b, c, d, e, f,
    output logic [17:0] sum
);
    wire [16:0] ab = a + b;   // Adder 1
    wire [16:0] cd = c + d;   // Adder 2
    wire [16:0] ef = e + f;   // Adder 3
    assign sum = ab + cd + ef; // Adder 4+5 (reduction)
endmodule
// Total: 5 adders, 1 cycle latency

💡 Hints

  • Use a 2-bit state counter (IDLE, ADD_AB, ADD_CD, ADD_EF, REDUCE)
  • 2비트 상태 카운터 사용 (IDLE, ADD_AB, ADD_CD, ADD_EF, REDUCE)
  • Store intermediate results in registers
  • 중간 결과를 레지스터에 저장
  • Mux the adder inputs based on state
  • 상태에 따라 가산기 입력을 먹스
module triple_add_shared (
    input  logic         clk, rst_n, start,
    input  logic [15:0]  a, b, c, d, e, f,
    output logic [17:0]  sum,
    output logic         done
);
    typedef enum logic [2:0] {
        IDLE, ADD_AB, ADD_CD, ADD_EF, REDUCE
    } state_t;
    state_t state;

    // Shared adder inputs (muxed by state)
    logic [17:0] add_a, add_b;
    wire  [17:0] add_result = add_a + add_b; // THE shared adder

    // Intermediate storage
    logic [16:0] ab_reg, cd_reg, ef_reg;

    // Mux adder inputs based on state
    always_comb begin
        add_a = '0;
        add_b = '0;
        case (state)
            ADD_AB:  begin add_a = a; add_b = b; end
            ADD_CD:  begin add_a = c; add_b = d; end
            ADD_EF:  begin add_a = e; add_b = f; end
            REDUCE:  begin add_a = ab_reg + cd_reg; add_b = ef_reg; end
            default: begin add_a = '0; add_b = '0; end
        endcase
    end

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            state <= IDLE;
            done  <= 0;
        end else begin
            done <= 0;
            case (state)
                IDLE:   if (start) state <= ADD_AB;
                ADD_AB: begin ab_reg <= add_result[16:0]; state <= ADD_CD;  end
                ADD_CD: begin cd_reg <= add_result[16:0]; state <= ADD_EF;  end
                ADD_EF: begin ef_reg <= add_result[16:0]; state <= REDUCE;  end
                REDUCE: begin sum    <= add_result;       done <= 1; state <= IDLE; end
            endcase
        end
    end
endmodule
// Area: 1 adder + muxes + FSM | Latency: 4 cycles
// Tradeoff: ~75% less adder area, but 4x slower

Note: For adders, sharing is usually NOT worth it (adders are cheap). This exercise demonstrates the technique — in practice, share expensive resources like multipliers and dividers.

참고: 가산기의 경우, 공유는 보통 가치가 없습니다 (가산기는 저렴함). 이 연습은 기법을 시연합니다 — 실제로는 곱셈기, 나눗셈기 같은 비싼 자원을 공유하세요.

Exercise 2: Pipelining a Multi-Stage Computation

This unpipelined design computes result = (a * b) + (c * d) + offset in one cycle. Pipeline it into 3 stages to improve Fmax.

이 파이프라인 없는 설계는 result = (a * b) + (c * d) + offset을 한 사이클에 계산합니다. Fmax를 개선하기 위해 3단계로 파이프라이닝하세요.

// UNPIPELINED: Everything in one cycle
module compute_unpipelined (
    input  logic         clk, rst_n,
    input  logic [15:0]  a, b, c, d,
    input  logic [31:0]  offset,
    input  logic         valid_in,
    output logic [33:0]  result,
    output logic         valid_out
);
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) begin
            result    <= '0;
            valid_out <= 0;
        end else begin
            result    <= (a * b) + (c * d) + offset;
            valid_out <= valid_in;
        end
endmodule
// Critical path: multiply + add + add (VERY long!)

💡 Hints

  • Stage 1: Both multiplications (parallel — they're independent!)
  • 1단계: 두 곱셈 (병렬 — 독립적!)
  • Stage 2: Add the two products
  • 2단계: 두 곱 더하기
  • Stage 3: Add the offset
  • 3단계: 오프셋 더하기
  • Don't forget to pipeline the valid signal and the offset!
  • valid 신호와 offset도 파이프라이닝하는 것을 잊지 마세요!
module compute_pipelined (
    input  logic         clk, rst_n,
    input  logic [15:0]  a, b, c, d,
    input  logic [31:0]  offset,
    input  logic         valid_in,
    output logic [33:0]  result,
    output logic         valid_out
);
    // ===== STAGE 1: Parallel Multiplications =====
    logic [31:0] s1_ab, s1_cd;
    logic [31:0] s1_offset;    // Pipeline offset forward!
    logic        s1_valid;

    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) begin
            s1_ab     <= '0;
            s1_cd     <= '0;
            s1_offset <= '0;
            s1_valid  <= 0;
        end else begin
            s1_ab     <= a * b;       // Multiplier 1
            s1_cd     <= c * d;       // Multiplier 2
            s1_offset <= offset;       // Forward to stage 3
            s1_valid  <= valid_in;
        end

    // ===== STAGE 2: Add Products =====
    logic [32:0] s2_sum;
    logic [31:0] s2_offset;    // Keep forwarding offset!
    logic        s2_valid;

    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) begin
            s2_sum    <= '0;
            s2_offset <= '0;
            s2_valid  <= 0;
        end else begin
            s2_sum    <= s1_ab + s1_cd;  // Add products
            s2_offset <= s1_offset;        // Forward offset
            s2_valid  <= s1_valid;
        end

    // ===== STAGE 3: Add Offset =====
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) begin
            result    <= '0;
            valid_out <= 0;
        end else begin
            result    <= s2_sum + s2_offset;  // Final add
            valid_out <= s2_valid;
        end
endmodule
// Critical path: max(multiply, add, add) — MUCH shorter!
// Latency: 3 cycles | Throughput: 1 result/cycle
// Extra area: ~96 FFs for pipeline registers

⚠️ Common Pipelining Mistake

Forgetting to pipeline all signals that are used in later stages! The offset is needed in Stage 3 but enters at Stage 1 — it must be registered through each intermediate stage. Same for valid. Missing this creates timing paths that bypass pipeline stages.

나중 단계에서 사용되는 모든 신호를 파이프라이닝하는 것을 잊는 것! offset은 3단계에서 필요하지만 1단계에서 입력됩니다 — 각 중간 단계를 통해 레지스터되어야 합니다. valid도 마찬가지입니다.

module wasteful_design (

    output logic [31:0]  state        // FSM with 5 states

    logic [31:0] temp_sum;  // Intermediate: max value 510 (255+255)

    // ... implementation ...

module optimized_design (
    input  logic         clk, rst_n,

    output logic [10:0]  byte_count,  // 11 bits: 0-2047 covers 0-1518
    output logic [7:0]   checksum,    // 8 bits: matches actual width

);
    logic [8:0]  temp_sum;   // 9 bits: covers 0-510

endmodule

Exercise 4: Design Decision Challenge

You're designing a packet processor for a 100BASE-T1 Ethernet switch. Answer these tradeoff questions:

100BASE-T1 이더넷 스위치용 패킷 프로세서를 설계하고 있습니다. 다음 트레이드오프 질문에 답하세요:

Scenario

  • Clock: 125 MHz
  • Data bus: 8 bits (1 byte/cycle = 1 Gbps at 125 MHz? No! 100 Mbps = 1 byte per 10 cycles at 12.5 MHz effective)
  • 4 ports, each needs: CRC check, MAC address lookup, VLAN tag processing
  • FPGA: 50% utilized currently

Questions:

  1. Should the CRC engine be shared across all 4 ports or dedicated per-port?
  2. CRC 엔진을 4개 포트에서 공유해야 하나요 아니면 포트별 전용이어야 하나요?
  3. The MAC lookup table has 1024 entries. Logic-based or BRAM?
  4. MAC 룩업 테이블에 1024개 항목이 있습니다. 논리 기반 또는 BRAM?
  5. Should the VLAN processing be pipelined?
  6. VLAN 처리를 파이프라이닝해야 하나요?

Answer 1: CRC — Dedicated Per Port ✅

At 100 Mbps, each port generates 1 byte every ~10 cycles (at 125 MHz clock). With 4 ports, that's potentially 4 simultaneous bytes. A shared CRC would need complex arbitration and buffering. Since FPGA is only 50% utilized and CRC-8 is small, dedicate one per port — simpler design, no contention. If it were 1000BASE-T1 (line-rate every cycle), sharing would require careful scheduling.

100 Mbps에서 각 포트는 ~10 사이클마다 1바이트를 생성합니다 (125 MHz 클록). 4개 포트로 동시에 4바이트가 가능합니다. 공유 CRC는 복잡한 중재와 버퍼링이 필요합니다. FPGA가 50%만 사용되고 CRC가 작으므로, 포트당 전용이 합리적입니다.

Answer 2: MAC Lookup — BRAM ✅

1024 entries × 48-bit MAC + port info = lots of data. A case statement would consume thousands of LUTs. Use BRAM — it's designed for exactly this. One dual-port BRAM can serve 2 lookups/cycle, or use 2 BRAMs for 4 simultaneous lookups. The 1-cycle read latency is fine since packets take many cycles to process.

1024 항목 × 48비트 MAC + 포트 정보 = 많은 데이터. Case문은 수천 개의 LUT를 소비합니다. BRAM 사용 — 정확히 이를 위해 설계되었습니다. 1사이클 읽기 지연은 패킷 처리에 여러 사이클이 걸리므로 괜찮습니다.

Answer 3: VLAN Processing — Probably Not ✅

VLAN tag insertion/removal is simple (read a 12-bit VID, compare, modify). At 100 Mbps with a 125 MHz clock, there's plenty of time. No pipelining needed — the operations are simple enough to complete in one cycle. Save the pipeline registers. If timing analysis later shows it's on the critical path, THEN add a pipeline stage.

VLAN 태그 삽입/제거는 간단합니다 (12비트 VID 읽기, 비교, 수정). 125 MHz 클록으로 100 Mbps에서는 시간이 충분합니다. 파이프라이닝 불필요 — 연산이 한 사이클에 완료될 만큼 간단합니다.

💡 Key Lesson

The "right" answer depends on your specific constraints. With 50% FPGA utilization, you can afford dedicated resources. At 90% utilization, you'd share more aggressively. Always consider your actual constraints — don't over-optimize prematurely!

정답은 특정 제약에 따라 달라집니다. 50% FPGA 활용률에서는 전용 자원을 감당할 수 있습니다. 90% 활용률에서는 더 적극적으로 공유합니다. 항상 실제 제약을 고려하세요 — 조기에 과도하게 최적화하지 마세요!

📐 Day 15: Timing Closure

📝 Quiz 💻 Practice ← Day 14

Today we bring together everything from this week — setup time, hold time, clock skew, and critical path — into the practical discipline of timing closure. This is the process of ensuring your design meets all timing constraints so the hardware works at the desired clock frequency.

오늘은 이번 주에 배운 모든 것 — 셋업 타임, 홀드 타임, 클럭 스큐, 크리티컬 패스 — 을 타이밍 클로저(Timing Closure)라는 실전 과정으로 통합합니다. 이는 설계가 원하는 클럭 주파수에서 모든 타이밍 제약을 충족하도록 보장하는 프로세스입니다.

1. What Is Timing Closure?

Timing closure means your design passes all timing checks — every path meets setup and hold requirements. Until you achieve timing closure, your chip or FPGA won't reliably work at the target frequency.

타이밍 클로저란 설계가 모든 타이밍 검사를 통과하는 것을 의미합니다 — 모든 경로가 셋업 및 홀드 요구 사항을 충족합니다. 타이밍 클로저를 달성하기 전까지, 칩이나 FPGA는 목표 주파수에서 안정적으로 작동하지 않습니다.

🎯 The Timing Closure Flow

1. Write RTL → 2. Define Constraints (SDC) → 3. Synthesize → 4. Run STA → 5. Fix Violations → 6. Repeat until clean

1. RTL 작성 → 2. 제약 조건 정의 (SDC) → 3. 합성 → 4. STA 실행 → 5. 위반 수정 → 6. 깨끗해질 때까지 반복

2. SDC — Synopsys Design Constraints

SDC is the industry-standard format for specifying timing constraints. It tells the synthesis and STA tools what your timing goals are.

SDC는 타이밍 제약 조건을 지정하는 산업 표준 형식입니다. 합성 및 STA 도구에 타이밍 목표가 무엇인지 알려줍니다.

# Define a 200 MHz clock (5 ns period)
create_clock -name clk -period 5.0 [get_ports clk]

# Input delay: signals arrive 1.5 ns after clock edge
set_input_delay -clock clk 1.5 [get_ports data_in*]

# Output delay: signals must be stable 1.0 ns before next edge
set_output_delay -clock clk 1.0 [get_ports data_out*]

# False path: async reset doesn't need timing
set_false_path -from [get_ports rst_n]

# Multicycle path: takes 2 clock cycles
set_multicycle_path 2 -setup -from [get_cells slow_reg*] -to [get_cells result_reg*]

3. Static Timing Analysis (STA)

STA checks every path in your design without running simulation. It's exhaustive — it finds violations that simulation might miss.

STA는 시뮬레이션을 실행하지 않고 설계의 모든 경로를 검사합니다. 철저하게 검사하므로 시뮬레이션이 놓칠 수 있는 위반 사항도 찾아냅니다.

🔍 Setup Check Formula (Recap)

🔍 셋업 체크 공식 (복습)

Tclk > Tcq + Tcomb + Tsetup - Tskew

Tclk > Tcq + Tcomb + Tsetup - Tskew

Slack = Tclk - (Tcq + Tcomb + Tsetup)

슬랙 = Tclk - (Tcq + Tcomb + Tsetup)

  • Positive slack → Path meets timing ✅
  • 양의 슬랙 → 경로가 타이밍을 충족 ✅
  • Zero slack → Path barely meets timing ⚠️
  • 0 슬랙 → 경로가 간신히 타이밍을 충족 ⚠️
  • Negative slack → Timing violation! ❌
  • 음의 슬랙 → 타이밍 위반! ❌

5. Pipelining to Fix Setup Violations

The most common RTL-level fix. When a path is too long, insert a register in the middle.

가장 흔한 RTL 수준의 수정법입니다. 경로가 너무 길면 중간에 레지스터를 삽입합니다.

Before: Single-Stage (Fails at 200 MHz)

수정 전: 단일 단계 (200 MHz에서 실패)

// Critical path: adder + comparator + mux = 6.2 ns
// Need: 5.0 ns (200 MHz) — FAILS!
always_ff @(posedge clk) begin
    result <= select ? (a + b > threshold) : (c + d > threshold);
end

After: Two-Stage Pipeline (Meets 200 MHz)

수정 후: 2단계 파이프라인 (200 MHz 충족)

// Stage 1: Compute sums (3.1 ns path)
always_ff @(posedge clk) begin
    sum_ab      <= a + b;
    sum_cd      <= c + d;
    select_d1   <= select;     // Pipeline the control signal too!
    threshold_d1 <= threshold; // Pipeline all inputs used in stage 2
end

// Stage 2: Compare and select (2.8 ns path)
always_ff @(posedge clk) begin
    result <= select_d1 ? (sum_ab > threshold_d1) : (sum_cd > threshold_d1);
end

⚠️ Pipeline Gotcha: Don't Forget Control Signals!

When you pipeline data, you must also pipeline any control or reference signals that are used in later stages. Forgetting select_d1 or threshold_d1 above would cause functional bugs — the compare would use the wrong cycle's values.

데이터를 파이프라인할 때, 이후 단계에서 사용되는 제어 또는 참조 신호도 반드시 파이프라인해야 합니다. 위의 select_d1이나 threshold_d1을 잊으면 기능적 버그가 발생합니다 — 비교가 잘못된 사이클의 값을 사용하게 됩니다.

6. False Paths & Multicycle Paths

Not all paths are real. Properly constraining your design avoids wasted effort optimizing paths that don't matter.

모든 경로가 실제로 작동하는 것은 아닙니다. 설계를 적절히 제약하면 중요하지 않은 경로를 최적화하는 데 낭비되는 노력을 피할 수 있습니다.

🚫 False Paths

🚫 거짓 경로 (False Path)

Paths that structurally exist but can never be activated in real operation:

구조적으로 존재하지만 실제 동작에서는 절대 활성화될 수 없는 경로:

  • Asynchronous reset to data registers
  • 비동기 리셋에서 데이터 레지스터로의 경로
  • Paths between unrelated clock domains (handled by CDC)
  • 관련 없는 클럭 도메인 간의 경로 (CDC로 처리)
  • Test/debug paths not active in normal mode
  • 일반 모드에서 활성화되지 않는 테스트/디버그 경로

🔄 Multicycle Paths

🔄 멀티사이클 경로

Paths that intentionally take more than one clock cycle. Common examples:

의도적으로 하나 이상의 클럭 사이클을 사용하는 경로. 일반적인 예:

  • Multiplier results sampled every 2 cycles
  • 2사이클마다 샘플링되는 곱셈기 결과
  • Slow configuration registers updated infrequently
  • 드물게 업데이트되는 느린 구성 레지스터
  • Enable-gated data paths
  • 인에이블 게이트된 데이터 경로
// Multicycle example: multiplier takes 2 cycles
module slow_multiply (
    input  logic        clk, rst_n,
    input  logic [15:0] a, b,
    input  logic        valid_in,
    output logic [31:0] product,
    output logic        valid_out
);
    logic [31:0] mult_result;
    logic        valid_d1;

    // Combinational multiply — big, slow
    assign mult_result = a * b;

    // Sample result every 2 cycles (valid_in pulses every 2 clocks)
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            product   <= '0;
            valid_d1  <= 1'b0;
            valid_out <= 1'b0;
        end else begin
            valid_d1  <= valid_in;
            valid_out <= valid_d1;
            if (valid_d1)
                product <= mult_result;
        end
    end
endmodule

// SDC constraint for this module:
// set_multicycle_path 2 -setup -from [get_pins a_reg*/Q] -to [get_pins product_reg*/D]
// set_multicycle_path 1 -hold  -from [get_pins a_reg*/Q] -to [get_pins product_reg*/D]

7. Timing Closure Strategies Summary

🎯 Timing Closure Decision Tree

🎯 타이밍 클로저 결정 트리

Negative setup slack?

셋업 슬랙이 음수인가?

  1. Is the path real? → If not, mark as false path
  2. 경로가 실제인가? → 아니면 거짓 경로로 표시
  3. Does it need 1 cycle? → If not, mark as multicycle
  4. 1사이클이 필요한가? → 아니면 멀티사이클로 표시
  5. Can you restructure logic? → Reduce combinational depth
  6. 로직을 재구성할 수 있는가? → 조합 논리 깊이 감소
  7. Can you pipeline? → Add register stages
  8. 파이프라인할 수 있는가? → 레지스터 단계 추가
  9. Last resort → Reduce clock frequency
  10. 최후의 수단 → 클럭 주파수 감소

💡 Interview Tip

Timing closure questions are extremely common in digital design interviews. Be ready to explain: (1) What slack is and how it's calculated, (2) How to fix setup vs hold violations, (3) When to use false_path vs multicycle_path, and (4) How pipelining trades latency for frequency.

타이밍 클로저 질문은 디지털 설계 면접에서 매우 흔합니다. 다음을 설명할 준비를 하세요: (1) 슬랙이란 무엇이고 어떻게 계산되는지, (2) 셋업 vs 홀드 위반을 어떻게 수정하는지, (3) false_path vs multicycle_path를 언제 사용하는지, (4) 파이프라이닝이 어떻게 지연 시간을 대가로 주파수를 높이는지.

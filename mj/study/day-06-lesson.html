1. What is a Finite State Machine?

A Finite State Machine (FSM) is a circuit that moves through a fixed set of states based on inputs and clock edges. At any given moment, the FSM is in exactly one state. On each clock edge, it transitions to the next state based on the current state and inputs.

유한 상태 기계(FSM)는 입력과 클럭 엣지에 따라 정해진 상태들 사이를 이동하는 회로입니다. 어느 순간이든 FSM은 정확히 하나의 상태에 있으며, 각 클럭 엣지에서 현재 상태와 입력에 따라 다음 상태로 전이합니다.

FSMs are everywhere in digital design — traffic lights, protocol handlers, CPU controllers, USB interfaces, memory controllers. If your hardware needs to "remember where it is" and "decide what to do next," you need an FSM.

FSM은 디지털 설계 어디에나 있습니다 — 신호등, 프로토콜 핸들러, CPU 컨트롤러, USB 인터페이스, 메모리 컨트롤러. 하드웨어가 "현재 위치를 기억"하고 "다음 동작을 결정"해야 한다면 FSM이 필요합니다.

🔑 Three Core Components of an FSM

1. States — the possible conditions the machine can be in (e.g., IDLE, RUNNING, DONE)
2. Transitions — rules for moving from one state to another based on inputs
3. Outputs — signals produced based on the current state (and possibly inputs)

1. 상태(States) — 기계가 취할 수 있는 가능한 조건 (예: IDLE, RUNNING, DONE)
2. 전이(Transitions) — 입력에 따라 한 상태에서 다른 상태로 이동하는 규칙
3. 출력(Outputs) — 현재 상태(및 가능하면 입력)에 따라 생성되는 신호

2. State Diagrams

Before writing any code, always draw a state diagram. It's a visual map of your FSM — circles for states, arrows for transitions, and labels for conditions.

코드를 작성하기 전에 항상 상태 다이어그램을 먼저 그리세요. FSM의 시각적 지도입니다 — 원은 상태, 화살표는 전이, 라벨은 조건을 나타냅니다.

Here's a simple example — a door lock controller:

간단한 예시 — 도어 잠금 컨트롤러:

┌──────────┐ │ │ ──► │ LOCKED │ ◄──── wrong_code │ │ ────┐ └────┬─────┘ │ │ │ correct_code │ │ │ ▼ │ ┌──────────┐ │ │ │ │ │ UNLOCKED │─────┘ │ │ timeout └──────────┘

Two states (LOCKED, UNLOCKED), two inputs (correct_code, timeout). Simple, clear, unambiguous. This is what you should have before touching SystemVerilog.

두 개의 상태(LOCKED, UNLOCKED), 두 개의 입력(correct_code, timeout). 심플하고 명확합니다. SystemVerilog를 작성하기 전에 이것을 먼저 준비해야 합니다.

3. FSM in SystemVerilog — The Standard Pattern

There's a clean, industry-standard way to code FSMs in SystemVerilog. It uses three blocks:

SystemVerilog에서 FSM을 코딩하는 깔끔한 산업 표준 방식이 있습니다. 세 개의 블록을 사용합니다:

Block Purpose 목적 Type 유형
1. State Register Stores current state, updates on clock edge 현재 상태 저장, 클럭 엣지에서 업데이트 always_ff
2. Next-State Logic Determines next state from current state + inputs 현재 상태 + 입력으로 다음 상태 결정 always_comb
3. Output Logic Generates outputs from current state 현재 상태에서 출력 생성 always_comb

Let's implement our door lock:

도어 잠금장치를 구현해봅시다:

typedef enum logic [1:0] {
    LOCKED   = 2'b00,
    UNLOCKED = 2'b01
} state_t;

module door_lock (
    input  logic clk,
    input  logic rst_n,
    input  logic correct_code,
    input  logic timeout,
    output logic door_open
);

    state_t state, next_state;

    // Block 1: State Register (sequential)
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            state <= LOCKED;
        else
            state <= next_state;
    end

    // Block 2: Next-State Logic (combinational)
    always_comb begin
        next_state = state;  // Default: stay in current state
        case (state)
            LOCKED: begin
                if (correct_code)
                    next_state = UNLOCKED;
            end
            UNLOCKED: begin
                if (timeout)
                    next_state = LOCKED;
            end
            default: next_state = LOCKED;
        endcase
    end

    // Block 3: Output Logic
    always_comb begin
        door_open = (state == UNLOCKED);
    end

endmodule

💡 Why next_state = state as the default?

💡 왜 next_state = state를 기본값으로?

This prevents latches. If you forget to assign next_state in some branch of your case statement, the default ensures it stays in the current state rather than synthesis inferring a latch. Always do this!

이것은 래치를 방지합니다. case 문의 일부 분기에서 next_state를 할당하는 것을 잊으면, 기본값이 합성이 래치를 추론하는 대신 현재 상태를 유지하도록 보장합니다. 항상 이렇게 하세요!

4. The typedef enum — Named States

Using typedef enum for states is critical. It makes your code readable and gives you:

typedef enum을 상태에 사용하는 것은 매우 중요합니다. 코드를 읽기 쉽게 만들고 다음을 제공합니다:

  • Named states — LOCKED is clearer than 2'b00
  • Waveform labels — simulators show state names instead of numbers
  • Type checking — compiler catches mismatched state types
  • Easy expansion — adding states is clean
  • 이름이 있는 상태 — LOCKED가 2'b00보다 명확
  • 파형 라벨 — 시뮬레이터가 숫자 대신 상태 이름 표시
  • 타입 검사 — 컴파일러가 불일치하는 상태 타입 감지
  • 쉬운 확장 — 상태 추가가 깔끔
// Good — named states with explicit encoding
typedef enum logic [2:0] {
    IDLE    = 3'b000,
    START   = 3'b001,
    RUNNING = 3'b010,
    DONE    = 3'b100
} state_t;

// Bad — magic numbers everywhere
if (state == 3'b010)  // What state is this??

5. A Bigger Example: Packet Receiver

Let's look at a more realistic FSM — a simple packet receiver that waits for a start-of-frame, receives data bytes, then signals done:

더 실제적인 FSM을 봅시다 — 프레임 시작을 기다리고, 데이터 바이트를 수신한 다음 완료를 알리는 간단한 패킷 수신기:

┌──────┐ ──► │ IDLE │ ◄─────────────────┐ └──┬───┘ │ │ sof (start of frame) │ ▼ │ ┌──────┐ │ │ RECV │──► count == MAX ───┘ │ │ (via DONE) └──┬───┘ │ count == MAX ▼ ┌──────┐ │ DONE │ ──► (1 cycle) ──► IDLE └──────┘ 
typedef enum logic [1:0] {
    IDLE = 2'b00,
    RECV = 2'b01,
    DONE = 2'b10
} pkt_state_t;

module packet_receiver #(
    parameter int MAX_BYTES = 8
)(
    input  logic       clk,
    input  logic       rst_n,
    input  logic       sof,        // start of frame
    input  logic       data_valid,
    input  logic [7:0] data_in,
    output logic       pkt_done,
    output logic       receiving
);

    pkt_state_t state, next_state;
    logic [3:0] byte_count;

    // State register
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            state <= IDLE;
        else
            state <= next_state;
    end

    // Byte counter
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            byte_count <= '0;
        else if (state == IDLE)
            byte_count <= '0;
        else if (state == RECV && data_valid)
            byte_count <= byte_count + 1;
    end

    // Next-state logic
    always_comb begin
        next_state = state;
        case (state)
            IDLE: if (sof) next_state = RECV;
            RECV: if (byte_count == MAX_BYTES - 1 && data_valid)
                      next_state = DONE;
            DONE: next_state = IDLE;
            default: next_state = IDLE;
        endcase
    end

    // Output logic
    always_comb begin
        pkt_done  = (state == DONE);
        receiving = (state == RECV);
    end

endmodule

🔑 Key Pattern: Counters with FSMs

🔑 핵심 패턴: FSM과 카운터

Notice how byte_count lives in its own always_ff block, separate from the state register. This is clean practice — the FSM controls when counting happens, the counter block handles how.

byte_count가 상태 레지스터와 별도의 always_ff 블록에 있는 것에 주목하세요. 이것이 깔끔한 관행입니다 — FSM은 카운팅이 언제 발생하는지 제어하고, 카운터 블록은 어떻게 카운트하는지를 처리합니다.

6. Testbench for an FSM

Testing an FSM means walking through each transition. Here's how to verify our door lock:

FSM 테스트는 각 전이를 하나씩 확인하는 것입니다. 도어 잠금장치를 검증하는 방법:

module tb_door_lock;
    logic clk, rst_n, correct_code, timeout, door_open;

    door_lock dut (.*);

    // Clock generation
    initial clk = 0;
    always #5 clk = ~clk;

    initial begin
        // Reset
        rst_n = 0; correct_code = 0; timeout = 0;
        #20 rst_n = 1;

        // Verify starts LOCKED
        assert(door_open == 0) else $error("Should start locked!");

        // Enter correct code → should UNLOCK
        @(posedge clk) correct_code = 1;
        @(posedge clk) correct_code = 0;
        @(posedge clk);
        assert(door_open == 1) else $error("Should be unlocked!");

        // Timeout → should LOCK again
        @(posedge clk) timeout = 1;
        @(posedge clk) timeout = 0;
        @(posedge clk);
        assert(door_open == 0) else $error("Should be locked!");

        $display("All tests passed!");
        $finish;
    end
endmodule

7. Common FSM Mistakes

⚠️ Mistake #1: Forgetting the Default in case

Without a default case, if your FSM somehow enters an undefined state (cosmic ray, power glitch), it gets stuck forever. Always include default: next_state = IDLE;

default 케이스 없이, FSM이 어떻게든 정의되지 않은 상태에 진입하면(우주선, 전원 글리치) 영원히 멈춥니다. 항상 default: next_state = IDLE;를 포함하세요.

⚠️ Mistake #2: Using always_ff for Next-State Logic

Next-state logic is combinational — it must use always_comb, not always_ff. Only the state register itself is sequential.

다음 상태 로직은 조합 논리입니다 — always_ff가 아닌 always_comb을 사용해야 합니다. 상태 레지스터 자체만 순차 논리입니다.

⚠️ Mistake #3: Not Setting Default next_state

If you don't set next_state = state; at the top of your always_comb block, any missing assignment path will infer a latch. Synthesis tools will warn you, but it's a real bug.

always_comb 블록 상단에서 next_state = state;를 설정하지 않으면, 누락된 할당 경로가 래치를 추론합니다. 합성 도구가 경고하지만 실제 버그입니다.

8. Summary

📋 Today's Key Takeaways

📋 오늘의 핵심 요약

  1. FSMs have states, transitions, and outputs
  2. Always draw a state diagram first
  3. Use the 3-block pattern: state register (always_ff), next-state logic (always_comb), output logic (always_comb)
  4. Use typedef enum for readable state names
  5. Always set next_state = state as default to prevent latches
  6. Always include a default case for safety
  7. Test every transition in your testbench
  1. FSM은 상태, 전이, 출력을 가짐
  2. 항상 상태 다이어그램을 먼저 그리기
  3. 3블록 패턴 사용: 상태 레지스터(always_ff), 다음 상태 로직(always_comb), 출력 로직(always_comb)
  4. 읽기 쉬운 상태 이름을 위해 typedef enum 사용
  5. 래치 방지를 위해 항상 next_state = state를 기본값으로 설정
  6. 안전을 위해 항상 default 케이스 포함
  7. 테스트벤치에서 모든 전이를 테스트

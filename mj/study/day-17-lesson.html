📅 Day 17: 2-Flop Synchronizer

Week 4, Day 2 — Clock Domain Crossing (CDC)

4주차, 2일 — 클록 도메인 크로싱 (CDC)

Yesterday we learned about metastability — what it is, why it's dangerous, and how it can corrupt data. Today we learn the #1 defense against metastability: the 2-flop synchronizer.

어제 메타스테이빌리티에 대해 배웠습니다 — 무엇인지, 왜 위험한지, 어떻게 데이터를 손상시키는지. 오늘은 메타스테이빌리티에 대한 #1 방어책인 2-플롭 동기화기를 배웁니다.

1. Why Do We Need a Synchronizer?

When a signal crosses from one clock domain to another, it can change at any time relative to the receiving clock — including during the setup/hold window. This causes metastability. A synchronizer gives the metastable signal time to resolve before it's used by downstream logic.

신호가 한 클록 도메인에서 다른 클록 도메인으로 넘어갈 때, 수신 클록 기준 아무 때나 변할 수 있습니다 — 셋업/홀드 윈도우 동안 포함. 이것이 메타스테이빌리티를 유발합니다. 동기화기는 메타스테이블 신호가 다운스트림 로직에 사용되기 전에 안정될 시간을 줍니다.

🔑 Core Idea

The 2-flop synchronizer is two flip-flops in series, both clocked by the receiving clock domain. The first flop may go metastable — the second flop gives it a full clock cycle to resolve.

2-플롭 동기화기는 두 개의 플립플롭을 직렬로 연결한 것으로, 둘 다 수신 클록 도메인으로 클로킹됩니다. 첫 번째 플롭이 메타스테이블 상태가 될 수 있고 — 두 번째 플롭이 안정될 수 있는 전체 클록 주기를 줍니다.

2. How It Works

  CLK_A domain          │         CLK_B domain
                        │
  ┌──────┐              │    ┌──────┐     ┌──────┐
  │      │  async_sig   │    │ FF1  │     │ FF2  │
  │ SRC  ├──────────────┼───►│      ├────►│      ├───► sync_out
  │      │              │    │      │     │      │
  └──────┘              │    └──┬───┘     └──┬───┘
                        │       │            │
                        │    CLK_B        CLK_B
                        │
               Domain boundary

Step by step:

단계별 설명:

  1. Signal from CLK_A domain arrives asynchronously at FF1
  2. FF1 samples it on CLK_B's rising edge — may go metastable
  3. FF1 has one full CLK_B period to resolve to 0 or 1
  4. FF2 samples the resolved output of FF1 — clean, stable signal
  5. sync_out is now safe to use in CLK_B domain
  6. CLK_A 도메인의 신호가 FF1에 비동기적으로 도착
  7. FF1이 CLK_B의 상승 에지에서 샘플링 — 메타스테이블 상태가 될 수 있음
  8. FF1이 0 또는 1로 안정되기 위해 전체 CLK_B 주기를 가짐
  9. FF2가 FF1의 안정된 출력을 샘플링 — 깨끗하고 안정적인 신호
  10. sync_out은 이제 CLK_B 도메인에서 안전하게 사용 가능

3. SystemVerilog Implementation

module sync_2ff (
    input  logic clk_b,       // Receiving clock
    input  logic rst_n,       // Active-low reset
    input  logic async_in,    // Asynchronous input from CLK_A
    output logic sync_out     // Synchronized output in CLK_B
);

    logic meta_ff;  // First flop — may go metastable

    always_ff @(posedge clk_b or negedge rst_n) begin
        if (!rst_n) begin
            meta_ff  <= 1'b0;
            sync_out <= 1'b0;
        end else begin
            meta_ff  <= async_in;   // Stage 1: capture
            sync_out <= meta_ff;    // Stage 2: resolve
        end
    end

endmodule

💡 Pro Tip: Naming Convention

Many teams name the first flop meta_ff or sync_ff1 to clearly indicate it may be metastable. This helps code reviewers immediately identify synchronizer stages.

많은 팀에서 첫 번째 플롭을 meta_ff 또는 sync_ff1으로 명명하여 메타스테이블 상태가 될 수 있음을 명확히 표시합니다. 이는 코드 리뷰어가 동기화기 단계를 즉시 식별하는 데 도움이 됩니다.

4. The Math: MTBF

MTBF (Mean Time Between Failures) measures how often a synchronizer is expected to fail. With a 2-flop synchronizer:

MTBF (평균 고장 간격)는 동기화기가 얼마나 자주 실패하는지를 측정합니다. 2-플롭 동기화기에서:

📊 MTBF Formula

MTBF = e^(t_r / τ) / (T₀ · f_clk · f_data)

t_r   = resolution time (one clock period available)
τ     = metastability time constant (technology-dependent)
f_clk = receiving clock frequency
f_data = rate of data transitions
T₀    = technology constant

Key insight: MTBF grows exponentially with resolution time. Doubling the clock period makes MTBF astronomically higher. Even at GHz frequencies, 2 flops typically achieve MTBF > 100 years.

핵심 통찰: MTBF는 해상 시간에 따라 기하급수적으로 증가합니다. 클록 주기를 두 배로 하면 MTBF가 천문학적으로 높아집니다. GHz 주파수에서도 2개 플롭으로 일반적으로 MTBF > 100년을 달성합니다.

6. Critical Rules

⚠️ Common Mistakes to Avoid

  1. Don't add logic between FF1 and FF2! The wire must be direct — any combinational logic increases the resolution time needed.
  2. Don't use a 2-flop synchronizer for multi-bit signals! Each bit may resolve to a different value → corrupted data. Use gray code counters or handshake protocols (covered in Days 18-19).
  3. Don't forget the reset! Both flops must reset to a known state to avoid garbage on startup.
  4. Don't constrain the path between FF1 and FF2! Tell synthesis tools this is a synchronizer so they don't optimize it away.
  5. FF1과 FF2 사이에 로직을 추가하지 마세요! 와이어는 직접 연결이어야 합니다 — 조합 로직을 추가하면 필요한 해상 시간이 증가합니다.
  6. 멀티비트 신호에 2-플롭 동기화기를 사용하지 마세요! 각 비트가 다른 값으로 안정될 수 있어 데이터 손상이 발생합니다. 그레이 코드 카운터 또는 핸드셰이크 프로토콜을 사용하세요 (18-19일차에서 다룸).
  7. 리셋을 잊지 마세요! 두 플롭 모두 알려진 상태로 리셋해야 시작 시 쓰레기 값을 방지합니다.
  8. FF1과 FF2 사이의 경로에 제약을 걸지 마세요! 합성 도구에 이것이 동기화기임을 알려서 최적화로 제거되지 않도록 하세요.

7. Synthesis Attributes

In real projects, you must tell the synthesis tool "this is a synchronizer — don't touch it!":

실제 프로젝트에서는 합성 도구에 "이것은 동기화기입니다 — 건드리지 마세요!"라고 알려야 합니다:

// Synopsys
(* dont_touch = "true" *) logic meta_ff;
(* async_reg = "true" *)  logic meta_ff;

// Xilinx (Vivado)
(* ASYNC_REG = "TRUE" *) logic meta_ff;
(* ASYNC_REG = "TRUE" *) logic sync_out;

// Cadence
// set_dont_touch [get_cells meta_ff]

💡 Why Attributes Matter

Without these attributes, the synthesis tool might: (1) merge the two flops into one, (2) move them apart physically, or (3) add logic between them. All of these break the synchronizer!

이러한 속성이 없으면 합성 도구가: (1) 두 플롭을 하나로 병합, (2) 물리적으로 멀리 배치, (3) 사이에 로직을 추가할 수 있습니다. 이 모든 것이 동기화기를 망가뜨립니다!

8. Parameterized N-Stage Synchronizer

module sync_nff #(
    parameter int STAGES = 2  // Default: 2 flops
)(
    input  logic clk,
    input  logic rst_n,
    input  logic async_in,
    output logic sync_out
);

    logic [STAGES-1:0] sync_pipe;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            sync_pipe <= '0;
        else
            sync_pipe <= {sync_pipe[STAGES-2:0], async_in};
    end

    assign sync_out = sync_pipe[STAGES-1];

endmodule

🎯 Key Takeaways

  • 2-flop synchronizer = simplest, most common CDC solution for single-bit signals
  • Both flops must be clocked by the receiving domain clock
  • No logic allowed between FF1 and FF2
  • MTBF grows exponentially with resolution time — 2 flops is almost always enough
  • Use synthesis attributes to protect the synchronizer from optimization
  • For multi-bit signals, you need different techniques (Days 18-20)
  • 2-플롭 동기화기 = 단일 비트 신호를 위한 가장 간단하고 일반적인 CDC 솔루션
  • 두 플롭 모두 수신 도메인 클록으로 클로킹되어야 함
  • FF1과 FF2 사이에 로직 없음
  • MTBF는 해상 시간에 따라 기하급수적으로 증가 — 2개 플롭이면 거의 항상 충분
  • 합성 속성을 사용하여 동기화기를 최적화로부터 보호
  • 멀티비트 신호에는 다른 기술 필요 (18-20일차)

Exercise 2: Write SDC ConstraintsSDC 제약 작성

Write SDC constraints for a design with these requirements:

다음 요구 사항을 가진 설계에 대한 SDC 제약을 작성하세요:

  • 100 MHz clock on port sys_clk
  • 포트 sys_clk에 100 MHz 클럭
  • Input data arrives 2 ns after clock edge on ports data_in[7:0]
  • 포트 data_in[7:0]에서 클럭 에지 후 2 ns에 입력 데이터 도착
  • Output must be stable 1.5 ns before next clock on port result_out
  • 포트 result_out에서 다음 클럭 1.5 ns 전에 출력이 안정되어야 함
  • Async reset rst_n — exclude from timing
  • 비동기 리셋 rst_n — 타이밍에서 제외
  • A slow config register path that takes 3 cycles
  • 3사이클이 소요되는 느린 구성 레지스터 경로
# 100 MHz clock → 10 ns period
create_clock -name sys_clk -period 10.0 [get_ports sys_clk]

# Input delay: data arrives 2 ns after clock edge
set_input_delay -clock sys_clk 2.0 [get_ports data_in*]

# Output delay: data must be stable 1.5 ns before next edge
set_output_delay -clock sys_clk 1.5 [get_ports result_out]

# Async reset: false path (not timing-critical)
set_false_path -from [get_ports rst_n]

# Slow config register: 3-cycle multicycle path
set_multicycle_path 3 -setup \
    -from [get_cells config_reg*] \
    -to   [get_cells config_dest_reg*]
set_multicycle_path 2 -hold \
    -from [get_cells config_reg*] \
    -to   [get_cells config_dest_reg*]

# Note: hold multicycle = setup multicycle - 1
# This is the standard convention!

💡 Why hold multicycle = setup - 1? When you relax setup to N cycles, the hold check still defaults to the original capture edge. Setting hold to N-1 moves the hold reference back to match, preventing overly conservative hold checks.

💡 왜 hold multicycle = setup - 1인가? 셋업을 N 사이클로 완화하면 홀드 체크는 여전히 원래 캡처 에지를 기본으로 합니다. 홀드를 N-1로 설정하면 홀드 참조가 뒤로 이동하여 과도하게 보수적인 홀드 체크를 방지합니다.

Exercise 3: Pipeline a Failing Design실패하는 설계를 파이프라인

This design fails timing at 250 MHz (4 ns period). The combinational path takes 5.8 ns. Pipeline it into 2 stages to meet timing.

이 설계는 250 MHz (4 ns 주기)에서 타이밍을 실패합니다. 조합 논리 경로가 5.8 ns 소요됩니다. 타이밍을 충족하기 위해 2단계 파이프라인으로 나누세요.

// FAILS at 250 MHz — combinational path = 5.8 ns > 4.0 ns
module data_processor (
    input  logic        clk, rst_n,
    input  logic [15:0] a, b, c,
    input  logic [1:0]  mode,
    output logic [15:0] result
);
    logic [15:0] sum, diff, product_trunc;

    // All in one cycle: add, subtract, multiply, mux
    always_comb begin
        sum           = a + b + c;        // ~1.8 ns
        diff          = a - b;             // ~1.2 ns
        product_trunc = (a * b) >> 8;      // ~3.0 ns
    end

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            result <= '0;
        else begin
            case (mode)                        // ~0.8 ns mux
                2'b00: result <= sum;
                2'b01: result <= diff;
                2'b10: result <= product_trunc;
                2'b11: result <= sum + diff;    // additional add
            endcase
        end
    end
endmodule

💡 Hints: (1) Stage 1: Compute sum, diff, product_trunc. (2) Stage 2: Mux select. (3) Don't forget to pipeline mode! (4) Critical path is through the multiply → mux.

💡 힌트: (1) 1단계: sum, diff, product_trunc 계산. (2) 2단계: Mux 선택. (3) mode를 파이프라인하는 것을 잊지 마세요! (4) 크리티컬 패스는 곱셈 → 먹스를 통과합니다.

// 2-stage pipeline — meets 250 MHz
module data_processor (
    input  logic        clk, rst_n,
    input  logic [15:0] a, b, c,
    input  logic [1:0]  mode,
    output logic [15:0] result
);
    // ── Stage 1 registers ──
    logic [15:0] sum_s1, diff_s1, product_trunc_s1;
    logic [1:0]  mode_s1;  // Pipeline the control signal!

    // Stage 1: Compute all operations (~3.0 ns worst case)
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            sum_s1           <= '0;
            diff_s1          <= '0;
            product_trunc_s1 <= '0;
            mode_s1          <= '0;
        end else begin
            sum_s1           <= a + b + c;
            diff_s1          <= a - b;
            product_trunc_s1 <= (a * b) >> 8;
            mode_s1          <= mode;
        end
    end

    // Stage 2: Mux select (~0.8 ns + add for mode 11)
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            result <= '0;
        else begin
            case (mode_s1)
                2'b00: result <= sum_s1;
                2'b01: result <= diff_s1;
                2'b10: result <= product_trunc_s1;
                2'b11: result <= sum_s1 + diff_s1;
            endcase
        end
    end

    // Result: +1 cycle latency, but meets 250 MHz!
    // Stage 1 critical path: ~3.0 ns (multiply) ✅ < 4.0 ns
    // Stage 2 critical path: ~2.0 ns (add+mux)  ✅ < 4.0 ns
endmodule

Key takeaways: (1) mode_s1 is pipelined — without it, stage 2 would use the wrong mode. (2) The multiply (slowest operation) is now isolated in stage 1. (3) Total latency increased by 1 cycle, but throughput stays at 1 result per clock.

핵심 포인트: (1) mode_s1이 파이프라인됨 — 없으면 2단계가 잘못된 모드를 사용. (2) 곱셈(가장 느린 연산)이 이제 1단계에 격리됨. (3) 총 지연이 1사이클 증가했지만, 처리량은 클럭당 1결과로 유지.

Exercise 4: Identify the Fix수정 방법 식별

For each scenario, choose the best timing closure strategy:

각 시나리오에 대해 최적의 타이밍 클로저 전략을 선택하세요:

Scenario A: A path from rst_n to data_reg shows -2.0 ns slack. The reset is asynchronous.

시나리오 A: rst_n에서 data_reg로의 경로가 -2.0 ns 슬랙을 보입니다. 리셋은 비동기입니다.

Scenario B: The critical path through a 32-bit multiplier has -1.5 ns slack. The multiplier output is only sampled every 3 clock cycles.

시나리오 B: 32비트 곱셈기를 통한 크리티컬 패스가 -1.5 ns 슬랙을 가집니다. 곱셈기 출력은 3 클럭 사이클마다만 샘플링됩니다.

Scenario C: A long chain of adders and comparators has -0.8 ns slack. All signals are used every cycle.

시나리오 C: 가산기와 비교기의 긴 체인이 -0.8 ns 슬랙을 가집니다. 모든 신호는 매 사이클 사용됩니다.

Scenario D: A path between clk_a domain and clk_b domain (unrelated clocks) fails timing.

시나리오 D: clk_a 도메인과 clk_b 도메인(관련 없는 클럭) 간의 경로가 타이밍을 실패합니다.

A: set_false_path — Async reset to data registers is not a real timing path. Mark it false.

A: set_false_path — 비동기 리셋에서 데이터 레지스터로는 실제 타이밍 경로가 아닙니다. 거짓 경로로 표시.

B: set_multicycle_path 3 — The multiplier output is only sampled every 3 cycles, so give it 3 cycles to settle.

B: set_multicycle_path 3 — 곱셈기 출력은 3사이클마다만 샘플링되므로, 안정되는 데 3사이클을 줍니다.

C: Pipeline — Real path used every cycle. Must break it into shorter stages with pipeline registers.

C: 파이프라인 — 매 사이클 사용되는 실제 경로. 파이프라인 레지스터로 더 짧은 단계로 나눠야 합니다.

D: set_false_path — Unrelated clock domains should be handled by CDC logic (synchronizers), not timing analysis. Mark the crossing as a false path.

D: set_false_path — 관련 없는 클럭 도메인은 타이밍 분석이 아닌 CDC 로직(동기화기)으로 처리해야 합니다. 크로싱을 거짓 경로로 표시.

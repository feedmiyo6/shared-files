🤝 Ready/Valid Handshake — Flow Control 🤝 Ready/Valid 핸드셰이크 — 흐름 제어

📝 Quiz 💻 Practice ← Day 24

Yesterday we explored backpressure mechanisms — stall signals and pipeline bubbles. Today we dive into the ready/valid handshake, the industry-standard protocol for reliable flow control between digital modules. This is the foundation of AXI, AHB, and virtually every modern SoC bus.

어제 우리는 백프레셔 메커니즘 — 스톨 신호와 파이프라인 버블에 대해 알아봤습니다. 오늘은 디지털 모듈 간 안정적인 흐름 제어를 위한 업계 표준 프로토콜인 ready/valid 핸드셰이크를 깊이 다룹니다. 이것은 AXI, AHB 및 거의 모든 현대 SoC 버스의 기초입니다.

1. The Core Protocol 1. 핵심 프로토콜

🎯 Ready/Valid Rules 🎯 Ready/Valid 규칙

The ready/valid handshake has exactly three signals:

ready/valid 핸드셰이크에는 정확히 세 가지 신호가 있습니다:

  • valid — Source asserts: "I have data to send"
  • valid — 소스가 주장: "보낼 데이터가 있습니다"
  • ready — Sink asserts: "I can accept data"
  • ready — 싱크가 주장: "데이터를 받을 수 있습니다"
  • data — The payload, valid when valid is high
  • data — 페이로드, valid가 high일 때 유효

Transfer occurs when: valid && ready are BOTH high on the same clock edge.

전송이 발생하는 시점: 같은 클럭 엣지에서 valid && ready가 모두 high일 때.

clk ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └ valid ────┐ ┌───────────┐ └───────────┘ └──── ready ────────┐ ┌───────┐ ┌── └───┘ └───────┘ data ════╳ A ╳═══════╳ B ╳═══════╳══ ↑ ↑ Transfer! Transfer! (valid&ready) (valid&ready)

In the diagram above, data A transfers on the first overlap of valid and ready. Data B transfers on the second overlap. The cycles where only one signal is high — no transfer happens, the data just waits.

위 다이어그램에서 데이터 A는 valid와 ready의 첫 번째 겹침에서 전송됩니다. 데이터 B는 두 번째 겹침에서 전송됩니다. 하나의 신호만 high인 사이클에서는 전송이 발생하지 않고 데이터가 대기합니다.

2. The Golden Rules (AXI-style) 2. 핵심 규칙 (AXI 스타일)

⚠️ Critical Protocol Rules ⚠️ 중요한 프로토콜 규칙

  1. Valid must NOT depend on Ready: The source must assert valid independently. It cannot wait to see ready before asserting valid — this creates combinational loops and deadlocks!
  2. Valid는 Ready에 의존하면 안 됩니다: 소스는 valid를 독립적으로 주장해야 합니다. valid를 주장하기 전에 ready를 기다리면 조합 루프와 데드락이 발생합니다!
  3. Valid must stay high until transfer: Once asserted, valid cannot drop until ready is also high (i.e., until the handshake completes).
  4. Valid는 전송까지 high를 유지해야 합니다: 한번 주장되면, valid는 ready도 high가 될 때까지 (즉, 핸드셰이크가 완료될 때까지) 떨어질 수 없습니다.
  5. Data must be stable while valid: The payload must not change while valid is high (until the transfer completes).
  6. Data는 valid 동안 안정적이어야 합니다: 페이로드는 valid가 high인 동안 (전송이 완료될 때까지) 변경되면 안 됩니다.
  7. Ready CAN depend on Valid (but the reverse is forbidden). The sink can look at valid to decide if it's ready.
  8. Ready는 Valid에 의존할 수 있습니다 (하지만 반대는 금지). 싱크는 valid를 확인하여 준비 여부를 결정할 수 있습니다.

3. Source (Producer) Implementation 3. 소스 (생산자) 구현

The source drives valid and data. It deasserts valid only after a successful transfer.

소스는 valid와 data를 구동합니다. 성공적인 전송 후에만 valid를 해제합니다.

module rv_source #(
    parameter WIDTH = 8
)(
    input  logic             clk,
    input  logic             rst_n,

    // Ready/Valid output interface
    output logic             out_valid,
    input  logic             out_ready,
    output logic [WIDTH-1:0] out_data,

    // Internal data source
    input  logic             new_data_avail,
    input  logic [WIDTH-1:0] new_data
);

    // Handshake completes when both valid and ready
    logic transfer;
    assign transfer = out_valid & out_ready;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            out_valid <= 1'b0;
            out_data  <= '0;
        end else if (transfer) begin
            // Transfer done — load next or deassert
            if (new_data_avail) begin
                out_valid <= 1'b1;
                out_data  <= new_data;
            end else begin
                out_valid <= 1'b0;
            end
        end else if (!out_valid && new_data_avail) begin
            // Not currently valid — pick up new data
            out_valid <= 1'b1;
            out_data  <= new_data;
        end
        // else: valid stays high, data stays stable (rule 2 & 3)
    end

endmodule

💡 Key Pattern 💡 핵심 패턴

Notice the source never checks out_ready before asserting out_valid. It asserts valid when it has data, period. It only uses out_ready to know when the transfer is done.

소스가 out_valid를 주장하기 전에 out_ready를 절대 확인하지 않는 것에 주목하세요. 데이터가 있으면 valid를 주장합니다, 끝. out_ready는 전송이 완료되었는지 확인할 때만 사용합니다.

4. Sink (Consumer) Implementation 4. 싱크 (소비자) 구현

The sink drives ready. It can freely assert or deassert ready based on its own capacity.

싱크는 ready를 구동합니다. 자체 용량에 따라 ready를 자유롭게 주장하거나 해제할 수 있습니다.

module rv_sink #(
    parameter WIDTH = 8
)(
    input  logic             clk,
    input  logic             rst_n,

    // Ready/Valid input interface
    input  logic             in_valid,
    output logic             in_ready,
    input  logic [WIDTH-1:0] in_data,

    // Downstream processing
    output logic [WIDTH-1:0] captured_data,
    output logic             data_captured,
    input  logic             downstream_busy
);

    // Ready when we can accept data
    assign in_ready = !downstream_busy;

    logic transfer;
    assign transfer = in_valid & in_ready;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            captured_data <= '0;
            data_captured <= 1'b0;
        end else begin
            data_captured <= transfer;
            if (transfer)
                captured_data <= in_data;
        end
    end

endmodule

5. Pipeline Stage with Ready/Valid 5. Ready/Valid 파이프라인 스테이지

The real power of ready/valid appears when you chain modules together. Each stage has an input interface (acts as sink) and an output interface (acts as source). This creates elastic pipelines that handle backpressure gracefully.

ready/valid의 진정한 힘은 모듈을 체인으로 연결할 때 나타납니다. 각 스테이지는 입력 인터페이스(싱크 역할)와 출력 인터페이스(소스 역할)를 가집니다. 이것이 백프레셔를 우아하게 처리하는 탄력적인 파이프라인을 만듭니다.

module rv_pipe_stage #(
    parameter WIDTH = 8
)(
    input  logic             clk,
    input  logic             rst_n,

    // Upstream (input) — we are the sink
    input  logic             in_valid,
    output logic             in_ready,
    input  logic [WIDTH-1:0] in_data,

    // Downstream (output) — we are the source
    output logic             out_valid,
    input  logic             out_ready,
    output logic [WIDTH-1:0] out_data
);

    // We can accept new data when downstream takes ours
    // OR when we have nothing stored
    assign in_ready = out_ready | !out_valid;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            out_valid <= 1'b0;
            out_data  <= '0;
        end else if (in_ready) begin
            out_valid <= in_valid;
            out_data  <= in_data;
        end
    end

endmodule

🔗 How in_ready Works 🔗 in_ready 작동 원리

in_ready = out_ready | !out_valid means:

in_ready = out_ready | !out_valid의 의미:

  • If we have no data stored (!out_valid) → always ready
  • 저장된 데이터가 없으면 (!out_valid) → 항상 준비됨
  • If we have data stored and downstream accepts it (out_ready) → ready (we'll clear and accept new)
  • 데이터가 저장되어 있고 다운스트림이 수락하면 (out_ready) → 준비됨 (비우고 새 데이터 수락)
  • If we have data stored and downstream is NOT ready → NOT ready (backpressure propagates!)
  • 데이터가 저장되어 있고 다운스트림이 준비되지 않으면 → 준비되지 않음 (백프레셔 전파!)

6. Skid Buffer — Breaking the Combinational Path 6. 스키드 버퍼 — 조합 경로 끊기

The simple pipe stage above has a problem: in_ready depends combinationally on out_ready. Across many stages, this creates a long combinational chain. A skid buffer adds a small buffer to break this path.

위의 간단한 파이프 스테이지에는 문제가 있습니다: in_ready가 조합적으로 out_ready에 의존합니다. 많은 스테이지에 걸쳐 긴 조합 체인이 만들어집니다. 스키드 버퍼는 작은 버퍼를 추가하여 이 경로를 끊습니다.

module skid_buffer #(
    parameter WIDTH = 8
)(
    input  logic             clk,
    input  logic             rst_n,

    // Input interface
    input  logic             in_valid,
    output logic             in_ready,
    input  logic [WIDTH-1:0] in_data,

    // Output interface
    output logic             out_valid,
    input  logic             out_ready,
    output logic [WIDTH-1:0] out_data
);

    // Main register + skid register
    logic [WIDTH-1:0] main_data, skid_data;
    logic main_valid, skid_valid;

    // Ready is registered — no combinational path!
    assign in_ready  = !skid_valid;  // Ready if skid is empty
    assign out_valid = main_valid;
    assign out_data  = main_data;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            main_valid <= 1'b0;
            skid_valid <= 1'b0;
            main_data  <= '0;
            skid_data  <= '0;
        end else begin
            // Downstream accepts — pull from skid or input
            if (out_ready | !main_valid) begin
                if (skid_valid) begin
                    // Drain skid buffer first
                    main_data  <= skid_data;
                    main_valid <= 1'b1;
                    skid_valid <= 1'b0;
                end else if (in_valid && in_ready) begin
                    // Accept from input
                    main_data  <= in_data;
                    main_valid <= 1'b1;
                end else begin
                    main_valid <= 1'b0;
                end
            end else if (in_valid && in_ready) begin
                // Downstream stalled — catch in skid
                skid_data  <= in_data;
                skid_valid <= 1'b1;
            end
        end
    end

endmodule

💡 Why "Skid"? 💡 왜 "스키드"인가?

When the downstream stalls, the upstream may have already sent data (one cycle latency of ready). The skid buffer "catches" this in-flight data, preventing data loss. Think of it like a skid mark — it's the momentum from the previous cycle.

다운스트림이 멈출 때, 업스트림이 이미 데이터를 보냈을 수 있습니다 (ready의 1 사이클 지연). 스키드 버퍼는 이 비행 중인 데이터를 "잡아서" 데이터 손실을 방지합니다. 이전 사이클의 관성으로 생기는 스키드 마크처럼 생각하면 됩니다.

8. Real-World Connection: AXI Protocol 8. 실제 연결: AXI 프로토콜

🌐 AXI Uses Ready/Valid Everywhere 🌐 AXI는 모든 곳에서 Ready/Valid를 사용합니다

The ARM AXI protocol has five channels, each using ready/valid:

ARM AXI 프로토콜에는 다섯 개의 채널이 있으며, 각각 ready/valid를 사용합니다:

  • AW (Write Address): AWVALID / AWREADY
  • AW (쓰기 주소): AWVALID / AWREADY
  • W (Write Data): WVALID / WREADY
  • W (쓰기 데이터): WVALID / WREADY
  • B (Write Response): BVALID / BREADY
  • B (쓰기 응답): BVALID / BREADY
  • AR (Read Address): ARVALID / ARREADY
  • AR (읽기 주소): ARVALID / ARREADY
  • R (Read Data): RVALID / RREADY
  • R (읽기 데이터): RVALID / RREADY

Master the ready/valid handshake, and you've mastered the building block of AXI. We'll explore AXI in depth next week!

ready/valid 핸드셰이크를 마스터하면 AXI의 기본 구성 요소를 마스터한 것입니다. 다음 주에 AXI를 심층적으로 탐구합니다!

9. Key Takeaways 9. 핵심 요약

📋 Summary 📋 요약

  1. Transfer = valid & ready. Both must be high on the clock edge.
  2. 전송 = valid & ready. 클럭 엣지에서 둘 다 high여야 합니다.
  3. Valid must NOT depend on ready — prevents deadlocks and combinational loops.
  4. Valid는 ready에 의존하면 안 됩니다 — 데드락과 조합 루프를 방지합니다.
  5. Valid stays high until transfer completes — data must be stable.
  6. Valid는 전송 완료까지 high를 유지 — 데이터가 안정적이어야 합니다.
  7. Skid buffers register the ready path for better timing across pipeline stages.
  8. 스키드 버퍼는 파이프라인 스테이지 간 더 나은 타이밍을 위해 ready 경로를 레지스터합니다.
  9. AXI uses ready/valid on all 5 channels — this is THE industry standard.
  10. AXI는 5개 채널 모두에서 ready/valid 사용 — 이것이 업계 표준입니다.

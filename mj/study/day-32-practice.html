Exercise 2: Spot the Expensive Hardware

Identify and fix the wasteful patterns 낭비적인 패턴을 식별하고 수정하세요

This module works in simulation but creates very expensive hardware. Find ALL the problems:

이 모듈은 시뮬레이션에서 작동하지만 매우 비싼 하드웨어를 생성합니다. 모든 문제를 찾으세요:

module wasteful_design (
    input  logic        clk,
    input  logic [7:0]  addr,
    input  logic [7:0]  wr_data,
    input  logic        wr_en,
    input  logic [15:0] dividend,
    input  logic [3:0]  divisor,
    output logic [7:0]  rd_data,
    output logic [15:0] quotient
);

// Problem 1: Memory
logic [7:0] mem [0:255];

always_ff @(posedge clk) begin
    if (wr_en)
        mem[addr] <= wr_data;
end

assign rd_data = mem[addr];  // ← What's wrong here?

// Problem 2: Arithmetic
assign quotient = dividend / divisor;  // ← What's wrong here?

endmodule

🔍 Hint: Think about: (1) How is the memory read happening? (2) What's the cost of division in combinational logic?

🔍 힌트: 생각해보세요: (1) 메모리 읽기가 어떻게 일어나는가? (2) 조합 논리에서 나눗셈의 비용은?

✅ Problems & Fixes

Problem 1: Asynchronous memory read → 2,048 flip-flops!

assign rd_data = mem[addr] is an async read. The synthesis tool cannot use block RAM — it must implement the entire 256×8 array as flip-flops. Fix: make the read synchronous.

assign rd_data = mem[addr]는 비동기 읽기입니다. 합성 도구가 블록 RAM을 사용할 수 없어 전체 256×8 배열을 플립플롭으로 구현해야 합니다.

// ✅ Fixed: Synchronous read → Block RAM
always_ff @(posedge clk) begin
    if (wr_en)
        mem[addr] <= wr_data;
    rd_data <= mem[addr];  // Now synchronous!
end

Problem 2: Combinational division → massive area!

Division in a single assign creates a huge combinational divider. For 16/4 bits, this is a large, slow circuit. Fix: use a multi-cycle divider or avoid division.

단일 assign에서의 나눗셈은 거대한 조합 나눗셈기를 만듭니다. 다중 사이클 나눗셈기를 사용하거나 나눗셈을 피하세요.

// ✅ If dividing by power-of-2, use shift instead!
// If divisor is always 2: assign quotient = dividend >> 1;
// If divisor is always 4: assign quotient = dividend >> 2;

Exercise 3: Count the Hardware

Calculate exact flip-flop and mux counts 정확한 플립플롭 및 멀티플렉서 수 계산

For each snippet, count the exact number of flip-flops and muxes:

각 코드 조각에 대해 정확한 플립플롭 및 멀티플렉서 수를 세세요:

Snippet A:

logic [31:0] accumulator;
logic        overflow;

always_ff @(posedge clk) begin
    if (reset)
        {overflow, accumulator} <= 33'b0;
    else if (load)
        {overflow, accumulator} <= {1'b0, data_in};
    else if (add_en)
        {overflow, accumulator} <= accumulator + data_in;
end

Snippet B:

logic [7:0] out;

always_comb begin
    if (sel_a)
        out = in_a;
    else if (sel_b)
        out = in_b;
    else if (sel_c)
        out = in_c;
    else
        out = 8'b0;
end

✅ Hardware Counts

Snippet A:

  • Flip-flops: 33 (32 for accumulator + 1 for overflow)
  • Muxes: Priority chain with 3 conditions → 3 levels of 33-bit 2:1 muxes (reset → load → add_en → hold)
  • Adder: 1× 33-bit adder (for the accumulate operation)
  • Clock enable: Combined from reset, load, add_en

Snippet B:

  • Flip-flops: 0 (purely combinational — always_comb!)
  • Muxes: 3× 8-bit 2:1 muxes in a priority chain
  • The chain: mux(sel_a, in_a, mux(sel_b, in_b, mux(sel_c, in_c, 8'b0)))
  • 체인: mux(sel_a, in_a, mux(sel_b, in_b, mux(sel_c, in_c, 8'b0)))
  • Critical path goes through all 3 mux levels!
  • 크리티컬 패스가 3개의 멀티플렉서 레벨을 모두 통과합니다!
Exercise 4: Write Hardware-Aware RTL

Design an ALU with known hardware cost 알려진 하드웨어 비용으로 ALU 설계

Write a simple 8-bit ALU that performs 4 operations. Before writing the code, predict what hardware each operation will create. Then write the code.

4개의 연산을 수행하는 간단한 8비트 ALU를 작성하세요. 코드를 작성하기 전에 각 연산이 어떤 하드웨어를 생성할지 예측하세요.

📋 Requirements

  • Inputs: a[7:0], b[7:0], op[1:0]
  • Output: result[7:0], zero_flag
  • Operations: 00=ADD, 01=AND, 10=XOR, 11=PASS-A
  • Use always_comb (combinational)
  • The zero_flag should be 1 when result is all zeros

🔍 Hint: Predict: ADD → adder, AND → AND gates, XOR → XOR gates, PASS → wires, case → 4:1 mux, zero_flag → NOR reduction. Then write the code!

🔍 힌트: 예측: ADD → 가산기, AND → AND 게이트, XOR → XOR 게이트, PASS → 와이어, case → 4:1 멀티플렉서, zero_flag → NOR 축소. 그런 다음 코드를 작성하세요!

✅ Solution

Hardware Prediction:

OperationHardwareCost
ADD (a + b)8-bit carry-chain adderLow
AND (a & b)8 AND gatesMinimal
XOR (a ^ b)8 XOR gatesMinimal
PASS (a)WiresZero
case(op)4:1 Mux (8-bit)Low
zero_flag8-input NOR (OR reduction + invert)Minimal
module alu_8bit (
    input  logic [7:0] a, b,
    input  logic [1:0] op,
    output logic [7:0] result,
    output logic       zero_flag
);

always_comb begin
    case (op)              // → 4:1 Mux
        2'b00: result = a + b;   // → 8-bit adder
        2'b01: result = a & b;   // → 8 AND gates
        2'b10: result = a ^ b;   // → 8 XOR gates
        2'b11: result = a;       // → wires (free)
        default: result = 8'b0;
    endcase
end

assign zero_flag = ~|result;  // → NOR reduction tree

endmodule

Total hardware: 1 adder + 8 AND gates + 8 XOR gates + 1 four-input mux (8-bit) + 1 NOR tree. Very efficient!

총 하드웨어: 가산기 1개 + AND 게이트 8개 + XOR 게이트 8개 + 4입력 멀티플렉서 1개 (8비트) + NOR 트리 1개. 매우 효율적입니다!

Exercise 5: Which Is Better?

Compare two implementations — predict hardware cost 두 구현을 비교하고 하드웨어 비용을 예측하세요

Both snippets compute the same output. Which produces more efficient hardware and why?

두 코드 조각은 동일한 출력을 계산합니다. 어느 것이 더 효율적인 하드웨어를 생성하고 왜 그런가요?

Version A:

always_comb begin
    if (sel == 2'b00)
        out = a;
    else if (sel == 2'b01)
        out = b;
    else if (sel == 2'b10)
        out = c;
    else
        out = d;
end

Version B:

always_comb begin
    unique case (sel)
        2'b00: out = a;
        2'b01: out = b;
        2'b10: out = c;
        2'b11: out = d;
    endcase
end

✅ Version B is better!

Version A: Creates a priority mux chain — 3 levels of 2:1 muxes. Each if comparison also needs equality comparators. Critical path: comparator → mux → comparator → mux → comparator → mux.

Version B: unique case tells the synthesis tool all conditions are mutually exclusive. It builds a flat 4:1 mux — just 1 level of selection. Much shorter critical path!

MetricVersion A (if-else)Version B (unique case)
Mux Levels3 (cascaded)1 (flat)
Comparators3 equality checksDirect decode
Critical PathLongerShorter ✅
AreaSlightly moreSlightly less ✅

Lesson: When conditions are mutually exclusive, always prefer case (or unique case) over if-else if chains. Modern tools may optimize both to the same result, but unique case guarantees it and is clearer intent.

교훈: 조건이 상호 배타적일 때는 if-else if 체인보다 case(또는 unique case)를 항상 선호하세요.

🏆 Key Takeaways

  • Always ask: "What hardware does this line create?"
  • 항상 물어보세요: "이 줄은 어떤 하드웨어를 생성하는가?"
  • Sync reads → RAM; Async reads → flip-flop arrays (expensive!)
  • 동기식 읽기 → RAM; 비동기식 읽기 → 플립플롭 배열 (비용이 큼!)
  • Constant shifts are free; variable shifts cost muxes
  • 상수 시프트는 무료; 가변 시프트는 멀티플렉서 비용이 발생
  • Use case over if-else if for mutually exclusive conditions
  • 상호 배타적 조건에는 if-else if보다 case를 사용
  • Avoid division in combinational logic — it's the most expensive operator!
  • 조합 논리에서 나눗셈을 피하세요 — 가장 비싼 연산자입니다!

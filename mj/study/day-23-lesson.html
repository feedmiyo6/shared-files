🚧 Day 23: Pipeline Hazards

📝 Quiz 🔧 Practice

Yesterday we learned how to add pipeline stages to improve throughput. Today we tackle the hard part: what happens when pipeline stages depend on each other? These conflicts are called hazards, and handling them correctly is essential for correct pipeline operation.

어제는 파이프라인 스테이지를 추가하여 처리량을 개선하는 방법을 배웠습니다. 오늘은 어려운 부분을 다룹니다: 파이프라인 스테이지가 서로 의존할 때 무슨 일이 일어나는가? 이러한 충돌을 해저드(hazard)라고 하며, 올바르게 처리하는 것이 파이프라인의 정확한 동작에 필수적입니다.

1. What Are Pipeline Hazards?

A pipeline hazard occurs when the next instruction in the pipeline cannot execute in its designated clock cycle. The pipeline must either stall (insert bubbles) or use special techniques to resolve the conflict.

파이프라인 해저드는 파이프라인의 다음 명령이 지정된 클록 사이클에서 실행될 수 없을 때 발생합니다. 파이프라인은 스톨(버블 삽입)하거나 특별한 기법을 사용하여 충돌을 해결해야 합니다.

2. Data Hazards (RAW, WAR, WAW)

Data hazards are the most common. They occur when instructions have data dependencies. The most critical type is Read-After-Write (RAW).

데이터 해저드가 가장 흔합니다. 명령들 사이에 데이터 의존성이 있을 때 발생합니다. 가장 중요한 유형은 쓰기 후 읽기 (RAW)입니다.

RAW (Read-After-Write) — True Dependency

Instruction B reads a value that Instruction A writes. If A hasn't finished writing, B reads stale data.

명령 B가 명령 A가 쓰는 값을 읽습니다. A가 쓰기를 완료하지 않았다면, B는 오래된 데이터를 읽습니다.

Cycle: 1 2 3 4 5 6 7 ┌─────┬─────┬─────┬─────┬─────┐ ADD: │ IF │ ID │ EX │ MEM │ WB │ ← writes result at WB └─────┴─────┴─────┴─────┴─────┘ ┌─────┬─────┬─────┬─────┬─────┐ SUB: │ IF │ ID │ EX │ MEM │ WB │ ← reads at ID (cycle 3) └─────┴─────┴─────┴─────┴─────┘ ↑ ↑ B reads here A writes here (cycle 3) (cycle 5) ⚠️ B reads BEFORE A writes = HAZARD!

3. Solving Data Hazards

Solution 1: Stalling (Bubble Insertion)

The simplest solution: freeze the pipeline until the data is ready. Insert "bubble" cycles (NOPs) where no useful work happens. Simple but costly — every stall wastes a cycle of throughput.

가장 간단한 해결책: 데이터가 준비될 때까지 파이프라인을 정지합니다. 유용한 작업이 없는 "버블" 사이클(NOP)을 삽입합니다. 간단하지만 비용이 큽니다 — 스톨마다 처리량 한 사이클을 낭비합니다.

Without stall (WRONG): With 2-cycle stall (CORRECT): C1 C2 C3 C4 C5 C1 C2 C3 C4 C5 C6 C7 IF ID EX MEM WB ADD IF ID EX MEM WB ADD IF ID EX MEM SUB IF 💤 💤 ID EX MEM SUB ↑ reads old data ↑ waits ↑ now reads correct data 
// Hazard detection unit — detect RAW dependency
module hazard_detector (
    input  logic [4:0] id_rs1, id_rs2,      // source regs in decode
    input  logic [4:0] ex_rd,                // dest reg in execute
    input  logic        ex_reg_write,         // execute writes a reg?
    input  logic [4:0] mem_rd,               // dest reg in memory
    input  logic        mem_reg_write,        // memory writes a reg?
    output logic        stall                // stall the pipeline?
);

    always_comb begin
        stall = 1'b0;
        
        // Check if decode sources match execute destination
        if (ex_reg_write && ex_rd != 5'd0) begin
            if (ex_rd == id_rs1 || ex_rd == id_rs2)
                stall = 1'b1;
        end
        
        // Check if decode sources match memory destination
        if (mem_reg_write && mem_rd != 5'd0) begin
            if (mem_rd == id_rs1 || mem_rd == id_rs2)
                stall = 1'b1;
        end
    end

endmodule

Solution 2: Data Forwarding (Bypassing)

Forwarding (also called bypassing) is the key optimization: instead of waiting for the result to be written back, we forward it directly from where it's computed to where it's needed. This eliminates most stalls!

포워딩(바이패싱이라고도 함)은 핵심 최적화입니다: 결과가 다시 쓰여질 때까지 기다리는 대신, 계산된 곳에서 필요한 곳으로 직접 전달합니다. 이로써 대부분의 스톨을 제거합니다!

┌──────────────────────────────────┐ │ FORWARDING PATH │ │ │ ▼ │ ┌────┐ ┌────┐ ┌────┐ ┌─────┐ ┌────┐ │ │ IF │→│ ID │→│ EX │→│ MEM │→│ WB │ │ └────┘ └────┘ └────┘ └─────┘ └────┘ │ ↑ │ │ │ │ └──────┘ EX→EX forward │ │ (1 cycle old result) │ │ │ └──────────── MEM→EX forward │ (2 cycle old result) │ 
// Forwarding MUX — select between normal and forwarded data
module forwarding_unit (
    input  logic [4:0] id_ex_rs1, id_ex_rs2,
    input  logic [4:0] ex_mem_rd,
    input  logic        ex_mem_reg_write,
    input  logic [4:0] mem_wb_rd,
    input  logic        mem_wb_reg_write,
    output logic [1:0] forward_a, forward_b
);

    // forward_a/b encoding:
    // 2'b00 = no forwarding (use register file)
    // 2'b01 = forward from MEM/WB stage
    // 2'b10 = forward from EX/MEM stage

    always_comb begin
        forward_a = 2'b00;
        forward_b = 2'b00;
        
        // EX/MEM forwarding (highest priority — most recent)
        if (ex_mem_reg_write && ex_mem_rd != 5'd0) begin
            if (ex_mem_rd == id_ex_rs1) forward_a = 2'b10;
            if (ex_mem_rd == id_ex_rs2) forward_b = 2'b10;
        end
        
        // MEM/WB forwarding (lower priority)
        if (mem_wb_reg_write && mem_wb_rd != 5'd0) begin
            if (mem_wb_rd == id_ex_rs1 && forward_a == 2'b00)
                forward_a = 2'b01;
            if (mem_wb_rd == id_ex_rs2 && forward_b == 2'b00)
                forward_b = 2'b01;
        end
    end

endmodule

⚠️ Load-Use Hazard — Forwarding Can't Fix Everything!

When a load instruction (memory read) is followed by an instruction that uses the loaded data, forwarding alone isn't enough. The data isn't available until the end of the MEM stage — one cycle too late for EX→EX forwarding. You must stall for 1 cycle even with forwarding.

로드 명령(메모리 읽기) 다음에 로드된 데이터를 사용하는 명령이 오면, 포워딩만으로는 부족합니다. MEM 스테이지 끝까지 데이터가 사용 불가능하여 EX→EX 포워딩에 한 사이클 늦습니다. 포워딩이 있어도 반드시 1 사이클 스톨해야 합니다.

// Load-use hazard detection
always_comb begin
    load_use_stall = 1'b0;
    
    // If EX stage has a load AND decode reads from that register
    if (id_ex_mem_read &&                       // EX stage is a load
        ((id_ex_rd == if_id_rs1) ||               // decode source 1 matches
         (id_ex_rd == if_id_rs2))) begin          // decode source 2 matches
        load_use_stall = 1'b1;                    // must stall 1 cycle
    end
end

4. Control Hazards

Control hazards occur when the pipeline doesn't know which instruction to fetch next because a branch hasn't been resolved yet. By the time a branch is decided (often in the EX stage), we've already fetched instructions after it that might be wrong!

제어 해저드는 분기가 아직 해결되지 않아 파이프라인이 다음에 어떤 명령을 페치해야 할지 모를 때 발생합니다. 분기가 결정될 때쯤(보통 EX 스테이지), 이미 틀릴 수 있는 다음 명령들을 페치해 버렸습니다!

Cycle: 1 2 3 4 5 6 7 ┌─────┬─────┬─────┬─────┬─────┐ BEQ: │ IF │ ID │ EX │ MEM │ WB │ └─────┴─────┴─────┴─────┴─────┘ ↑ Branch resolved here (cycle 3) ┌─────┬─────┐ NEXT+1: │ IF │ ID │ ← Already fetched! May be WRONG └─────┴─────┘ ┌─────┐ NEXT+2: │ IF │ ← Also fetched! May be WRONG └─────┘ If branch taken → flush these 2 instructions (2-cycle penalty)

Solution 1: Always Stall (Simple but Slow)

Stall the pipeline whenever a branch is detected. Wait until the branch is resolved, then fetch the correct instruction. This wastes 2+ cycles per branch.

분기가 감지될 때마다 파이프라인을 정지합니다. 분기가 해결될 때까지 기다린 후 올바른 명령을 페치합니다. 분기마다 2+ 사이클을 낭비합니다.

Solution 2: Branch Prediction

Predict whether the branch will be taken or not, and fetch instructions based on that prediction. If wrong, flush the incorrect instructions.

분기가 취해질지 아닐지 예측하고, 그 예측에 기반하여 명령을 페치합니다. 틀리면 잘못된 명령을 플러시합니다.

// Simple 2-bit saturating branch predictor
module branch_predictor #(
    parameter int TABLE_SIZE = 256
)(
    input  logic        clk, rst_n,
    input  logic [7:0] pc_index,          // lower bits of PC
    input  logic        branch_taken,      // actual outcome
    input  logic        update_en,         // update the predictor
    output logic        predict_taken      // prediction output
);

    // 2-bit counter per entry: 00=strong NT, 01=weak NT, 10=weak T, 11=strong T
    logic [1:0] counter_table [TABLE_SIZE];

    // Predict: MSB of counter determines prediction
    assign predict_taken = counter_table[pc_index][1];

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            for (int i = 0; i < TABLE_SIZE; i++)
                counter_table[i] <= 2'b01;  // weakly not-taken
        end else if (update_en) begin
            if (branch_taken && counter_table[pc_index] < 2'b11)
                counter_table[pc_index] <= counter_table[pc_index] + 1;
            else if (!branch_taken && counter_table[pc_index] > 2'b00)
                counter_table[pc_index] <= counter_table[pc_index] - 1;
        end
    end

endmodule

Solution 3: Pipeline Flush

When a branch misprediction is detected, flush (cancel) all instructions that entered the pipeline after the branch. Reset those pipeline registers to NOP values.

분기 오예측이 감지되면, 분기 이후 파이프라인에 들어온 모든 명령을 플러시(취소)합니다. 해당 파이프라인 레지스터를 NOP 값으로 리셋합니다.

// Pipeline flush on branch misprediction
always_ff @(posedge clk) begin
    if (branch_mispredict) begin
        // Flush IF/ID and ID/EX pipeline registers
        if_id_instruction <= 32'h00000013;  // NOP (addi x0, x0, 0)
        id_ex_instruction <= 32'h00000013;  // NOP
        id_ex_reg_write   <= 1'b0;
        id_ex_mem_read    <= 1'b0;
        id_ex_mem_write   <= 1'b0;
        id_ex_branch      <= 1'b0;
        
        // Redirect fetch to correct address
        pc <= branch_target;
    end
end

5. Structural Hazards

Structural hazards occur when two pipeline stages need the same hardware resource at the same time. The classic example: a single-port memory used for both instruction fetch (IF) and data access (MEM).

구조적 해저드는 두 파이프라인 스테이지가 동시에 같은 하드웨어 자원을 필요로 할 때 발생합니다. 고전적인 예: 명령 페치(IF)와 데이터 접근(MEM) 모두에 사용되는 단일 포트 메모리.

🔧 Common Solutions

  • Duplicate the resource: Use separate instruction and data memories (Harvard architecture)
  • 자원 복제: 별도의 명령 메모리와 데이터 메모리 사용 (하버드 아키텍처)
  • Pipeline the resource: Allow memory to handle two accesses in one cycle
  • 자원 파이프라인화: 메모리가 한 사이클에 두 접근을 처리하도록 허용
  • Stall: If neither option is feasible, stall one stage
  • 스톨: 두 옵션 모두 불가능하면 한 스테이지를 정지

6. Hazard Summary & Design Impact

📊 Performance Impact

In a typical program, about 30% of instructions are loads/stores and 20% are branches. Without hazard handling, a 5-stage pipeline would stall almost every other cycle. With forwarding and branch prediction:

일반적인 프로그램에서 약 30%의 명령이 로드/스토어이고 20%가 분기입니다. 해저드 처리 없이는 5단계 파이프라인이 거의 매 사이클마다 스톨합니다. 포워딩과 분기 예측을 사용하면:

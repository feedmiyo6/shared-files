Ready/Valid Handshake — Quiz Ready/Valid 핸드셰이크 — 퀴즈

Q1. When does a data transfer occur in a ready/valid handshake?ready/valid 핸드셰이크에서 데이터 전송은 언제 발생합니까?

  • A) When valid rises to highA) valid가 high로 올라갈 때
  • B) When both valid AND ready are high on a clock edgeB) 클럭 엣지에서 valid와 ready가 모두 high일 때
  • C) When ready rises to highC) ready가 high로 올라갈 때
  • D) When valid goes from high to lowD) valid가 high에서 low로 갈 때
✅ Transfer = valid & ready. Both signals must be high simultaneously on the same positive clock edge for data to transfer.✅ 전송 = valid & ready. 데이터가 전송되려면 같은 양의 클럭 엣지에서 두 신호가 동시에 high여야 합니다.

Q2. Which of the following is FORBIDDEN in the AXI-style ready/valid protocol?AXI 스타일 ready/valid 프로토콜에서 금지된 것은?

  • A) Ready depends on validA) Ready가 valid에 의존
  • B) Data changes after a transfer completesB) 전송 완료 후 데이터 변경
  • C) Valid depends on readyC) Valid가 ready에 의존
  • D) Ready is deasserted while valid is highD) valid가 high인 동안 ready 해제
✅ The source must assert valid independently of ready. If valid waits for ready, and ready waits for valid, you get a deadlock. Ready CAN depend on valid, but not the other way around.✅ 소스는 ready와 독립적으로 valid를 주장해야 합니다. valid가 ready를 기다리고 ready가 valid를 기다리면 데드락이 발생합니다. Ready는 valid에 의존할 수 있지만 반대는 안 됩니다.

Q3. What must happen to valid once it's asserted?valid가 주장된 후 어떻게 되어야 합니까?

  • A) It must stay high until both valid and ready are high (transfer completes)A) valid와 ready가 모두 high가 될 때까지(전송 완료) high를 유지해야 함
  • B) It can drop at any timeB) 언제든지 떨어질 수 있음
  • C) It must stay high for at least 2 clock cyclesC) 최소 2 클럭 사이클 동안 high를 유지해야 함
  • D) It must pulse high for exactly one cycleD) 정확히 한 사이클 동안 high 펄스여야 함
✅ Once valid is asserted, it must remain high until the handshake completes (valid & ready both high). Dropping valid early would violate the protocol and could cause data loss.✅ valid가 주장되면 핸드셰이크가 완료될 때까지(valid & ready 모두 high) high를 유지해야 합니다. valid를 일찍 떨어뜨리면 프로토콜 위반이며 데이터 손실이 발생할 수 있습니다.

Q4. In a simple pipe stage, in_ready = out_ready | !out_valid. What does !out_valid mean?간단한 파이프 스테이지에서 in_ready = out_ready | !out_valid. !out_valid는 무엇을 의미합니까?

  • A) The downstream is readyA) 다운스트림이 준비됨
  • B) The stage has no data stored, so it can accept new dataB) 스테이지에 저장된 데이터가 없으므로 새 데이터를 받을 수 있음
  • C) The upstream has no dataC) 업스트림에 데이터가 없음
  • D) A reset conditionD) 리셋 조건
✅ When out_valid is low, the pipeline register is empty — nothing is being presented downstream. Therefore the stage can freely accept new data from upstream.✅ out_valid가 low이면 파이프라인 레지스터가 비어있어 다운스트림에 아무것도 표시되지 않습니다. 따라서 스테이지는 업스트림에서 자유롭게 새 데이터를 받을 수 있습니다.

Q5. What problem does a skid buffer solve?스키드 버퍼는 어떤 문제를 해결합니까?

  • A) Increases throughput beyond 1 transfer/cycleA) 1 전송/사이클 이상으로 처리량 증가
  • B) Eliminates the need for valid signalsB) valid 신호의 필요성 제거
  • C) Breaks the combinational ready path across pipeline stagesC) 파이프라인 스테이지 간 조합적 ready 경로를 끊음
  • D) Converts ready/valid to credit-based flow controlD) ready/valid를 크레딧 기반 흐름 제어로 변환
✅ In a simple pipe stage, in_ready depends combinationally on out_ready. Across many stages, this chain becomes too long for timing. The skid buffer uses a small extra register to make in_ready depend only on local state (is the skid register empty?), breaking the combinational path.✅ 간단한 파이프 스테이지에서 in_ready는 조합적으로 out_ready에 의존합니다. 많은 스테이지에 걸쳐 이 체인은 타이밍에 너무 길어집니다. 스키드 버퍼는 작은 추가 레지스터를 사용하여 in_ready가 로컬 상태(스키드 레지스터가 비어있는가?)에만 의존하게 하여 조합 경로를 끊습니다.

Q6. In a skid buffer, when does data go into the skid register?스키드 버퍼에서 데이터가 스키드 레지스터에 들어가는 시점은?

  • A) Every clock cycleA) 매 클럭 사이클
  • B) When the main register is emptyB) 메인 레지스터가 비어있을 때
  • C) When valid risesC) valid가 올라갈 때
  • D) When downstream is stalled but new data arrives from upstreamD) 다운스트림이 멈추었지만 업스트림에서 새 데이터가 도착할 때
✅ The skid register catches "in-flight" data. When the downstream can't accept data (stalled) but the upstream has already sent data (because ready was registered and took a cycle to deassert), the skid register saves that data from being lost.✅ 스키드 레지스터는 "비행 중" 데이터를 잡습니다. 다운스트림이 데이터를 수락할 수 없지만(멈춤) 업스트림이 이미 데이터를 보냈을 때(ready가 레지스터되어 해제에 한 사이클 걸림), 스키드 레지스터가 해당 데이터를 손실로부터 저장합니다.

Q7. How many channels in AXI use the ready/valid handshake?AXI에서 몇 개의 채널이 ready/valid 핸드셰이크를 사용합니까?

  • A) 2 (read and write)A) 2개 (읽기와 쓰기)
  • B) 5 (AW, W, B, AR, R)B) 5개 (AW, W, B, AR, R)
  • C) 3 (address, data, response)C) 3개 (주소, 데이터, 응답)
  • D) 1 (the main data channel)D) 1개 (메인 데이터 채널)
✅ AXI has 5 independent channels: Write Address (AW), Write Data (W), Write Response (B), Read Address (AR), and Read Data (R). Each one uses its own VALID/READY pair.✅ AXI에는 5개의 독립 채널이 있습니다: 쓰기 주소(AW), 쓰기 데이터(W), 쓰기 응답(B), 읽기 주소(AR), 읽기 데이터(R). 각각 자체 VALID/READY 쌍을 사용합니다.

Q8. What is the throughput of a properly implemented skid buffer?올바르게 구현된 스키드 버퍼의 처리량은?

  • A) 1 transfer per clock cycle (same as simple pipe)A) 클럭 사이클당 1 전송 (간단한 파이프와 동일)
  • B) 2 transfers per clock cycleB) 클럭 사이클당 2 전송
  • C) 0.5 transfers per clock cycleC) 클럭 사이클당 0.5 전송
  • D) Variable, depends on dataD) 가변적, 데이터에 따라 다름
✅ A well-designed skid buffer maintains full throughput of 1 transfer per cycle (sustained), while also registering the ready signal. The extra register absorbs the one-cycle gap when ready deasserts.✅ 잘 설계된 스키드 버퍼는 사이클당 1 전송의 전체 처리량(지속)을 유지하면서 ready 신호도 레지스터합니다. 추가 레지스터가 ready가 해제될 때 1 사이클 갭을 흡수합니다.

Q9. Why can ready depend on valid but not vice versa?왜 ready는 valid에 의존할 수 있지만 반대는 안 됩니까?

  • A) Because ready is always registeredA) ready는 항상 레지스터되기 때문
  • B) Because the source is always fasterB) 소스가 항상 더 빠르기 때문
  • C) Because valid is a higher priority signalC) valid가 더 높은 우선순위 신호이기 때문
  • D) Because if both depended on each other, neither would ever assert (deadlock)D) 둘 다 서로에게 의존하면 어느 것도 주장되지 않기 때문 (데드락)
✅ If valid waited for ready, and ready waited for valid, neither would ever go high — a classic deadlock. By making valid independent, someone always "goes first" and breaks the dependency cycle. Ready is allowed to depend on valid because that creates a one-way dependency, not a loop.✅ valid가 ready를 기다리고 ready가 valid를 기다리면 어느 것도 high가 되지 않습니다 — 전형적인 데드락. valid를 독립적으로 만들면 항상 누군가가 "먼저 가서" 의존성 사이클을 끊습니다. ready는 valid에 의존할 수 있는데, 이것이 루프가 아닌 단방향 의존성을 만들기 때문입니다.

Q10. You have a 10-stage pipeline using simple pipe stages (combinational ready). What's the main timing concern?간단한 파이프 스테이지(조합적 ready)를 사용하는 10단 파이프라인이 있습니다. 주요 타이밍 우려는?

  • A) Data path is too longA) 데이터 경로가 너무 김
  • B) Too many clock domainsB) 너무 많은 클럭 도메인
  • C) The ready signal has a 10-stage combinational chain, violating timingC) ready 신호가 10단 조합 체인을 가져 타이밍을 위반
  • D) Throughput drops to 0.1 transfers/cycleD) 처리량이 0.1 전송/사이클로 감소
✅ Each simple pipe stage has in_ready = out_ready | !out_valid, creating a combinational dependency on the next stage's ready. Across 10 stages, ready propagates through 10 levels of combinational logic — often too slow for high-frequency designs. This is exactly why skid buffers exist!✅ 각 간단한 파이프 스테이지는 in_ready = out_ready | !out_valid로 다음 스테이지의 ready에 대한 조합적 의존성을 만듭니다. 10단에 걸쳐 ready가 10레벨의 조합 로직을 통과합니다 — 고주파 설계에는 종종 너무 느립니다. 이것이 바로 스키드 버퍼가 존재하는 이유입니다!

Q11. In a ready/valid interface, who drives valid and who drives ready?ready/valid 인터페이스에서 누가 valid를, 누가 ready를 구동합니까?

  • A) The sink drives bothA) 싱크가 둘 다 구동
  • B) Source drives valid, sink drives readyB) 소스가 valid를, 싱크가 ready를 구동
  • C) Source drives ready, sink drives validC) 소스가 ready를, 싱크가 valid를 구동
  • D) An arbiter drives bothD) 중재기가 둘 다 구동
✅ The source (producer) asserts valid when it has data. The sink (consumer) asserts ready when it can accept data. Each side controls its own signal — this separation of concerns is what makes the protocol clean and deadlock-free.✅ 소스(생산자)는 데이터가 있을 때 valid를 주장합니다. 싱크(소비자)는 데이터를 받을 수 있을 때 ready를 주장합니다. 각 측이 자체 신호를 제어합니다 — 이 관심사의 분리가 프로토콜을 깔끔하고 데드락 없게 만듭니다.

Q12. What happens to data while valid is high but ready is low?valid가 high이지만 ready가 low일 때 데이터는 어떻게 됩니까?

  • A) Data must remain stable — no changes allowedA) 데이터가 안정적으로 유지되어야 함 — 변경 불가
  • B) Data can change freely since no transfer occursB) 전송이 발생하지 않으므로 데이터를 자유롭게 변경 가능
  • C) Data is ignored by the sinkC) 데이터가 싱크에 의해 무시됨
  • D) Data must be set to zeroD) 데이터를 0으로 설정해야 함
✅ While valid is asserted, data must remain stable. The sink might sample data on the very cycle it asserts ready. Changing data while valid is high violates the protocol and could cause the sink to capture corrupted data.✅ valid가 주장되는 동안 데이터는 안정적으로 유지되어야 합니다. 싱크가 ready를 주장하는 바로 그 사이클에 데이터를 샘플링할 수 있습니다. valid가 high인 동안 데이터를 변경하면 프로토콜 위반이며 싱크가 손상된 데이터를 캡처할 수 있습니다.

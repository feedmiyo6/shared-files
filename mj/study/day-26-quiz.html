Q1. When does a transfer occur in a ready/valid handshake?

Q1. Ready/valid 핸드셰이크에서 전송은 언제 발생합니까?

  • A) When valid rises (posedge valid)
  • B) When both valid AND ready are high on the rising clock edge
  • C) When ready rises (posedge ready)
  • D) When data changes value

✅ Transfer = valid && ready sampled at the rising clock edge. Neither signal edge alone triggers a transfer.

✅ 전송 = 상승 클록 에지에서 샘플링된 valid && ready. 어느 신호의 에지만으로는 전송이 트리거되지 않습니다.

Q2. What is the golden rule that prevents deadlocks?

Q2. 데드락을 방지하는 황금 규칙은 무엇입니까?

  • A) Ready must not depend on valid
  • B) Valid must not depend on ready
  • C) Both valid and ready must be registered
  • D) Data must change every cycle

✅ Valid must not depend on ready. The source must assert valid whenever it has data, regardless of the sink's state. Ready MAY depend on valid in some protocols.

✅ Valid는 ready에 의존하면 안 됩니다. 소스는 싱크 상태와 관계없이 데이터가 있을 때마다 valid를 어서트해야 합니다. 일부 프로토콜에서 ready는 valid에 의존할 수 있습니다.

Q3. During a stall (valid=1, ready=0), what must the source do?

Q3. 스톨 중 (valid=1, ready=0), 소스는 무엇을 해야 합니까?

  • A) Deassert valid and retry later
  • B) Change data to signal urgency
  • C) Hold both valid and data stable
  • D) Toggle valid to get the sink's attention

✅ Once valid is asserted, the source must keep it asserted AND keep data stable until the transfer completes (ready goes high).

✅ Valid가 어서트되면, 소스는 전송이 완료될 때까지 (ready가 하이가 될 때까지) valid를 유지하고 data를 안정적으로 유지해야 합니다.

Q4. If 8 transfers happen over 20 clock cycles, what is the throughput?

Q4. 20 클록 사이클 동안 8개의 전송이 발생하면 처리량은 얼마입니까?

  • A) 80%
  • B) 20%
  • C) 40%
  • D) 8%

✅ Throughput = transfers / cycles = 8/20 = 40%. Maximum throughput (100%) means one transfer per cycle.

✅ 처리량 = 전송 / 사이클 = 8/20 = 40%. 최대 처리량 (100%)은 사이클당 하나의 전송을 의미합니다.

Q5. In back-to-back transfers, what state are valid and ready in?

Q5. 연속 전송에서 valid와 ready는 어떤 상태입니까?

  • A) They alternate — one cycle valid, one cycle ready
  • B) Both stay high continuously
  • C) Valid pulses each cycle, ready stays high
  • D) Ready pulses each cycle, valid stays high

✅ For maximum throughput, both valid and ready stay asserted continuously. Data changes every clock edge while both are high.

✅ 최대 처리량을 위해 valid와 ready 모두 지속적으로 어서트됩니다. 둘 다 하이인 동안 데이터는 매 클록 에지마다 변경됩니다.

Q6. What is the purpose of a skid buffer?

Q6. 스키드 버퍼의 목적은 무엇입니까?

  • A) To increase data width
  • B) To convert between clock domains
  • C) To absorb one cycle of backpressure and prevent stall propagation
  • D) To synchronize metastable signals

✅ A skid buffer adds one slot of storage, absorbing a single cycle of stall so the source doesn't immediately stall when the sink pauses.

✅ 스키드 버퍼는 하나의 저장 슬롯을 추가하여 싱크가 일시 정지할 때 소스가 즉시 스톨되지 않도록 단일 사이클의 스톨을 흡수합니다.

Q7. In the source module, when does new data get loaded?

Q7. 소스 모듈에서 새 데이터는 언제 로드됩니까?

  • A) Every clock cycle
  • B) When a transfer completes OR when idle (not valid)
  • C) Only when ready is asserted
  • D) Only on reset

✅ New data loads on transfer || !o_valid. After a successful transfer, load next data immediately (back-to-back capable). When idle, also free to load.

✅ 새 데이터는 transfer || !o_valid에서 로드됩니다. 성공적 전송 후 즉시 다음 데이터를 로드 (연속 전송 가능). 유휴 시에도 자유롭게 로드.

Q8. In the skid buffer, when does data get saved to the skid register?

Q8. 스키드 버퍼에서 데이터는 언제 스키드 레지스터에 저장됩니까?

  • A) On every transfer
  • B) When the skid register is full
  • C) When input is valid, output is valid, but downstream isn't ready
  • D) When both valid and ready are low

✅ The skid register captures data when: i_valid && o_valid && !i_ready. The output is stalled but new input is arriving — save it to prevent data loss.

✅ 스키드 레지스터는 i_valid && o_valid && !i_ready일 때 데이터를 캡처합니다. 출력은 스톨되었지만 새 입력이 도착 — 데이터 손실을 방지하기 위해 저장합니다.

Q9. How much latency does a skid buffer add?

Q9. 스키드 버퍼는 얼마나 많은 지연을 추가합니까?

  • A) 1 clock cycle
  • B) 2 clock cycles
  • C) 0 cycles (purely combinational)
  • D) Variable, depends on data width

✅ A skid buffer adds exactly 1 cycle of latency but preserves full throughput. It's the minimum-cost way to break timing paths in a pipeline.

✅ 스키드 버퍼는 정확히 1 사이클의 지연을 추가하지만 전체 처리량을 유지합니다. 파이프라인에서 타이밍 경로를 끊는 최소 비용 방법입니다.

Q10. Which protocols use the ready/valid handshake pattern?

Q10. 어떤 프로토콜이 ready/valid 핸드셰이크 패턴을 사용합니까?

  • A) Only AXI
  • B) Only AMBA protocols
  • C) AXI, AHB, TileLink, and most custom on-chip interfaces
  • D) Only off-chip protocols like PCIe

✅ The ready/valid handshake is ubiquitous in on-chip design. AXI (TVALID/TREADY), TileLink, and virtually all custom interfaces use this pattern.

✅ Ready/valid 핸드셰이크는 온칩 설계에서 유비쿼터스입니다. AXI (TVALID/TREADY), TileLink, 그리고 거의 모든 커스텀 인터페이스가 이 패턴을 사용합니다.

Q11. Can ready depend on valid?

Q11. ready는 valid에 의존할 수 있습니까?

  • A) Never — both must be independent
  • B) Yes — ready may depend on valid (but not the reverse)
  • C) Yes — valid may depend on ready (but not the reverse)
  • D) Both may depend on each other

✅ Ready may depend on valid (common in some protocols). But valid MUST NOT depend on ready — that's the rule that prevents deadlocks.

✅ Ready는 valid에 의존할 수 있습니다 (일부 프로토콜에서 일반적). 하지만 valid는 ready에 의존하면 안 됩니다 — 이것이 데드락을 방지하는 규칙입니다.

Q12. In the sink module, what determines o_ready?

Q12. 싱크 모듈에서 o_ready는 무엇에 의해 결정됩니까?

  • A) It's always high
  • B) Whether the internal buffer is empty (not full)
  • C) Whether valid is asserted
  • D) A fixed timer

✅ o_ready = !buffer_full. The sink is ready to accept data when its internal buffer has room. This is a common pattern — ready reflects available capacity.

✅ o_ready = !buffer_full. 싱크는 내부 버퍼에 공간이 있을 때 데이터를 수용할 준비가 됩니다. 이것은 일반적인 패턴입니다 — ready는 사용 가능한 용량을 반영합니다.

What Is the Critical Path? 크리티컬 패스란?

The critical path is the longest combinational delay path between any two sequential elements (flip-flops) in your design. It determines the maximum clock frequency — your entire chip can only run as fast as its slowest path.

크리티컬 패스(Critical Path)는 설계에서 두 순차 요소(플립플롭) 사이의 가장 긴 조합 논리 지연 경로입니다. 최대 클럭 주파수를 결정하며, 칩 전체는 가장 느린 경로만큼만 빠르게 동작할 수 있습니다.

🔑 Key Relationship

T_clk ≥ T_cq + T_comb + T_setup

T_clk ≥ T_cq + T_comb + T_setup

  • T_cq — Clock-to-Q delay of the source flip-flop
  • T_cq — 소스 플립플롭의 Clock-to-Q 지연
  • T_comb — Total combinational logic delay (THIS is what you optimize!)
  • T_comb — 전체 조합 논리 지연 (이것을 최적화합니다!)
  • T_setup — Setup time requirement of the destination flip-flop
  • T_setup — 목적지 플립플롭의 셋업 타임 요구사항

Visualizing the Critical Path 크리티컬 패스 시각화

Consider a circuit with multiple paths between two flip-flops:

두 플립플롭 사이에 여러 경로가 있는 회로를 생각해봅시다:

         Path A: 2ns          Path B: 1ns
        ┌─────────┐          ┌─────────┐
   FF1 ─┤  Adder  ├── MUX ──┤ Buffer  ├── FF2
        └─────────┘  (0.5ns) └─────────┘
              │
              │      Path C: 3ns
              └──┤ Multiplier ├── MUX ── FF3
                 └────────────┘  (0.5ns)

  Path to FF2: T_cq + 2ns + 0.5ns + 1ns + T_setup = T_cq + 3.5ns + T_setup
  Path to FF3: T_cq + 2ns + 3ns + 0.5ns + T_setup = T_cq + 5.5ns + T_setup  ← CRITICAL!

The path through the multiplier to FF3 is the critical path — it has the longest combinational delay. Even if every other path is fast, the clock period must accommodate this worst case.

곱셈기를 거쳐 FF3에 이르는 경로가 크리티컬 패스입니다 — 가장 긴 조합 논리 지연을 가집니다. 다른 모든 경로가 빠르더라도 클럭 주기는 이 최악의 경우를 수용해야 합니다.

Finding the Critical Path 크리티컬 패스 찾기

In real design flows, synthesis tools (Synopsys Design Compiler, Cadence Genus) automatically report the critical path. But understanding how to spot it in RTL is essential for interviews and good design intuition.

실제 설계 플로우에서는 합성 도구(Synopsys Design Compiler, Cadence Genus)가 자동으로 크리티컬 패스를 보고합니다. 하지만 RTL에서 이를 찾는 방법을 이해하는 것은 면접과 좋은 설계 직관에 필수적입니다.

Example: Spotting the Critical Path in RTL 예제: RTL에서 크리티컬 패스 찾기

Look at this combinational block — can you spot what makes the critical path long?

이 조합 논리 블록을 보세요 — 크리티컬 패스를 길게 만드는 것이 무엇인지 찾을 수 있나요?

always_comb begin
    // Step 1: 32-bit multiply (DEEP logic)
    product = a * b;

    // Step 2: Add offset (adds carry chain)
    sum = product + offset;

    // Step 3: Compare and select (more logic depth)
    if (sum > threshold)
        result = sum - threshold;
    else
        result = sum;
end

The critical path here: a/b → multiply → add → compare → subtract → result. That's multiply + add + compare + subtract all in one clock cycle! This will be very slow.

여기서 크리티컬 패스: a/b → 곱셈 → 덧셈 → 비교 → 뺄셈 → result. 곱셈 + 덧셈 + 비교 + 뺄셈이 모두 하나의 클럭 사이클에! 매우 느릴 것입니다.

Optimization Technique #1: Pipelining 최적화 기법 #1: 파이프라이닝

The most powerful optimization: break the long path with flip-flops. Trade latency (more cycles) for throughput (faster clock).

가장 강력한 최적화: 긴 경로를 플립플롭으로 분할합니다. 레이턴시(더 많은 사이클)를 스루풋(더 빠른 클럭)과 교환합니다.

// BEFORE: Everything in one cycle (slow clock)
always_ff @(posedge clk) begin
    result <= (a * b) + offset;  // multiply + add in one cycle!
end

// AFTER: Pipelined into two stages (faster clock)
// Stage 1: Multiply
always_ff @(posedge clk) begin
    product_reg <= a * b;       // Only multiply this cycle
    offset_reg  <= offset;        // Save offset for next stage
end

// Stage 2: Add
always_ff @(posedge clk) begin
    result <= product_reg + offset_reg;  // Only add this cycle
end

💡 Pipeline Tradeoff

Pipelining doesn't reduce total computation time — it still takes the same total nanoseconds. But it lets you increase clock frequency because each stage has less combinational logic. Result arrives one cycle later, but you can start a new computation every cycle.

파이프라이닝은 총 계산 시간을 줄이지 않습니다 — 여전히 같은 나노초가 걸립니다. 하지만 각 스테이지의 조합 논리가 줄어들어 클럭 주파수를 높일 수 있습니다. 결과는 한 사이클 늦게 나오지만, 매 사이클마다 새로운 계산을 시작할 수 있습니다.

Optimization Technique #2: Logic Restructuring 최적화 기법 #2: 로직 재구성

Sometimes you can reduce the critical path without adding pipeline stages — by rearranging the logic.

때로는 파이프라인 스테이지를 추가하지 않고도 로직을 재배치하여 크리티컬 패스를 줄일 수 있습니다.

Example: Tree vs Chain Addition 예제: 트리 vs 체인 덧셈 

// SLOW: Chain addition (3 adder delays in series)
sum = a + b + c + d;
//      └─┬─┘
//        └───┬─┘
//            └───┬─┘   → 3 levels deep

// FAST: Tree addition (2 adder delays — parallel!)
sum_ab = a + b;    // These two happen
sum_cd = c + d;    // in PARALLEL!
sum    = sum_ab + sum_cd;  // → 2 levels deep

📊 Depth Comparison

For adding N values:

N개의 값을 더할 때:

MethodLogic Depth4 Values8 Values
Chain (serial)N - 13 levels7 levels
Tree (parallel)log₂(N)2 levels3 levels

Optimization Technique #3: Precomputation 최적화 기법 #3: 사전 계산

Move computation before the MUX instead of after, so the MUX select signal is on the critical path for less time.

MUX 뒤가 아닌 앞에서 계산을 수행하여, MUX 선택 신호가 크리티컬 패스에 있는 시간을 줄입니다.

// SLOW: Compute after MUX (MUX + adder on critical path)
always_comb begin
    case (sel)
        2'b00: val = a;
        2'b01: val = b;
        2'b10: val = c;
        2'b11: val = d;
    endcase
    result = val + offset;  // Adder AFTER mux
end

// FAST: Precompute all options, then MUX (only MUX on critical path)
always_comb begin
    sum_a = a + offset;  // All 4 additions
    sum_b = b + offset;  // happen in PARALLEL
    sum_c = c + offset;
    sum_d = d + offset;

    case (sel)
        2'b00: result = sum_a;
        2'b01: result = sum_b;
        2'b10: result = sum_c;
        2'b11: result = sum_d;
    endcase
end

⚠️ Precomputation Tradeoff

Precomputation uses more area (4 adders instead of 1) to get less delay. This is a classic area vs. speed tradeoff. Use it when timing is critical and area budget allows.

사전 계산은 더 적은 지연을 위해 더 많은 면적을 사용합니다 (1개 대신 4개의 가산기). 이것은 전형적인 면적 vs 속도 트레이드오프입니다. 타이밍이 중요하고 면적 예산이 허용될 때 사용하세요.

Optimization Technique #4: Flatten Priority Logic 최적화 기법 #4: 우선순위 로직 평탄화

Deeply nested if-else creates a priority chain. If priority isn't needed, use case or unique case instead.

깊이 중첩된 if-else는 우선순위 체인을 만듭니다. 우선순위가 필요하지 않다면 case 또는 unique case를 사용하세요.

// SLOW: Priority chain (N conditions = N mux levels)
if (cond_a)      out = val_a;
else if (cond_b) out = val_b;
else if (cond_c) out = val_c;
else if (cond_d) out = val_d;
else             out = val_default;

// FAST: Parallel decode (if conditions are mutually exclusive)
unique case (1'b1)
    cond_a: out = val_a;
    cond_b: out = val_b;
    cond_c: out = val_c;
    cond_d: out = val_d;
    default: out = val_default;
endcase

💡 unique case Tells the Synthesizer

unique case tells the synthesis tool that conditions are mutually exclusive, allowing it to generate a parallel MUX tree instead of a priority chain. This can significantly reduce logic depth.

unique case는 합성 도구에게 조건이 상호 배타적임을 알려, 우선순위 체인 대신 병렬 MUX 트리를 생성할 수 있게 합니다. 이는 로직 깊이를 크게 줄일 수 있습니다.

🎯 Interview Tip

"How would you reduce the critical path?" is one of the most common digital design interview questions. Always think: (1) Can I pipeline it? (2) Can I restructure the logic tree? (3) Can I precompute? (4) Do I really need priority encoding?

"크리티컬 패스를 어떻게 줄이겠습니까?"는 가장 흔한 디지털 설계 면접 질문 중 하나입니다. 항상 생각하세요: (1) 파이프라인 가능한가? (2) 로직 트리를 재구성 가능한가? (3) 사전 계산 가능한가? (4) 우선순위 인코딩이 정말 필요한가?

Real-World: Reading a Timing Report 실무: 타이밍 리포트 읽기

In real ASIC/FPGA flows, the synthesis tool generates timing reports. Here's what a simplified critical path report looks like:

실제 ASIC/FPGA 플로우에서 합성 도구는 타이밍 리포트를 생성합니다. 간소화된 크리티컬 패스 리포트의 모습:

// Timing Report (simplified)
Startpoint: reg_a (rising edge-triggered flip-flop)
Endpoint:   reg_result (rising edge-triggered flip-flop)
Path Group:  clk
Path Type:   max (setup check)

Point                          Delay      Total
----------------------------------------------
clock clk (rise edge)           0.00       0.00
reg_a/CK (DFF)                  0.00       0.00
reg_a/Q  (clock-to-Q)           0.15       0.15   ← T_cq
mult_u1/Z (multiplier)          1.80       1.95   ← Biggest delay!
add_u2/S  (adder)               0.40       2.35
mux_u3/Y  (mux)                 0.20       2.55
reg_result/D (setup)            0.10       2.65   ← T_setup

Required time:                              2.50   ← Clock period
Arrival time:                               2.65
Slack:                                     -0.15   ← NEGATIVE = VIOLATION!

⚠️ Negative Slack = Timing Violation

Slack = Required Time - Arrival Time. Negative slack means the data arrives too late — the design won't work at this clock frequency. You must optimize the critical path or slow down the clock.

Slack = 요구 시간 - 도착 시간. 음의 슬랙은 데이터가 너무 늦게 도착한다는 의미입니다 — 이 클럭 주파수에서 설계가 작동하지 않습니다. 크리티컬 패스를 최적화하거나 클럭을 느리게 해야 합니다.

  6. 곱셈기, 넓은 MUX, 연쇄 비교가 흔한 원인

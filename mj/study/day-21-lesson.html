1. What Are Latency and Throughput?

🎯 Key Definitions

Latency = the time it takes for ONE piece of data to travel from input to output. Think of it as the delay for a single transaction.

레이턴시(Latency) = 하나의 데이터가 입력에서 출력까지 이동하는 데 걸리는 시간. 단일 트랜잭션의 지연 시간이라고 생각하세요.

Throughput = the number of results produced per unit time. Think of it as the rate of output.

처리량(Throughput) = 단위 시간당 생산되는 결과의 수. 출력 속도라고 생각하세요.

The Restaurant Analogy

Imagine a restaurant kitchen:

레스토랑 주방을 상상해 보세요:

  • Latency = How long from ordering to getting YOUR meal (e.g., 30 minutes)
  • 레이턴시 = 주문부터 본인의 음식을 받기까지의 시간 (예: 30분)
  • Throughput = How many meals the kitchen serves per hour (e.g., 60 meals/hour)
  • 처리량 = 주방이 시간당 제공하는 식사 수 (예: 시간당 60끼)

A kitchen can serve many meals per hour even if each meal takes 30 minutes — because multiple meals are being prepared simultaneously (pipelining!).

주방은 각 식사가 30분이 걸리더라도 시간당 많은 식사를 제공할 수 있습니다 — 여러 식사가 동시에 준비되기 때문입니다 (파이프라이닝!).

2. Measuring in Hardware

📏 Formal Definitions

Metric Formula 공식 Unit 단위
Latency Number of clock cycles × Clock period 클럭 사이클 수 × 클럭 주기 ns, μs
Throughput Results per clock cycle × Clock frequency 클럭 사이클당 결과 × 클럭 주파수 ops/sec, GB/s

Example: A Simple Multiplier

Consider an 8×8 multiplier running at 100 MHz (10 ns clock period):

100 MHz(10ns 클럭 주기)로 동작하는 8×8 곱셈기를 생각해 보세요:

// Non-pipelined: result in 1 cycle
// Latency = 1 cycle = 10 ns
// Throughput = 1 result/cycle = 100M results/sec

module multiplier_simple (
    input  logic [7:0] a, b,
    input  logic        clk,
    output logic [15:0] result
);
    always_ff @(posedge clk)
        result <= a * b;
endmodule

But what if the combinational path is too long and limits clock speed to 50 MHz?

하지만 조합 경로가 너무 길어서 클럭 속도가 50 MHz로 제한된다면?

3. The Pipelining Tradeoff

Pipelining increases latency (more cycles) but can dramatically improve throughput (faster clock).

파이프라이닝은 레이턴시를 증가시키지만(더 많은 사이클), 처리량을 극적으로 향상시킬 수 있습니다(더 빠른 클럭).

Non-Pipelined (50 MHz) ──────────────────────────────────────── │ A*B compute (20ns) │ C*D compute (20ns) │ ──────────────────────────────────────── Latency: 1 cycle = 20ns Throughput: 50M ops/sec 2-Stage Pipeline (100 MHz) ────────────────────────────────────────────── │ A*B stage1 │ A*B stage2 │ │ │ │ C*D stage1 │ C*D stage2 │ ────────────────────────────────────────────── Latency: 2 cycles = 20ns Throughput: 100M ops/sec ← 2× better!

🔑 Key Insight

Pipelining does NOT reduce latency for a single operation. It improves throughput by allowing overlapping execution of multiple operations.

파이프라이닝은 단일 연산의 레이턴시를 줄이지 않습니다. 여러 연산의 겹침 실행을 허용하여 처리량을 향상시킵니다.

2-Stage Pipelined Multiplier

module multiplier_pipelined (
    input  logic        clk, rst_n,
    input  logic [7:0]  a, b,
    output logic [15:0] result
);
    // Stage 1: Partial products
    logic [15:0] partial_low, partial_high;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            partial_low  <= '0;
            partial_high <= '0;
        end else begin
            partial_low  <= a[3:0] * b;  // Lower nibble × b
            partial_high <= a[7:4] * b;  // Upper nibble × b
        end
    end

    // Stage 2: Combine partial products
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            result <= '0;
        else
            result <= partial_low + (partial_high << 4);
    end
endmodule

4. Quantifying the Tradeoff

Design 설계 Clock Freq 클럭 주파수 Latency (cycles) 레이턴시(사이클) Latency (time) 레이턴시(시간) Throughput 처리량
No pipeline 파이프라인 없음 50 MHz 1 20 ns 50 Mops/s
2-stage 2단계 100 MHz 2 20 ns 100 Mops/s
4-stage 4단계 200 MHz 4 20 ns 200 Mops/s

💡 Notice the Pattern

In an ideal pipeline, total latency stays the same (pipeline register overhead aside), but throughput scales with the number of stages! In reality, register overhead adds a small delay per stage.

이상적인 파이프라인에서 총 레이턴시는 동일하게 유지되지만(파이프라인 레지스터 오버헤드 제외), 처리량은 단계 수에 비례하여 확장됩니다! 실제로는 레지스터 오버헤드가 단계당 약간의 지연을 추가합니다.

6. Bandwidth × Latency = "In-Flight" Data

📦 The Bandwidth-Delay Product

The amount of data "in flight" at any time equals:

어느 시점에서든 "전송 중인" 데이터의 양은 다음과 같습니다:

In-Flight Data = Throughput × Latency

This tells you how much buffering you need. A high-throughput, high-latency system needs large buffers (like a deep pipeline or FIFO).

이것은 얼마나 많은 버퍼링이 필요한지 알려줍니다. 높은 처리량과 높은 레이턴시의 시스템은 큰 버퍼가 필요합니다(깊은 파이프라인이나 FIFO처럼).

Example Calculation

// System: 200 MHz, 10-stage pipeline
// Throughput = 200M results/sec (1 per cycle)
// Latency = 10 cycles = 50 ns
//
// In-flight data = 10 operations at any given time
// → Need storage for 10 intermediate results
// → Each pipeline register holds one partial result

7. Little's Law in Hardware

📐 Little's Law

L = λ × W

Where: L = average items in system, λ = throughput (arrival rate), W = average latency

여기서: L = 시스템 내 평균 항목 수, λ = 처리량(도착률), W = 평균 레이턴시

This applies to FIFOs, pipelines, networks, caches — any queuing system!

이것은 FIFO, 파이프라인, 네트워크, 캐시 — 모든 큐잉 시스템에 적용됩니다!

💡 Interview Tip

If an interviewer asks "how deep should your FIFO be?" — Little's Law is your go-to tool. Throughput × latency = minimum FIFO depth.

면접관이 "FIFO의 깊이는 얼마나 되어야 하나요?"라고 물으면 — Little's Law가 핵심 도구입니다. 처리량 × 레이턴시 = 최소 FIFO 깊이.

8. Real-World Tradeoffs

⚠️ Diminishing Returns

More pipeline stages don't always help:

파이프라인 단계를 늘린다고 항상 좋은 것은 아닙니다:

  • Register overhead: Each stage adds setup/hold time + clock-to-q delay (~50-100ps per stage)
  • 레지스터 오버헤드: 각 단계가 셋업/홀드 타임 + clock-to-q 지연을 추가 (단계당 ~50-100ps)
  • Area cost: More registers = more silicon area and power
  • 면적 비용: 레지스터가 많을수록 = 더 많은 실리콘 면적과 전력
  • Hazard complexity: Deep pipelines create more forwarding/stalling challenges
  • 해저드 복잡성: 깊은 파이프라인은 더 많은 포워딩/스톨 문제를 야기

9. Summary

📝 Key Takeaways

  • Latency = time for one operation (input → output)
  • 레이턴시 = 하나의 연산 시간 (입력 → 출력)
  • Throughput = operations per unit time
  • 처리량 = 단위 시간당 연산 수
  • Pipelining trades latency (in cycles) for throughput (faster clock)
  • 파이프라이닝은 레이턴시(사이클)를 처리량(빠른 클럭)과 교환
  • In-flight data = throughput × latency (determines buffer sizing)
  • 전송 중 데이터 = 처리량 × 레이턴시 (버퍼 크기 결정)
  • Little's Law (L = λW) governs all queuing systems
  • Little's Law (L = λW)는 모든 큐잉 시스템을 지배
  • Choose based on application: latency-sensitive vs throughput-critical
  • 응용에 따라 선택: 레이턴시 민감 vs 처리량 중요

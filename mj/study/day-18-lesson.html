1. The Problem: Beyond Single-Bit CDC

Yesterday we learned the 2-flop synchronizer for single-bit signals. But what if we need to safely pass multi-bit data (like an 8-bit value or a command packet) across clock domains?

어제 단일 비트 신호를 위한 2-플립플롭 동기화기를 배웠습니다. 그런데 멀티비트 데이터(예: 8비트 값이나 명령 패킷)를 클록 도메인 간에 안전하게 전달하려면 어떻게 할까요?

⚠️ Multi-Bit CDC Danger

You cannot simply put a 2-flop synchronizer on each bit of a multi-bit bus! Different bits may arrive at different times, causing data corruption.

멀티비트 버스의 각 비트에 2-플립플롭 동기화기를 단순히 넣으면 안 됩니다! 다른 비트들이 다른 시간에 도착하여 데이터 손상을 일으킬 수 있습니다.

Example: Sending 0111 → 1000. If bits change at different rates, the receiver might see 0000, 1111, or any garbage value!

예시: 0111 → 1000 전송 시, 비트들이 다른 속도로 변하면 수신측이 0000, 1111 또는 쓰레기 값을 볼 수 있습니다!

Solutions for multi-bit CDC include:

멀티비트 CDC 해결책:

  1. Handshake protocols (today's topic) — low throughput, simple, reliable
  2. 핸드셰이크 프로토콜 (오늘의 주제) — 낮은 처리량, 단순, 신뢰성
  3. Gray code counters (Day 19) — for FIFO pointers
  4. 그레이 코드 카운터 (19일차) — FIFO 포인터용
  5. Async FIFOs (Day 20) — high throughput, more complex
  6. 비동기 FIFO (20일차) — 높은 처리량, 더 복잡

2. Req/Ack Handshake Protocol

The req/ack handshake is the simplest reliable way to pass multi-bit data across clock domains. Think of it like a conversation:

req/ack 핸드셰이크는 멀티비트 데이터를 클록 도메인 간에 전달하는 가장 간단하고 신뢰성 있는 방법입니다. 대화처럼 생각하세요:

🤝 The Handshake Conversation

  1. Sender places data on the bus, then asserts req (request)
  2. 송신측이 버스에 데이터를 놓고 req (요청) 신호를 어서트
  3. Receiver synchronizes req (2-flop), captures data, then asserts ack (acknowledge)
  4. 수신측이 req를 동기화(2-플립플롭)하고, 데이터를 캡처한 후, ack (확인) 신호를 어서트
  5. Sender synchronizes ack (2-flop), then de-asserts req
  6. 송신측이 ack를 동기화(2-플립플롭)하고, req를 디어서트
  7. Receiver sees req de-asserted, de-asserts ack
  8. 수신측이 req 디어서트를 감지하고, ack를 디어서트
  9. Now it's safe to send the next data!
  10. 이제 다음 데이터를 보낼 수 있습니다!

Timing Diagram

Sender Clock Domain │ Receiver Clock Domain │ data ════╦════════════════╦═╪══════════════════════════ ║ VALID DATA ║ │ req ────┘ ┌─────────────┘ │ │ │ req_sync ──────┼───────────────┼──┐ (2-flop delay) │ │ │ data_cap ──────┼───────────────┼──┤ Receiver captures data │ │ │ ack ───────┼───────────────┼──┘──────────┐ │ │ │ ack_sync ──────┘ (2-flop) │ │ │ │ │ req ───────┘ (de-assert) │ │ │ │ │ ack ───────┼───────────────┼─────────────┘ (de-assert) │ │ READY FOR NEXT TRANSFER

The key insight: data is held stable during the entire handshake. Only the single-bit req and ack signals cross domains (via 2-flop synchronizers). The multi-bit data is just sampled when it's guaranteed to be stable.

핵심 통찰: 전체 핸드셰이크 동안 데이터가 안정적으로 유지됩니다. 단일 비트 req와 ack 신호만 도메인을 넘어갑니다(2-플립플롭 동기화기를 통해). 멀티비트 데이터는 안정이 보장될 때만 샘플링됩니다.

RTL Implementation

module cdc_handshake #(
    parameter DATA_W = 8
)(
    // Sender side (clk_a domain)
    input  logic              clk_a,
    input  logic              rst_a_n,
    input  logic [DATA_W-1:0] data_in,
    input  logic              valid_in,
    output logic              ready_out,

    // Receiver side (clk_b domain)
    input  logic              clk_b,
    input  logic              rst_b_n,
    output logic [DATA_W-1:0] data_out,
    output logic              valid_out
);

    // --- Sender side signals ---
    logic              req_a;
    logic [DATA_W-1:0] data_reg;
    logic              ack_sync_1, ack_sync_2;  // 2-flop sync for ack

    // --- Receiver side signals ---
    logic              req_sync_1, req_sync_2;  // 2-flop sync for req
    logic              req_sync_prev;
    logic              ack_b;

    // ==========================================
    // Sender Side (clk_a domain)
    // ==========================================

    // Synchronize ack from receiver into sender domain
    always_ff @(posedge clk_a or negedge rst_a_n) begin
        if (!rst_a_n) begin
            ack_sync_1 <= 1'b0;
            ack_sync_2 <= 1'b0;
        end else begin
            ack_sync_1 <= ack_b;
            ack_sync_2 <= ack_sync_1;
        end
    end

    // Sender state machine
    typedef enum logic [1:0] {
        S_IDLE,        // Ready for new data
        S_WAIT_ACK,   // Waiting for ack assertion
        S_WAIT_DEACK  // Waiting for ack de-assertion
    } sender_state_t;

    sender_state_t s_state;

    always_ff @(posedge clk_a or negedge rst_a_n) begin
        if (!rst_a_n) begin
            s_state   <= S_IDLE;
            req_a     <= 1'b0;
            data_reg  <= '0;
        end else begin
            case (s_state)
                S_IDLE: begin
                    if (valid_in) begin
                        data_reg <= data_in;
                        req_a    <= 1'b1;
                        s_state  <= S_WAIT_ACK;
                    end
                end
                S_WAIT_ACK: begin
                    if (ack_sync_2) begin
                        req_a   <= 1'b0;
                        s_state <= S_WAIT_DEACK;
                    end
                end
                S_WAIT_DEACK: begin
                    if (!ack_sync_2) begin
                        s_state <= S_IDLE;
                    end
                end
                default: s_state <= S_IDLE;
            endcase
        end
    end

    assign ready_out = (s_state == S_IDLE);

    // ==========================================
    // Receiver Side (clk_b domain)
    // ==========================================

    // Synchronize req from sender into receiver domain
    always_ff @(posedge clk_b or negedge rst_b_n) begin
        if (!rst_b_n) begin
            req_sync_1    <= 1'b0;
            req_sync_2    <= 1'b0;
            req_sync_prev <= 1'b0;
        end else begin
            req_sync_1    <= req_a;
            req_sync_2    <= req_sync_1;
            req_sync_prev <= req_sync_2;
        end
    end

    // Detect rising edge of synchronized req
    logic req_rising;
    assign req_rising = req_sync_2 && !req_sync_prev;

    // Capture data and generate ack
    always_ff @(posedge clk_b or negedge rst_b_n) begin
        if (!rst_b_n) begin
            data_out  <= '0;
            valid_out <= 1'b0;
            ack_b     <= 1'b0;
        end else begin
            valid_out <= 1'b0;  // Default: pulse
            if (req_rising) begin
                data_out  <= data_reg;  // Safe: data is stable!
                valid_out <= 1'b1;
                ack_b     <= 1'b1;
            end else if (!req_sync_2) begin
                ack_b     <= 1'b0;
            end
        end
    end

endmodule

3. Pulse Synchronizer

Sometimes you don't need to transfer data — you just need to send a pulse event (like "increment counter" or "clear flag") from one clock domain to another. A pulse synchronizer converts a single-cycle pulse in one domain to a single-cycle pulse in another.

때로는 데이터를 전달할 필요 없이 한 클록 도메인에서 다른 도메인으로 펄스 이벤트("카운터 증가" 또는 "플래그 클리어" 같은)만 보내면 됩니다. 펄스 동기화기는 한 도메인의 단일 사이클 펄스를 다른 도메인의 단일 사이클 펄스로 변환합니다.

💡 Pulse Sync: The Toggle Trick

The idea is elegant:

아이디어가 우아합니다:

  1. On each pulse in domain A, toggle a level signal (0→1 or 1→0)
  2. 도메인 A에서 각 펄스마다 레벨 신호를 토글 (0→1 또는 1→0)
  3. Synchronize the toggling level through a 2-flop synchronizer into domain B
  4. 토글하는 레벨 신호를 2-플립플롭 동기화기를 통해 도메인 B로 동기화
  5. In domain B, detect edges (XOR with previous value) → that's your pulse!
  6. 도메인 B에서 엣지를 감지 (이전 값과 XOR) → 그것이 펄스!
module pulse_sync (
    input  logic clk_a,
    input  logic rst_a_n,
    input  logic pulse_in,    // Single-cycle pulse in clk_a

    input  logic clk_b,
    input  logic rst_b_n,
    output logic pulse_out   // Single-cycle pulse in clk_b
);

    // Toggle in domain A
    logic toggle_a;
    always_ff @(posedge clk_a or negedge rst_a_n) begin
        if (!rst_a_n)
            toggle_a <= 1'b0;
        else if (pulse_in)
            toggle_a <= ~toggle_a;
    end

    // 2-flop synchronizer in domain B
    logic sync_1, sync_2, sync_prev;
    always_ff @(posedge clk_b or negedge rst_b_n) begin
        if (!rst_b_n) begin
            sync_1    <= 1'b0;
            sync_2    <= 1'b0;
            sync_prev <= 1'b0;
        end else begin
            sync_1    <= toggle_a;
            sync_2    <= sync_1;
            sync_prev <= sync_2;
        end
    end

    // Edge detect = pulse output
    assign pulse_out = sync_2 ^ sync_prev;

endmodule

⚠️ Pulse Sync Limitation

The input pulse must be at least one clk_a cycle wide, and pulses must be spaced far enough apart that the toggle has time to propagate. If clk_a is much faster than clk_b, back-to-back pulses can be lost!

입력 펄스는 최소 clk_a 한 사이클 폭이어야 하고, 토글이 전파될 시간이 있도록 펄스 간 충분한 간격이 필요합니다. clk_a가 clk_b보다 훨씬 빠르면 연속 펄스가 손실될 수 있습니다!

Rule of thumb: Minimum spacing between pulses ≥ 2 × clk_b period + synchronizer delay.

경험 법칙: 펄스 간 최소 간격 ≥ 2 × clk_b 주기 + 동기화기 지연.

4. Comparison: Which CDC Method to Use?

2-Flop Sync Single-bit level signals 단일 비트 레벨 신호 N/A (level) 해당 없음 (레벨) Very Low 매우 낮음
Pulse Sync Single-bit events/pulses 단일 비트 이벤트/펄스 Low 낮음 Low 낮음

💡 Interview Tip

A very common interview question: "How do you transfer multi-bit data across clock domains?" Start with the handshake (simplest), then mention async FIFO for high-throughput scenarios. Always emphasize that the data must be stable when sampled.

매우 흔한 면접 질문: "클록 도메인 간에 멀티비트 데이터를 어떻게 전달하나요?" 핸드셰이크(가장 단순)부터 시작하고, 높은 처리량이 필요한 경우 비동기 FIFO를 언급하세요. 데이터가 샘플링될 때 안정적이어야 한다는 것을 항상 강조하세요.

5. Full-Cycle vs. Half-Cycle Handshake

What we described above is a full-cycle (4-phase) handshake: req goes high, ack goes high, req goes low, ack goes low. There's also a faster variant:

위에서 설명한 것은 풀 사이클 (4-phase) 핸드셰이크입니다: req 상승, ack 상승, req 하강, ack 하강. 더 빠른 변형도 있습니다:

⚡ Half-Cycle (2-Phase) Handshake

Instead of waiting for both req and ack to return to zero, treat each toggle (edge) as a new transaction. This doubles throughput but adds complexity.

req와 ack가 모두 0으로 돌아오길 기다리는 대신, 각 토글(엣지)을 새로운 트랜잭션으로 취급합니다. 처리량이 두 배가 되지만 복잡도가 증가합니다.

  • 4-phase: req↑ → ack↑ → req↓ → ack↓ (4 sync delays per transfer)
  • 4-phase: req↑ → ack↑ → req↓ → ack↓ (전송당 4번의 동기화 지연)
  • 2-phase: req toggle → ack toggle (2 sync delays per transfer)
  • 2-phase: req 토글 → ack 토글 (전송당 2번의 동기화 지연)

6. Key Takeaways

📌 Summary

  1. Never synchronize multi-bit data bit-by-bit — use a handshake or FIFO
  2. 멀티비트 데이터를 비트별로 동기화하지 절대 마세요 — 핸드셰이크나 FIFO를 사용
  3. Req/ack handshake: simple, reliable, but low throughput (~4 sync delays per transfer)
  4. Req/ack 핸드셰이크: 간단하고 신뢰성 있지만 낮은 처리량 (~전송당 4번의 동기화 지연)
  5. Pulse synchronizer: converts a pulse event across domains using toggle + edge detect
  6. 펄스 동기화기: 토글 + 엣지 감지를 사용하여 도메인 간 펄스 이벤트 변환
  7. Data stability is the core principle — hold data until the receiver confirms capture
  8. 데이터 안정성이 핵심 원칙 — 수신측이 캡처를 확인할 때까지 데이터를 유지
  9. Choose complexity based on throughput needs: handshake → async FIFO
  10. 처리량 요구사항에 따라 복잡도 선택: 핸드셰이크 → 비동기 FIFO

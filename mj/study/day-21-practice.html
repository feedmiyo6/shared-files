Exercise 1: Pipeline a Simple Adder

🎯 Goal

🎯 목표

Take a non-pipelined 32-bit adder-accumulator and convert it to a 2-stage pipelined version. Compare latency and throughput.

파이프라인 없는 32비트 덧셈기-누적기를 2단계 파이프라인 버전으로 변환하세요. 레이턴시와 처리량을 비교하세요.

Starting Code (Non-Pipelined)

시작 코드 (파이프라인 없음)

module add_and_saturate (
    input  logic        clk, rst_n,
    input  logic [31:0] a, b,
    output logic [31:0] result,
    output logic        overflow
);
    // All in one cycle: add, check overflow, saturate
    logic [32:0] sum_ext;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            result   <= '0;
            overflow <= '0;
        end else begin
            sum_ext  = {1'b0, a} + {1'b0, b};
            overflow <= sum_ext[32];
            result   <= sum_ext[32] ? 32'hFFFF_FFFF : sum_ext[31:0];
        end
    end
endmodule

💡 Hint

Stage 1: Perform the addition and store the extended result.
Stage 2: Check overflow and apply saturation.

1단계: 덧셈을 수행하고 확장된 결과를 저장합니다.
2단계: 오버플로를 확인하고 포화를 적용합니다.

module add_and_saturate_pipe (
    input  logic        clk, rst_n,
    input  logic [31:0] a, b,
    output logic [31:0] result,
    output logic        overflow
);
    // ---- Stage 1: Addition ----
    logic [32:0] sum_ext_s1;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n)
            sum_ext_s1 <= '0;
        else
            sum_ext_s1 <= {1'b0, a} + {1'b0, b};
    end

    // ---- Stage 2: Overflow check + Saturation ----
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            result   <= '0;
            overflow <= '0;
        end else begin
            overflow <= sum_ext_s1[32];
            result   <= sum_ext_s1[32] ? 32'hFFFF_FFFF
                                            : sum_ext_s1[31:0];
        end
    end
endmodule

📊 분석

MetricNon-pipelined2-stage
Latency (cycles)12
Max clock (est.)200 MHz350 MHz
Latency (time)5 ns5.7 ns
Throughput200 Mops/s350 Mops/s

Exercise 2: Calculate FIFO Depth

🎯 Scenario

🎯 시나리오

A producer writes data at 500 MHz. A consumer reads at 400 MHz. The CDC synchronization adds 5 cycles of latency on the read side. What is the minimum FIFO depth to avoid data loss during a burst of 100 consecutive writes?

프로듀서가 500 MHz로 데이터를 씁니다. 컨슈머가 400 MHz로 읽습니다. CDC 동기화가 읽기 측에 5 사이클의 레이턴시를 추가합니다. 100개 연속 쓰기 버스트 동안 데이터 손실을 방지하기 위한 최소 FIFO 깊이는?

💡 Hints

1. During the burst, how many writes happen?
2. During the same time, how many reads can happen?
3. Don't forget the initial latency before reads start!
4. FIFO depth ≥ max(writes - reads) at any point in time.

1. 버스트 동안 몇 번의 쓰기가 발생하나요?
2. 같은 시간 동안 몇 번의 읽기가 가능하나요?
3. 읽기가 시작되기 전 초기 레이턴시를 잊지 마세요!
4. FIFO 깊이 ≥ 어느 시점에서든 max(쓰기 - 읽기).

📊 Solution

📊 풀이

Step 1: Burst duration = 100 writes / 500 MHz = 200 ns

1단계: 버스트 기간 = 100 쓰기 / 500 MHz = 200 ns

Step 2: Read latency = 5 cycles / 400 MHz = 12.5 ns (reads start after this)

2단계: 읽기 레이턴시 = 5 사이클 / 400 MHz = 12.5 ns (이후 읽기 시작)

Step 3: Effective read time = 200 - 12.5 = 187.5 ns

3단계: 유효 읽기 시간 = 200 - 12.5 = 187.5 ns

Step 4: Reads completed = 187.5 ns × 400 MHz = 75 reads

4단계: 완료된 읽기 = 187.5 ns × 400 MHz = 75 읽기

Step 5: Max backlog = 100 - 75 = 25 entries

5단계: 최대 백로그 = 100 - 75 = 25 엔트리

Answer: Minimum FIFO depth = 25 (round up to 32 for power-of-2)

답: 최소 FIFO 깊이 = 25 (2의 거듭제곱으로 반올림하여 32)

Exercise 3: Throughput Analysis

🎯 Challenge

🎯 도전

You have a data processing pipeline with these stages:

다음 단계를 가진 데이터 처리 파이프라인이 있습니다:

  • Stage A: Decode — 3 ns combinational delay
  • A단계: 디코드 — 3 ns 조합 지연
  • Stage B: Execute — 8 ns combinational delay
  • B단계: 실행 — 8 ns 조합 지연
  • Stage C: Writeback — 2 ns combinational delay
  • C단계: 쓰기 — 2 ns 조합 지연

Register overhead (setup + clk-to-q) = 0.5 ns per stage.

레지스터 오버헤드(셋업 + clk-to-q) = 단계당 0.5 ns.

Calculate: (a) Max clock freq non-pipelined? (b) Max clock freq pipelined? (c) Throughput improvement? (d) Latency change?

계산: (a) 파이프라인 없는 최대 클럭 주파수? (b) 파이프라인 최대 클럭 주파수? (c) 처리량 개선? (d) 레이턴시 변화?

📊 Solution

(a) Non-pipelined:

(a) 파이프라인 없음:

Total delay = 3 + 8 + 2 + 0.5 = 13.5 ns → Max freq = 74 MHz

(b) Pipelined (3 stages):

(b) 파이프라인 (3단계):

Critical stage = B = 8 + 0.5 = 8.5 ns → Max freq = 117.6 MHz

(c) Throughput improvement:

(c) 처리량 개선:

117.6 / 74 = 1.59×

(d) Latency:

(d) 레이턴시:

Non-pipelined: 1 × 13.5 = 13.5 ns
Pipelined: 3 × 8.5 = 25.5 ns
Latency increased by 1.89× — this is the tradeoff!

파이프라인 없음: 1 × 13.5 = 13.5 ns
파이프라인: 3 × 8.5 = 25.5 ns
레이턴시 1.89배 증가 — 이것이 트레이드오프입니다!

💡 Key Observation

The bottleneck stage (B = 8 ns) limits the whole pipeline. To improve further, you'd split Stage B into two sub-stages — that's tomorrow's topic!

병목 단계(B = 8 ns)가 전체 파이프라인을 제한합니다. 더 개선하려면 B단계를 두 개의 하위 단계로 분할해야 합니다 — 이것이 내일의 주제입니다!

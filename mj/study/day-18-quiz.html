Q1. Why can't you just put a 2-flop synchronizer on each bit of a multi-bit bus?멀티비트 버스의 각 비트에 2-플립플롭 동기화기를 넣을 수 없는 이유는?

  • A) It uses too many flip-flopsA) 플립플롭을 너무 많이 사용해서
  • B) Different bits may resolve metastability at different times, corrupting dataB) 다른 비트들이 다른 시점에 메타스터빌리티를 해결하여 데이터가 손상될 수 있음
  • C) It only works for synchronous domainsC) 동기 도메인에서만 작동해서
  • D) The synthesis tool won't allow itD) 합성 도구가 허용하지 않아서
✅ Each bit's synchronizer resolves independently, so bits can arrive at different clock edges, creating a corrupted intermediate value. For example, 0111→1000 might be read as 0000 or 1111. ✅ 각 비트의 동기화기가 독립적으로 해결되므로, 비트들이 다른 클록 엣지에 도착하여 손상된 중간 값이 생성될 수 있습니다. 예: 0111→1000이 0000이나 1111로 읽힐 수 있습니다.

Q2. In a 4-phase req/ack handshake, what is the correct sequence?4-phase req/ack 핸드셰이크에서 올바른 순서는?

  • A) req↑ → req↓ → ack↑ → ack↓A) req↑ → req↓ → ack↑ → ack↓
  • B) ack↑ → req↑ → ack↓ → req↓B) ack↑ → req↑ → ack↓ → req↓
  • C) req↑ → ack↑ → req↓ → ack↓C) req↑ → ack↑ → req↓ → ack↓
  • D) req↑ → ack↑ → ack↓ → req↓D) req↑ → ack↑ → ack↓ → req↓
✅ The 4-phase handshake: sender asserts req, receiver asserts ack, sender de-asserts req, receiver de-asserts ack. Each transition is separated by a synchronization delay. ✅ 4-phase 핸드셰이크: 송신측이 req 어서트, 수신측이 ack 어서트, 송신측이 req 디어서트, 수신측이 ack 디어서트. 각 전환은 동기화 지연으로 분리됩니다.

Q3. How many synchronization delays does a full 4-phase handshake require per transfer?4-phase 핸드셰이크는 전송당 몇 번의 동기화 지연이 필요합니까?

  • A) 2A) 2
  • B) 4B) 4
  • C) 6C) 6
  • D) 8D) 8
✅ Each of the 4 transitions (req↑, ack↑, req↓, ack↓) must pass through a 2-flop synchronizer, so 4 synchronization delays per complete transfer. ✅ 4개의 전환(req↑, ack↑, req↓, ack↓) 각각이 2-플립플롭 동기화기를 통과해야 하므로, 완전한 전송당 4번의 동기화 지연이 필요합니다.

Q4. What ensures the multi-bit data is safely captured in a handshake CDC?핸드셰이크 CDC에서 멀티비트 데이터가 안전하게 캡처되는 것을 보장하는 것은?

  • A) Data is held stable while only single-bit req/ack signals cross domainsA) 단일 비트 req/ack 신호만 도메인을 넘는 동안 데이터가 안정적으로 유지
  • B) Each data bit has its own synchronizerB) 각 데이터 비트마다 자체 동기화기가 있음
  • C) Gray coding is used on the data busC) 데이터 버스에 그레이 코딩이 사용됨
  • D) The receiver uses a faster clockD) 수신측이 더 빠른 클록을 사용
✅ The key principle: data is placed on the bus and held stable. Only the single-bit req signal crosses domains. The receiver samples data only after req is safely synchronized, guaranteeing stability. ✅ 핵심 원칙: 데이터가 버스에 놓이고 안정적으로 유지됩니다. 단일 비트 req 신호만 도메인을 넘습니다. 수신측은 req가 안전하게 동기화된 후에만 데이터를 샘플링하여 안정성을 보장합니다.

Q5. How does a pulse synchronizer work?펄스 동기화기는 어떻게 작동합니까?

  • A) Stretches the pulse to span multiple clock cyclesA) 펄스를 여러 클록 사이클에 걸쳐 늘림
  • B) Uses a FIFO to buffer pulsesB) FIFO를 사용하여 펄스를 버퍼링
  • C) Converts pulse to toggle, synchronizes the toggle, then detects edgesC) 펄스를 토글로 변환하고, 토글을 동기화한 후, 엣지를 감지
  • D) Directly passes the pulse through a 2-flop synchronizerD) 펄스를 2-플립플롭 동기화기를 통해 직접 전달
✅ The toggle trick: each pulse toggles a level signal in domain A. This level is synchronized via 2-flop into domain B, where an XOR with the previous value detects the edge and regenerates the pulse. ✅ 토글 트릭: 각 펄스가 도메인 A에서 레벨 신호를 토글합니다. 이 레벨이 2-플립플롭을 통해 도메인 B로 동기화되고, 이전 값과의 XOR로 엣지를 감지하여 펄스를 재생성합니다.

Q6. What happens if you send back-to-back pulses through a pulse synchronizer when clk_a >> clk_b?clk_a >> clk_b일 때 펄스 동기화기를 통해 연속 펄스를 보내면 어떻게 됩니까?

  • A) They get queued and delivered in orderA) 큐에 저장되어 순서대로 전달됨
  • B) Pulses can be lost because the toggle doesn't have time to propagateB) 토글이 전파될 시간이 없어 펄스가 손실될 수 있음
  • C) The synchronizer generates multiple pulses for each inputC) 동기화기가 각 입력에 대해 여러 펄스를 생성
  • D) Metastability occurs on the data busD) 데이터 버스에서 메타스터빌리티가 발생
✅ If two pulses arrive before the first toggle propagates to domain B, the second toggle cancels the first, and a pulse is lost. Minimum pulse spacing must be ≥ 2 × clk_b period + sync delay. ✅ 첫 번째 토글이 도메인 B로 전파되기 전에 두 번째 펄스가 도착하면, 두 번째 토글이 첫 번째를 취소하여 펄스가 손실됩니다. 최소 펄스 간격은 ≥ 2 × clk_b 주기 + 동기화 지연이어야 합니다.

  • A) IDLE, SENDA) IDLE, SEND
  • B) IDLE, WAIT_ACKB) IDLE, WAIT_ACK
  • C) IDLE, SEND, DONEC) IDLE, SEND, DONE

Q8. What advantage does a 2-phase handshake have over a 4-phase handshake?2-phase 핸드셰이크가 4-phase 핸드셰이크에 비해 가지는 장점은?

  • A) It's simpler to implementA) 구현이 더 간단함
  • B) It has higher throughput (2 sync delays vs. 4)B) 더 높은 처리량 (2번 vs. 4번의 동기화 지연)
  • C) It doesn't need synchronizersC) 동기화기가 필요 없음
  • D) It supports wider data busesD) 더 넓은 데이터 버스를 지원
✅ A 2-phase handshake treats each edge (toggle) as a transaction, so it only needs 2 synchronization delays per transfer instead of 4, doubling throughput. However, it's more complex to implement. ✅ 2-phase 핸드셰이크는 각 엣지(토글)를 트랜잭션으로 취급하므로, 전송당 4번 대신 2번의 동기화 지연만 필요하여 처리량이 두 배가 됩니다. 하지만 구현이 더 복잡합니다.

Q9. When should you choose a handshake over an async FIFO for CDC?CDC에서 비동기 FIFO 대신 핸드셰이크를 선택해야 할 때는?

  • A) When data transfers are infrequent and low throughput is acceptableA) 데이터 전송이 비빈번하고 낮은 처리량이 허용될 때
  • B) When you need to stream continuous dataB) 연속 데이터를 스트리밍해야 할 때
  • C) When both clocks are the same frequencyC) 두 클록이 같은 주파수일 때
  • D) When you need zero latencyD) 제로 레이턴시가 필요할 때
✅ Handshakes are ideal for infrequent, low-bandwidth transfers (config registers, commands, status updates). For continuous streaming data, an async FIFO is more appropriate due to much higher throughput. ✅ 핸드셰이크는 비빈번한 저대역폭 전송(설정 레지스터, 명령, 상태 업데이트)에 이상적입니다. 연속 스트리밍 데이터에는 훨씬 높은 처리량 때문에 비동기 FIFO가 더 적합합니다.

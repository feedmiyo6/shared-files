Q1. What are the three core components of an FSM?

FSM의 세 가지 핵심 구성 요소는?

  • A) Inputs, outputs, clock
  • B) States, transitions, outputs
  • C) Registers, wires, modules
  • D) Clock, reset, enable

✅ States, transitions, and outputs are the three fundamental components. States define possible conditions, transitions define how to move between them, and outputs define what the FSM produces.

✅ 상태, 전이, 출력이 세 가지 기본 구성 요소입니다.

Q2. In the standard 3-block FSM pattern, what type of block is used for next-state logic?

표준 3블록 FSM 패턴에서 다음 상태 로직에 어떤 블록 유형을 사용하나요?

  • A) always_ff
  • B) always_latch
  • C) always_comb
  • D) assign

✅ Next-state logic is combinational — it calculates the next state from current state + inputs without any clock dependency. Use always_comb.

✅ 다음 상태 로직은 조합 논리입니다 — always_comb을 사용합니다.

Q3. Why do we set next_state = state; at the top of the next-state logic block?

다음 상태 로직 블록 상단에서 왜 next_state = state;를 설정하나요?

  • A) To prevent latch inference from missing assignments
  • B) To make the FSM run faster
  • C) It's just a coding convention with no functional purpose
  • D) To reset the state machine

✅ If any branch of the case statement doesn't assign next_state, synthesis will infer a latch to hold the previous value. The default assignment ensures every path has a value.

✅ case 문의 어떤 분기가 next_state를 할당하지 않으면, 합성이 이전 값을 유지하기 위해 래치를 추론합니다.

Q4. What happens if you omit the default case in your FSM?

FSM에서 default 케이스를 생략하면 어떻게 되나요?

  • A) The FSM will always reset to IDLE
  • B) Synthesis will fail with an error
  • C) The FSM runs normally — default isn't needed
  • D) An illegal state could trap the FSM forever

✅ Without a default case, if the FSM enters an undefined state (due to SEU, power glitch, etc.), there's no transition defined — it gets stuck. Always include default: next_state = IDLE;

✅ default 케이스 없이 FSM이 정의되지 않은 상태에 진입하면 전이가 정의되지 않아 멈춥니다.

Q5. Which block should contain the state register?

상태 레지스터는 어떤 블록에 포함되어야 하나요?

  • A) always_comb
  • B) always_ff @(posedge clk)
  • C) assign
  • D) initial

✅ The state register is sequential — it updates on the clock edge and must use always_ff with non-blocking assignments (<=).

✅ 상태 레지스터는 순차 논리입니다 — 클럭 엣지에서 업데이트되며 always_ff를 사용해야 합니다.

Q6. What is the benefit of typedef enum for FSM states?

FSM 상태에 typedef enum을 사용하는 이점은?

  • A) It makes the FSM run faster in hardware
  • B) It reduces the number of flip-flops needed
  • C) Readable names, waveform labels, and type checking
  • D) It automatically prevents illegal states

✅ typedef enum gives you human-readable state names in code and waveforms, plus compile-time type checking. It doesn't affect the actual hardware.

✅ typedef enum은 코드와 파형에서 읽기 쉬운 상태 이름과 컴파일 타임 타입 검사를 제공합니다.

Q7. What's wrong with this code?

always_ff @(posedge clk) begin
    case (state)
        IDLE: if (start) next_state = RUN;
        RUN:  if (done)  next_state = IDLE;
    endcase
end
  • A) Next-state logic should use always_comb, not always_ff
  • B) Missing reset logic
  • C) Should use <= instead of =
  • D) Missing default case only

✅ The biggest issue is using always_ff for combinational next-state logic. This should be always_comb. (It's also missing a default and default assignment, but the block type is the primary error.)

✅ 가장 큰 문제는 조합 논리인 다음 상태 로직에 always_ff를 사용한 것입니다. always_comb이어야 합니다.

Q8. In the 3-block pattern, output logic for a basic FSM should be:

3블록 패턴에서 기본 FSM의 출력 로직은:

  • A) Sequential — clocked with always_ff
  • B) Combinational — based on current state with always_comb
  • C) Either one works exactly the same
  • D) Must use continuous assign statements

✅ In a standard (Moore) FSM, output logic is combinational — outputs depend only on the current state. Use always_comb or assign.

✅ 표준 (Moore) FSM에서 출력 로직은 조합 논리입니다 — 출력은 현재 상태에만 의존합니다.

Q9. What should you do BEFORE writing any FSM SystemVerilog code?

FSM SystemVerilog 코드를 작성하기 전에 무엇을 해야 하나요?

  • A) Write the testbench first
  • B) Choose the encoding (binary, one-hot, etc.)
  • C) Draw a state diagram
  • D) Set up the synthesis constraints

✅ Always draw a state diagram first. It forces you to think through all states, transitions, and edge cases before writing code. Coding without a diagram leads to bugs.

✅ 항상 상태 다이어그램을 먼저 그리세요. 코드 작성 전에 모든 상태, 전이, 엣지 케이스를 생각하게 합니다.

Q10. In the packet receiver example, why is byte_count in a separate always_ff block from the state register?

패킷 수신기 예시에서 왜 byte_count가 상태 레지스터와 별도의 always_ff 블록에 있나요?

  • A) SystemVerilog doesn't allow two registers in one block
  • B) It runs on a different clock
  • C) It needs to count faster than the state changes
  • D) Clean separation of concerns — FSM controls when, counter controls how

✅ It's a design pattern — separating the counter from the state register keeps each block focused on one job. The FSM decides when counting happens; the counter block handles the counting logic.

✅ 디자인 패턴입니다 — 카운터를 상태 레지스터와 분리하면 각 블록이 하나의 역할에 집중합니다.

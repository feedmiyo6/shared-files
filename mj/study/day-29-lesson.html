Welcome to Day 29! Yesterday we explored arbitration — how to fairly share a bus among multiple masters. Today we tackle the next critical piece: flow control. How does a sender know if the receiver can accept data? How do we prevent data loss without killing throughput? Buffering and credit-based flow control are the answers.

Day 29에 오신 걸 환영합니다! 어제는 중재(arbitration) — 여러 마스터가 버스를 공정하게 공유하는 방법을 배웠습니다. 오늘은 다음 핵심 주제인 흐름 제어(flow control)를 다룹니다. 송신자가 수신자가 데이터를 받을 수 있는지 어떻게 알 수 있을까요? 처리량을 죽이지 않고 데이터 손실을 방지하는 방법은? 버퍼링과 크레딧 기반 흐름 제어가 그 답입니다.

1. Why Flow Control Matters

In any digital system where a producer generates data and a consumer processes it, the two may operate at different rates. Without flow control:

데이터를 생성하는 생산자(producer)와 처리하는 소비자(consumer)가 있는 디지털 시스템에서, 둘은 서로 다른 속도로 동작할 수 있습니다. 흐름 제어 없이는:

  • Data gets dropped when the receiver is busy
  • 수신자가 바쁠 때 데이터가 손실됩니다
  • The receiver overflows its internal storage
  • 수신자의 내부 저장소가 오버플로됩니다
  • The system becomes unreliable
  • 시스템이 불안정해집니다

🎯 The Core Problem

A sender producing 1 word/cycle talks to a receiver that sometimes needs 2-3 cycles per word (e.g., memory writes). Without flow control, the sender blindly pushes data and the receiver loses it.

1 cycle당 1 워드를 생산하는 송신자가, 가끔 워드당 2~3 cycle이 필요한 수신자(예: 메모리 쓰기)와 통신합니다. 흐름 제어 없이는, 송신자가 맹목적으로 데이터를 밀어넣어 수신자가 데이터를 잃게 됩니다.

3. Buffering with FIFOs

The most common flow control mechanism is inserting a FIFO buffer between producer and consumer. The FIFO absorbs bursts when the consumer is slower, and drains when the consumer catches up.

가장 흔한 흐름 제어 메커니즘은 생산자와 소비자 사이에 FIFO 버퍼를 삽입하는 것입니다. FIFO는 소비자가 느릴 때 버스트를 흡수하고, 소비자가 따라잡으면 비워집니다.

Producer FIFO Buffer Consumer ┌─────┐ ┌─────────────┐ ┌─────┐ │ ├──────►│ ░░░░░░░░ ├──────►│ │ │ TX │ wr_en │ depth = 8 │ rd_en │ RX │ │ │◄──────┤ count = 5 ├──────►│ │ └─────┘ !full └─────────────┘!empty └─────┘ Write side: Read side: - Writes when !full - Reads when !empty - Stalls when full - Stalls when empty - count tracks occupancy - Decouples timing

Key FIFO Signals for Flow Control

module fifo_flow_ctrl #(
    parameter DEPTH = 8,
    parameter WIDTH = 32
)(
    input  logic             clk,
    input  logic             rst_n,
    // Write (producer) side
    input  logic             wr_valid,   // Producer has data
    input  logic [WIDTH-1:0] wr_data,
    output logic             wr_ready,   // FIFO can accept (not full)
    // Read (consumer) side
    output logic             rd_valid,   // FIFO has data (not empty)
    output logic [WIDTH-1:0] rd_data,
    input  logic             rd_ready,   // Consumer can accept
    // Status
    output logic [$clog2(DEPTH):0] count
);

    logic [WIDTH-1:0] mem [DEPTH];
    logic [$clog2(DEPTH)-1:0] wr_ptr, rd_ptr;

    wire do_write = wr_valid && wr_ready;
    wire do_read  = rd_valid && rd_ready;

    assign wr_ready = (count < DEPTH);     // Not full
    assign rd_valid = (count > 0);         // Not empty
    assign rd_data  = mem[rd_ptr];

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            wr_ptr <= '0;
            rd_ptr <= '0;
            count  <= '0;
        end else begin
            if (do_write) begin
                mem[wr_ptr] <= wr_data;
                wr_ptr <= wr_ptr + 1;
            end
            if (do_read) begin
                rd_ptr <= rd_ptr + 1;
            end
            // Update count
            case ({do_write, do_read})
                2'b10: count <= count + 1;
                2'b01: count <= count - 1;
                default: count <= count;
            endcase
        end
    end

endmodule

💡 FIFO Sizing Rule of Thumb

FIFO depth should cover the worst-case burst where the producer outpaces the consumer. If the producer sends at rate Rp and consumer drains at rate Rc during a burst of B cycles: Depth ≥ B × (R_p - R_c) / R_p

FIFO 깊이는 생산자가 소비자보다 빠른 최악의 버스트를 커버해야 합니다. 생산자가 Rp 속도로, 소비자가 Rc 속도로, B cycle 동안 버스트하면: 깊이 ≥ B × (R_p - R_c) / R_p

4. Credit-Based Flow Control

Ready/valid has a subtle problem: the ready signal must propagate from receiver to sender, creating a combinational path. For long pipelines or across chips, this path is too slow. Credit-based flow control solves this elegantly.

Ready/valid에는 미묘한 문제가 있습니다: ready 신호가 수신자에서 송신자로 전파되어야 하며, 이것이 조합 경로를 만듭니다. 긴 파이프라인이나 칩 간에는 이 경로가 너무 느립니다. 크레딧 기반 흐름 제어가 이를 우아하게 해결합니다.

🏦 Credit System Analogy

Think of it like a bank account. The receiver has a FIFO with N slots. The sender starts with N credits (one per slot). Each send costs 1 credit. Each time the receiver consumes an entry, it returns 1 credit. The sender never sends when credits = 0, guaranteeing no overflow.

은행 계좌처럼 생각하세요. 수신자는 N개 슬롯의 FIFO를 가집니다. 송신자는 N개의 크레딧(슬롯당 하나)으로 시작합니다. 전송할 때마다 크레딧 1개 소모. 수신자가 항목을 소비하면 크레딧 1개 반환. 송신자는 크레딧 = 0일 때 절대 전송하지 않으므로, 오버플로가 보장되지 않습니다.

Credit-Based Flow Control Sender Receiver ┌──────────┐ data (when credits>0) ┌──────────┐ │ ├────────────────────────────►│ FIFO │ │ credits │ │ (N=4) │ │ = 2 │◄────────────────────────────┤ │ │ │ credit_return │ │ └──────────┘ (when entry consumed) └──────────┘ Timeline: Cycle 1: credits=4, send A → credits=3 Cycle 2: credits=3, send B → credits=2 Cycle 3: credits=2, send C → credits=1, recv consumes A → credits=2 Cycle 4: credits=2, send D → credits=1 Cycle 5: credits=1, send E → credits=0 ← STALL until credit returns Cycle 6: credits=0, WAIT. recv consumes B → credits=1, send F

Credit-Based Sender Module

module credit_sender #(
    parameter MAX_CREDITS = 4,
    parameter WIDTH       = 32
)(
    input  logic             clk,
    input  logic             rst_n,
    // From upstream (data to send)
    input  logic             src_valid,
    input  logic [WIDTH-1:0] src_data,
    output logic             src_ready,    // Backpressure upstream
    // To downstream (credit-controlled link)
    output logic             tx_valid,
    output logic [WIDTH-1:0] tx_data,
    // Credit return from receiver
    input  logic             credit_return // Pulse: 1 credit returned
);

    logic [$clog2(MAX_CREDITS):0] credits;

    wire can_send  = (credits > 0) && src_valid;
    assign src_ready = (credits > 0);
    assign tx_valid  = can_send;
    assign tx_data   = src_data;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            credits <= MAX_CREDITS;  // Start with full credits
        end else begin
            case ({can_send, credit_return})
                2'b10: credits <= credits - 1;  // Sent, no return
                2'b01: credits <= credits + 1;  // Return, no send
                default: credits <= credits;    // Both or neither
            endcase
        end
    end

endmodule

Credit-Based Receiver Module

module credit_receiver #(
    parameter DEPTH = 4,
    parameter WIDTH = 32
)(
    input  logic             clk,
    input  logic             rst_n,
    // From sender (credit-controlled link)
    input  logic             rx_valid,
    input  logic [WIDTH-1:0] rx_data,
    // To downstream consumer
    output logic             out_valid,
    output logic [WIDTH-1:0] out_data,
    input  logic             out_ready,
    // Credit return to sender
    output logic             credit_return
);

    // Internal FIFO storage
    logic [WIDTH-1:0] fifo [DEPTH];
    logic [$clog2(DEPTH)-1:0] wr_ptr, rd_ptr;
    logic [$clog2(DEPTH):0] count;

    wire do_read = (count > 0) && out_ready;
    assign out_valid     = (count > 0);
    assign out_data      = fifo[rd_ptr];
    assign credit_return = do_read;  // Return credit when consumed

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            wr_ptr <= '0;
            rd_ptr <= '0;
            count  <= '0;
        end else begin
            if (rx_valid) begin
                fifo[wr_ptr] <= rx_data;
                wr_ptr <= wr_ptr + 1;
            end
            if (do_read) begin
                rd_ptr <= rd_ptr + 1;
            end
            case ({rx_valid, do_read})
                2'b10: count <= count + 1;
                2'b01: count <= count - 1;
                default: count <= count;
            endcase
        end
    end

endmodule

⚠️ Credit Counter Bugs

The most dangerous bug in credit systems: credit leak. If a credit is consumed but never returned (e.g., due to a dropped packet), the system slowly deadlocks. Always verify: credits_sent == credits_returned over any long period. Some designs add a periodic credit "refresh" as a safety net.

크레딧 시스템의 가장 위험한 버그: 크레딧 누수(leak). 크레딧이 소비되었지만 반환되지 않으면(예: 패킷 드롭), 시스템이 서서히 데드락에 빠집니다. 항상 검증하세요: 장기간에 걸쳐 보낸 크레딧 == 반환된 크레딧. 일부 설계는 안전장치로 주기적인 크레딧 "갱신"을 추가합니다.

6. XON/XOFF (Pause Frame) Flow Control

In serial links like Ethernet (very relevant to your work!), the receiver can send a pause frame to tell the sender to stop. This is XON/XOFF flow control — the same concept Minjun sees in 100BASE-T1 and 1000BASE-T1 PHYs.

이더넷과 같은 시리얼 링크에서(Minjun의 업무와 매우 관련 있음!), 수신자는 pause 프레임을 보내 송신자에게 멈추라고 알릴 수 있습니다. 이것이 XON/XOFF 흐름 제어입니다 — 100BASE-T1과 1000BASE-T1 PHY에서 볼 수 있는 바로 그 개념입니다.

🔌 Ethernet Pause Frames (IEEE 802.3x)

  • XOFF (Pause): Receiver sends a pause frame with a quanta timer value. Sender stops for that many quanta (1 quanta = 512 bit times).
  • XOFF (Pause): 수신자가 quanta 타이머 값이 포함된 pause 프레임을 전송. 송신자는 해당 quanta만큼 정지 (1 quanta = 512 비트 시간).
  • XON (Resume): Receiver sends a pause frame with quanta = 0 to cancel the pause early.
  • XON (Resume): 수신자가 quanta = 0인 pause 프레임을 보내 조기 재개.
  • Priority-Based (PFC): IEEE 802.1Qbb allows pausing specific traffic classes independently — critical for automotive networks.
  • 우선순위 기반 (PFC): IEEE 802.1Qbb는 특정 트래픽 클래스를 독립적으로 일시정지 가능 — 자동차 네트워크에 중요.

7. Elastic Buffers — Combining Concepts

In real chips, you often combine buffering with credit or ready/valid to create elastic buffers (also called skid buffers). These add 1-2 entries of storage to break timing paths while maintaining full throughput.

실제 칩에서는 종종 버퍼링을 크레딧이나 ready/valid와 결합하여 탄성 버퍼(elastic buffer)(스키드 버퍼라고도 함)를 만듭니다. 이는 1~2개의 저장 항목을 추가하여 전체 처리량을 유지하면서 타이밍 경로를 끊습니다.

// Skid buffer: breaks ready path while maintaining throughput
module skid_buffer #(
    parameter WIDTH = 32
)(
    input  logic             clk,
    input  logic             rst_n,
    // Input (registered ready)
    input  logic             in_valid,
    input  logic [WIDTH-1:0] in_data,
    output logic             in_ready,
    // Output
    output logic             out_valid,
    output logic [WIDTH-1:0] out_data,
    input  logic             out_ready
);

    logic [WIDTH-1:0] skid_data;
    logic             skid_valid;

    // Output comes from skid register if it has data
    assign out_valid = skid_valid || in_valid;
    assign out_data  = skid_valid ? skid_data : in_data;

    // Ready is registered — breaks combinational path!
    assign in_ready = !skid_valid;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            skid_valid <= 1'b0;
        end else if (in_valid && in_ready && !out_ready) begin
            // Input arrives but output blocked — store in skid
            skid_data  <= in_data;
            skid_valid <= 1'b1;
        end else if (out_ready) begin
            skid_valid <= 1'b0;  // Drain skid
        end
    end

endmodule

💡 Why Skid Buffers Matter

In ready/valid, the ready signal often creates the worst timing path in the design because it goes from consumer back through every pipeline stage. A skid buffer at each stage breaks this into 1-stage hops, making timing closure much easier.

Ready/valid에서 ready 신호는 종종 설계에서 최악의 타이밍 경로를 만듭니다. 소비자에서 모든 파이프라인 단계를 거꾸로 거쳐가기 때문입니다. 각 단계의 스키드 버퍼는 이를 1단계 홉으로 분리하여 타이밍 클로저를 훨씬 쉽게 만듭니다.

8. Real-World: Where You'll See This

🚗 Automotive Ethernet (Your Domain!)

  • MAC TX buffer: FIFO between the MAC layer and PHY. When the PHY can't transmit (e.g., link training), the buffer absorbs frames.
  • MAC TX 버퍼: MAC 계층과 PHY 사이의 FIFO. PHY가 전송할 수 없을 때(예: 링크 트레이닝), 버퍼가 프레임을 흡수합니다.
  • Switch fabric: Multi-port switches use credit-based flow control between ingress and egress ports to prevent head-of-line blocking.
  • 스위치 패브릭: 멀티포트 스위치는 입력과 출력 포트 사이에 크레딧 기반 흐름 제어를 사용하여 head-of-line 블로킹을 방지합니다.
  • RGMII/SGMII interface: Elastic buffers compensate for clock frequency differences between MAC and PHY.
  • RGMII/SGMII 인터페이스: 탄성 버퍼가 MAC과 PHY 간의 클럭 주파수 차이를 보상합니다.

🧠 Key Takeaways

  1. FIFOs are the workhorses of flow control — they decouple producer and consumer rates
  2. FIFO는 흐름 제어의 핵심 — 생산자와 소비자 속도를 분리합니다
  3. Credit-based flow control eliminates the ready-path problem in long pipelines
  4. 크레딧 기반 흐름 제어는 긴 파이프라인에서 ready 경로 문제를 제거합니다
  5. Skid buffers break combinational paths while maintaining throughput
  6. 스키드 버퍼는 처리량을 유지하면서 조합 경로를 끊습니다
  7. XON/XOFF pause frames are how Ethernet does flow control — directly relevant to your PHY work
  8. XON/XOFF pause 프레임은 이더넷의 흐름 제어 방식 — PHY 업무에 직접 관련됩니다
  9. Size buffers for worst-case burst, not average case
  10. 버퍼 크기는 평균이 아닌 최악의 버스트 기준으로 설정하세요

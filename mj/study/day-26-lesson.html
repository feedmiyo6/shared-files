1. The Ready/Valid Contract

The ready/valid handshake is the most fundamental bus protocol in digital design. Every modern SoC uses it — AXI, AHB, TileLink, and custom interfaces all build on this pattern.

Ready/valid 핸드셰이크는 디지털 설계에서 가장 기본적인 버스 프로토콜입니다. 모든 현대 SoC가 이를 사용합니다 — AXI, AHB, TileLink, 커스텀 인터페이스 모두 이 패턴 위에 구축됩니다.

📋 The Three Signals

Valid — Source says "I have data ready"
Ready — Sink says "I can accept data"
Data — The payload being transferred

Valid — 소스가 "데이터가 준비됐다"고 알림
Ready — 싱크가 "데이터를 받을 수 있다"고 알림
Data — 전송되는 페이로드

Transfer happens when: valid && ready on the rising clock edge.

전송 발생 조건: 클록 상승 에지에서 valid && ready.

2. Timing Diagram: Normal Transfer

Let's trace cycle-by-cycle how a normal handshake works. The source asserts valid and presents data. The sink asserts ready. When both are high simultaneously, the transfer completes.

정상 핸드셰이크가 어떻게 작동하는지 사이클별로 추적해봅시다. 소스가 valid를 어서트하고 data를 제시합니다. 싱크가 ready를 어서트합니다. 둘 다 동시에 하이일 때 전송이 완료됩니다.

              Cycle 1    Cycle 2    Cycle 3    Cycle 4    Cycle 5
         ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐
  clk    ┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘

              ┌─────────────────────┐
  valid  ─────┘                     └─────────────────────────────
              ┌─────────────────────┐
  data   ═════╡       D0           ╞═════════════════════════════
                        ┌──────────┐
  ready  ───────────────┘          └──────────────────────────────

                           ↑
                      TRANSFER! (valid & ready both HIGH)

Key observations:

주요 관찰:

  • Source asserts valid + data at Cycle 1
  • 소스가 사이클 1에서 valid + data를 어서트
  • Sink asserts ready at Cycle 2 (it needed one cycle to prepare)
  • 싱크가 사이클 2에서 ready를 어서트 (준비에 1 사이클 필요)
  • Transfer occurs at the Cycle 2→3 clock edge (both high)
  • 전송은 사이클 2→3 클록 에지에서 발생 (둘 다 하이)
  • Source deasserts valid after successful transfer
  • 소스가 성공적 전송 후 valid를 디어서트

4. Timing Diagram: Backpressure (Stall)

This is the most important scenario for pipeline design. The sink is busy and cannot accept data, so it deasserts ready. The source MUST hold valid and data stable.

파이프라인 설계에서 가장 중요한 시나리오입니다. 싱크가 바빠서 데이터를 받을 수 없으므로 ready를 디어서트합니다. 소스는 valid와 data를 안정적으로 유지해야 합니다.

              C1     C2     C3     C4     C5     C6
         ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
  clk    ┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─

         ┌────────────────────────────────────┐
  valid  ┘                                    └──────────

         ┌────────────────────────────────────┐
  data   ╡            D0 (HELD STABLE)        ╞═════════
                                  ┌───────────┐
  ready  ─────────────────────────┘           └──────────

                STALL     STALL    ↑ TRANSFER!

⚠️ Critical Rule: Valid Must Not Depend on Ready!

Once valid is asserted, the source CANNOT deassert it until the transfer completes (i.e., until ready goes high). This prevents deadlocks where both sides wait for each other.

valid가 어서트되면, 소스는 전송이 완료될 때까지 (즉, ready가 하이가 될 때까지) 디어서트할 수 없습니다. 이는 양쪽이 서로를 기다리는 데드락을 방지합니다.

Also: data must remain stable while valid is asserted. Changing data mid-handshake is a protocol violation!

또한: valid가 어서트된 동안 data는 안정적이어야 합니다. 핸드셰이크 중 데이터 변경은 프로토콜 위반입니다!

5. Timing Diagram: Back-to-Back Transfers

In high-throughput pipelines, we want transfers every cycle. This means valid and ready stay high continuously — no gaps!

고처리량 파이프라인에서는 매 사이클 전송을 원합니다. 이는 valid와 ready가 지속적으로 하이 상태를 유지한다는 뜻입니다 — 갭 없이!

              C1     C2     C3     C4     C5
         ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
  clk    ┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─

         ┌──────────────────────────────────┐
  valid  ┘                                  └────

         ┌─────┬──────┬──────┬──────┬──────┐
  data   ╡ D0  │  D1  │  D2  │  D3  │  D4  ╞═══
         ┌──────────────────────────────────┐
  ready  ┘                                  └────

          ↑ T0  ↑ T1   ↑ T2   ↑ T3   ↑ T4
        (Transfer every single cycle = max throughput!)

💡 Throughput Formula

Throughput = Transfers / Total Cycles
Back-to-back: 5 transfers in 5 cycles = 100% throughput
With stalls: 5 transfers in 10 cycles = 50% throughput
This metric is crucial for performance analysis in design reviews!

처리량 = 전송 수 / 총 사이클
연속 전송: 5 사이클에 5 전송 = 100% 처리량
스톨 포함: 10 사이클에 5 전송 = 50% 처리량
이 메트릭은 설계 리뷰에서 성능 분석에 필수적입니다!

6. Timing Diagram: Intermittent Valid

Sometimes the source doesn't have data every cycle. valid toggles on and off. The sink keeps ready high, accepting whenever data appears.

때때로 소스가 매 사이클 데이터를 가지고 있지 않습니다. valid가 켜졌다 꺼졌다 합니다. 싱크는 ready를 하이로 유지하며 데이터가 나타날 때마다 수용합니다.

              C1     C2     C3     C4     C5     C6
         ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
  clk    ┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─┘  └─

         ┌─────┐           ┌─────┐     ┌─────┐
  valid  ┘     └───────────┘     └─────┘     └──────

         ┌─────┐           ┌─────┐     ┌─────┐
  data   ╡ D0  ╞═══════════╡ D1  ╞═════╡ D2  ╞════
         ┌──────────────────────────────────────────
  ready  ┘

          ↑ T0              ↑ T1        ↑ T2
        (3 transfers in 6 cycles = 50% throughput)

7. SystemVerilog: Ready/Valid Source

module rv_source #(
    parameter DATA_W = 8
)(
    input  logic              clk,
    input  logic              rst_n,
    // Ready/Valid output interface
    output logic              o_valid,
    output logic [DATA_W-1:0] o_data,
    input  logic              i_ready
);

    logic [DATA_W-1:0] next_data;
    logic              data_available;

    // Transfer happens when both valid and ready are high
    logic transfer;
    assign transfer = o_valid && i_ready;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            o_valid <= 1'b0;
            o_data  <= '0;
        end else if (transfer || !o_valid) begin
            // Load new data when: transfer just completed OR we're idle
            o_valid <= data_available;
            o_data  <= next_data;
        end
        // If valid && !ready: HOLD — do nothing (stall)
    end

endmodule

🔍 Code Walkthrough

  • transfer fires only when both valid and ready are asserted
  • transfer는 valid와 ready가 모두 어서트될 때만 발생
  • On transfer: load new data immediately (back-to-back capable)
  • 전송 시: 새 데이터를 즉시 로드 (연속 전송 가능)
  • On stall (valid && !ready): do nothing — data stays stable
  • 스톨 시 (valid && !ready): 아무것도 하지 않음 — 데이터 안정 유지
  • On idle (!valid): can load new data without waiting
  • 유휴 시 (!valid): 대기 없이 새 데이터 로드 가능

8. SystemVerilog: Ready/Valid Sink

module rv_sink #(
    parameter DATA_W = 8
)(
    input  logic              clk,
    input  logic              rst_n,
    // Ready/Valid input interface
    input  logic              i_valid,
    input  logic [DATA_W-1:0] i_data,
    output logic              o_ready
);

    logic [DATA_W-1:0] stored_data;
    logic              buffer_full;

    // Ready when buffer is empty
    assign o_ready = !buffer_full;

    // Transfer detection
    logic transfer;
    assign transfer = i_valid && o_ready;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            stored_data <= '0;
            buffer_full <= 1'b0;
        end else begin
            if (transfer) begin
                stored_data <= i_data;
                buffer_full <= 1'b1;
            end else if (buffer_full) begin
                // Process and consume data
                buffer_full <= 1'b0;
            end
        end
    end

endmodule

9. Timing Diagram: Deadlock Hazard

What happens if both sides wait for the other? This creates a deadlock — a circular dependency that never resolves.

양쪽이 서로를 기다리면 어떻게 될까요? 이것은 데드락을 만듭니다 — 절대 해결되지 않는 순환 의존성입니다.

  DEADLOCK SCENARIO:
  Source thinks: "I'll assert valid only when I see ready"
  Sink thinks:   "I'll assert ready only when I see valid"

              C1     C2     C3     C4     C5 ...forever
  valid  ──────────────────────────────────── (never asserted!)
  ready  ──────────────────────────────────── (never asserted!)

  ❌ NO TRANSFER EVER HAPPENS!

⚠️ The Golden Rule of Ready/Valid

Valid MUST NOT depend on ready. The source must be willing to assert valid regardless of ready's state. However, ready MAY depend on valid (this is allowed and common in some protocols).

Valid는 ready에 의존하면 안 됩니다. 소스는 ready 상태와 관계없이 valid를 어서트할 수 있어야 합니다. 그러나 ready는 valid에 의존할 수 있습니다 (이것은 일부 프로토콜에서 허용되고 일반적입니다).

10. Skid Buffer: Handling Backpressure Gracefully

A skid buffer (also called a pipeline register) adds one slot of storage between source and sink. This prevents the source from stalling when the sink briefly isn't ready.

스키드 버퍼(파이프라인 레지스터라고도 함)는 소스와 싱크 사이에 하나의 저장 슬롯을 추가합니다. 이는 싱크가 잠시 준비되지 않았을 때 소스가 스톨되는 것을 방지합니다.

module skid_buffer #(
    parameter DATA_W = 8
)(
    input  logic              clk,
    input  logic              rst_n,
    // Input side (from source)
    input  logic              i_valid,
    input  logic [DATA_W-1:0] i_data,
    output logic              o_ready,
    // Output side (to sink)
    output logic              o_valid,
    output logic [DATA_W-1:0] o_data,
    input  logic              i_ready
);

    // Skid register — catches data when output stalls
    logic [DATA_W-1:0] skid_data;
    logic              skid_valid;

    // We can accept data if skid register is empty
    assign o_ready = !skid_valid;

    // Output mux: prefer skid data if available
    assign o_valid = skid_valid || i_valid;
    assign o_data  = skid_valid ? skid_data : i_data;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            skid_data  <= '0;
            skid_valid <= 1'b0;
        end else begin
            if (skid_valid) begin
                // Skid has data — drain it when output accepts
                if (i_ready)
                    skid_valid <= 1'b0;
            end else if (i_valid && o_valid && !i_ready) begin
                // Output stalled + new input arriving → save to skid
                skid_data  <= i_data;
                skid_valid <= 1'b1;
            end
        end
    end

endmodule

🧩 Why Skid Buffers Matter

  • Decouples source timing from sink timing
  • 소스 타이밍과 싱크 타이밍을 분리
  • Prevents stall propagation through the pipeline
  • 파이프라인을 통한 스톨 전파를 방지
  • Adds only 1 cycle of latency, but preserves throughput
  • 1 사이클의 지연만 추가하지만 처리량을 유지
  • Used everywhere: AXI interfaces, pipeline stages, NoC routers
  • 모든 곳에서 사용: AXI 인터페이스, 파이프라인 스테이지, NoC 라우터

11. Key Takeaways

📝 Today's Summary

  1. Transfer = valid && ready on clock edge — this is the fundamental rule
  2. 전송 = valid && ready 클록 에지에서 — 이것이 기본 규칙
  3. Valid must not depend on ready — prevents deadlocks
  4. Valid는 ready에 의존하면 안 됨 — 데드락 방지
  5. Data must stay stable while valid is asserted during stall
  6. 스톨 중 valid가 어서트된 동안 데이터는 안정적이어야 함
  7. Throughput = transfers / cycles — measure pipeline efficiency
  8. 처리량 = 전송 / 사이클 — 파이프라인 효율 측정
  9. Skid buffers decouple stages and prevent stall propagation
  10. 스키드 버퍼는 스테이지를 분리하고 스톨 전파를 방지

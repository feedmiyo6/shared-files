Yesterday we learned what synthesis does at a high level — transforming RTL into gates. Today we go deeper: what specific hardware does your SystemVerilog code actually become? Understanding this mapping is the difference between writing code that works in simulation and writing code that produces efficient, predictable hardware.

어제 우리는 합성이 높은 수준에서 무엇을 하는지 — RTL을 게이트로 변환하는 것을 배웠습니다. 오늘은 더 깊이 들어갑니다: SystemVerilog 코드가 실제로 어떤 하드웨어가 되는가? 이 매핑을 이해하는 것이 시뮬레이션에서 작동하는 코드와 효율적이고 예측 가능한 하드웨어를 생성하는 코드의 차이입니다.

1. The Hardware Inference Mental Model 1. 하드웨어 추론 멘탈 모델

Every line of synthesizable SystemVerilog maps to actual hardware primitives. The synthesis tool reads your code and infers what hardware you meant. Think of it like a translator — your code is the source language, gates/flip-flops/muxes are the target.

합성 가능한 SystemVerilog의 모든 줄은 실제 하드웨어 프리미티브에 매핑됩니다. 합성 도구는 코드를 읽고 의도한 하드웨어를 추론합니다. 번역기처럼 생각하세요 — 코드가 소스 언어이고, 게이트/플립플롭/멀티플렉서가 대상 언어입니다.

2. Flip-Flops & Registers — The Storage Elements 2. 플립플롭과 레지스터 — 저장 요소

Any signal assigned inside an always_ff block becomes a flip-flop. Each bit gets its own flip-flop. A multi-bit signal becomes a register (group of flip-flops).

always_ff 블록 내에서 할당된 모든 신호는 플립플롭이 됩니다. 각 비트는 자체 플립플롭을 갖습니다. 다중 비트 신호는 레지스터(플립플롭 그룹)가 됩니다.

// This code infers 8 flip-flops (one per bit)
always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n)
        counter <= 8'b0;        // Reset value
    else
        counter <= counter + 1; // Increment
end
// Result: 8 D flip-flops with async reset + an 8-bit adder

📋 What Gets a Flip-Flop?

  • Every bit of every signal assigned in always_ff
  • always_ff에서 할당된 모든 신호의 모든 비트
  • logic [31:0] data → 32 flip-flops
  • logic [31:0] data → 32개의 플립플롭
  • logic [7:0] mem [0:255] → 2,048 flip-flops (8 × 256)
  • logic [7:0] mem [0:255] → 2,048개의 플립플롭 (8 × 256)
  • Unused bits still get flip-flops unless the tool optimizes them away
  • 사용되지 않는 비트도 도구가 최적화하지 않는 한 플립플롭을 갖습니다

Register with Enable 인에이블이 있는 레지스터 

// Infers flip-flops WITH clock enable
always_ff @(posedge clk) begin
    if (enable)
        data_reg <= data_in;
    // No else → data_reg holds its value (implicit feedback mux)
end
// Result: Flip-flops with a mux on D input controlled by 'enable'

💡 Pro Tip: Many FPGA flip-flops have a built-in clock enable (CE) pin. Synthesis tools recognize this pattern and use the CE pin directly, saving a mux!

💡 프로 팁: 많은 FPGA 플립플롭에는 내장 클록 인에이블(CE) 핀이 있습니다. 합성 도구는 이 패턴을 인식하고 CE 핀을 직접 사용하여 멀티플렉서를 절약합니다!

3. Multiplexers — The Decision Makers 3. 멀티플렉서 — 결정을 내리는 것들

Every if, case, or ternary operator (? :) infers a multiplexer. The condition becomes the select signal; the branches become data inputs.

모든 if, case 또는 삼항 연산자(? :)는 멀티플렉서를 추론합니다. 조건은 선택 신호가 되고, 분기는 데이터 입력이 됩니다.

// 2:1 Mux — if/else
always_comb begin
    if (sel)
        out = a;
    else
        out = b;
end
// Equivalent: assign out = sel ? a : b;

// 4:1 Mux — case statement
always_comb begin
    case (sel)
        2'b00: out = a;
        2'b01: out = b;
        2'b10: out = c;
        2'b11: out = d;
    endcase
end

Nested Muxes — Priority Chains 중첩된 멀티플렉서 — 우선순위 체인

Nested if-else creates a priority mux chain. The first condition has highest priority. This creates longer combinational paths!

중첩된 if-else는 우선순위 멀티플렉서 체인을 만듭니다. 첫 번째 조건이 가장 높은 우선순위를 갖습니다. 이것은 더 긴 조합 경로를 만듭니다!

// Priority mux chain — 3 levels deep
always_comb begin
    if (cond_a)        // Highest priority → checked first
        out = val_a;
    else if (cond_b)  // Second priority
        out = val_b;
    else if (cond_c)  // Third priority
        out = val_c;
    else
        out = val_d;    // Default (lowest)
end
// Creates: mux(cond_a, val_a, mux(cond_b, val_b, mux(cond_c, val_c, val_d)))

⚠️ Priority vs Parallel

if-else if → priority chain (series of muxes, longer path)
case → parallel mux (flat selection, shorter path)

If your conditions are mutually exclusive, prefer case or unique case — the synthesis tool can build a flatter, faster mux tree!

if-else if → 우선순위 체인 (직렬 멀티플렉서, 더 긴 경로)
case → 병렬 멀티플렉서 (평면 선택, 더 짧은 경로)

조건이 상호 배타적이면 case 또는 unique case를 선호하세요 — 합성 도구가 더 평평하고 빠른 멀티플렉서 트리를 구축할 수 있습니다!

4. Arithmetic Operators — Adders, Multipliers, Shifters 4. 산술 연산자 — 가산기, 곱셈기, 시프터

Arithmetic in your code maps directly to hardware arithmetic blocks. The cost varies dramatically by operation!

코드의 산술은 하드웨어 산술 블록에 직접 매핑됩니다. 연산에 따라 비용이 극적으로 달라집니다!

OperatorHardwareCostNotes
+, -Adder/SubtractorLowCarry chain grows linearly with width
*MultiplierHigh!Area grows quadratically; uses DSP blocks on FPGA
/, %DividerVery High!Often multi-cycle; avoid in combinational logic

<<, >> (variable)Barrel ShifterMediumLog2(N) levels of muxes
// What each line becomes:
assign sum     = a + b;         // → Adder (carry chain)
assign product = a * b;         // → Multiplier (expensive!)
assign doubled = a << 1;        // → Just wires! (free)
assign shifted = a << amt;     // → Barrel shifter (mux tree)
assign halved  = a >> 1;        // → Just wires! (free)

💡 Multiply by Constants: Synthesis tools are smart! a * 3 becomes (a << 1) + a — a shift and an add instead of a full multiplier. a * 8 becomes a << 3 — completely free!

💡 상수 곱셈: 합성 도구는 똑똑합니다! a * 3은 (a << 1) + a가 됩니다 — 전체 곱셈기 대신 시프트와 가산. a * 8은 a << 3이 됩니다 — 완전히 무료!

5. Bitwise & Logic Operations — Direct Gate Mapping 5. 비트 연산 및 논리 연산 — 직접 게이트 매핑

These are the simplest inferences — each operator maps directly to logic gates:

이것들은 가장 간단한 추론입니다 — 각 연산자가 로직 게이트에 직접 매핑됩니다:

assign y1 = a & b;     // → AND gate
assign y2 = a | b;     // → OR gate
assign y3 = a ^ b;     // → XOR gate
assign y4 = ~a;         // → NOT gate (inverter)
assign y5 = &data;      // → AND reduction tree
assign y6 = |data;      // → OR reduction tree
assign y7 = ^data;      // → XOR reduction tree (parity!)

🔗 Reduction Operators — Hidden Trees

Reduction operators like &data (AND all bits) create a tree of gates. For 8 bits: 4 AND gates → 2 AND gates → 1 AND gate = 3 levels of logic. XOR reduction (^data) gives you parity checking for free!

축소 연산자 &data(모든 비트 AND)는 게이트 트리를 만듭니다. 8비트의 경우: AND 게이트 4개 → AND 게이트 2개 → AND 게이트 1개 = 3 레벨의 로직. XOR 축소(^data)는 패리티 검사를 무료로 제공합니다!

7. Memory Inference — RAM vs Flip-Flops 7. 메모리 추론 — RAM vs 플립플롭

How you write array access determines whether synthesis infers block RAM (efficient) or flip-flop arrays (expensive):

배열 접근을 작성하는 방식이 합성이 블록 RAM(효율적)을 추론할지 플립플롭 배열(비용이 큰)을 추론할지 결정합니다:

// ✅ This infers Block RAM (synchronous read)
logic [7:0] mem [0:255];

always_ff @(posedge clk) begin
    if (wr_en)
        mem[wr_addr] <= wr_data;
    rd_data <= mem[rd_addr];  // Synchronous read → RAM
end

// ❌ This infers 2048 flip-flops! (asynchronous read)
always_ff @(posedge clk) begin
    if (wr_en)
        mem[wr_addr] <= wr_data;
end
assign rd_data = mem[rd_addr];  // Async read → FF array!

⚠️ The RAM vs FF Trap

The difference is one line. Synchronous reads (inside always_ff) → block RAM. Asynchronous reads (assign) → thousands of flip-flops. For a 256×8 memory, that's the difference between 1 RAM block and 2,048 flip-flops!

차이는 한 줄입니다. 동기식 읽기(always_ff 내부) → 블록 RAM. 비동기식 읽기(assign) → 수천 개의 플립플롭. 256×8 메모리의 경우, 이것은 1개의 RAM 블록과 2,048개의 플립플롭의 차이입니다!

📅 Day 22: Pipeline Stages — Adding Registers

📝 Quiz 💻 Practice ← Day 21

Yesterday we explored the fundamental tradeoff between latency and throughput. Today we get hands-on: how do you actually add pipeline stages to a design? We'll take unpipelined combinational logic and systematically break it into stages with registers.

어제 레이턴시와 처리량 사이의 근본적인 트레이드오프를 살펴봤습니다. 오늘은 실제로 파이프라인 스테이지를 디자인에 어떻게 추가하는지 직접 해봅니다. 파이프라인이 없는 조합 논리를 레지스터를 사용하여 체계적으로 스테이지로 나누겠습니다.

1. The Core Idea: Cutting Combinational Paths

Pipelining is the act of inserting registers (flip-flops) into a long combinational path to break it into shorter segments. Each segment becomes a pipeline stage.

파이프라이닝은 긴 조합 경로에 레지스터(플립플롭)를 삽입하여 더 짧은 세그먼트로 나누는 작업입니다. 각 세그먼트는 파이프라인 스테이지가 됩니다.

Unpipelined:파이프라인 없음:

Input → [───── Long Combinational Logic (20ns) ─────] → Output
Clock period must be ≥ 20ns → fmax = 50 MHz

3-Stage Pipeline:3단계 파이프라인:

Input → [Logic A (7ns)] → REG → [Logic B (7ns)] → REG → [Logic C (6ns)] → Output
Clock period must be ≥ 7ns → fmax ≈ 143 MHz (2.86× faster!)

🔑 Key Principle

The clock frequency is limited by the slowest stage, not the total path. By balancing stage delays, you maximize throughput.

클럭 주파수는 전체 경로가 아닌 가장 느린 스테이지에 의해 제한됩니다. 스테이지 지연을 균형있게 맞추면 처리량을 극대화할 수 있습니다.

2. Step-by-Step: Pipelining a 4-Bit Multiplier

Let's take a concrete example. Here's an unpipelined multiplier with accumulate:

구체적인 예를 들어보겠습니다. 파이프라인이 없는 곱셈-누적기입니다:

// Unpipelined: multiply then add — long critical path
module mac_unpipelined (
    input  logic clk, rst_n,
    input  logic [7:0] a, b,
    input  logic [15:0] c,
    output logic [16:0] result
);
    // Everything in one clock cycle!
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) result <= '0;
        else        result <= (a * b) + c;  // multiply + add in one cycle
endmodule

The critical path includes both the multiplier AND the adder. Let's split them:

크리티컬 패스에 곱셈기와 덧셈기가 모두 포함됩니다. 이를 분리해봅시다:

// 2-Stage Pipeline: separate multiply and add
module mac_pipelined (
    input  logic clk, rst_n,
    input  logic [7:0] a, b,
    input  logic [15:0] c,
    output logic [16:0] result
);

    // ===== Stage 1: Multiply =====
    logic [15:0] product_r;     // pipeline register
    logic [15:0] c_r;           // carry 'c' forward!

    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) begin
            product_r <= '0;
            c_r       <= '0;
        end else begin
            product_r <= a * b;       // Stage 1 work
            c_r       <= c;            // Pass-through register
        end

    // ===== Stage 2: Add =====
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) result <= '0;
        else        result <= product_r + c_r;  // Stage 2 work

endmodule

⚠️ Critical: Data Must Travel Together!

Notice c_r — we must register c alongside the product so it arrives at Stage 2 at the same time. This is called a pass-through register or data forwarding. Forgetting this is the #1 pipelining bug!

c_r에 주목하세요 — 곱셈 결과와 함께 c도 반드시 레지스터에 저장하여 Stage 2에 동시에 도착하도록 해야 합니다. 이를 패스스루 레지스터라고 합니다. 이것을 잊는 것이 파이프라이닝 버그 1위입니다!

3. The Pass-Through Register Pattern

When pipelining, every signal that crosses a stage boundary needs a register — even if it's not being "processed" in that stage.

파이프라이닝할 때, 스테이지 경계를 넘는 모든 신호에는 레지스터가 필요합니다 — 해당 스테이지에서 "처리"되지 않더라도요.

3-Stage Pipeline — Signal Flow:3단계 파이프라인 — 신호 흐름:

         Stage 1        Stage 2        Stage 3
         ┌──────┐       ┌──────┐       ┌──────┐
  a ───→ │Mult  │──→ R ─│Add   │──→ R ─│Shift │──→ result
  b ───→ │      │       │      │       │      │
  c ───→ │ (c_r)│──→ R ─│      │       │      │
  sh ──→ │(sh_1)│──→ R ─│(sh_2)│──→ R ─│      │
         └──────┘       └──────┘       └──────┘

  R = Pipeline Register
  (xx) = pass-through — signal not used here, just forwarded

Notice how sh (shift amount) travels through Stage 1 and Stage 2 without being used — it's only needed in Stage 3. It still needs two pipeline registers to stay aligned!

sh(시프트 양)가 Stage 1과 Stage 2를 사용되지 않으면서 통과하는 것에 주목하세요 — Stage 3에서만 필요합니다. 정렬을 유지하기 위해 여전히 두 개의 파이프라인 레지스터가 필요합니다!

4. Pipeline Register Cost

FactorImpact 요소영향
AreaEach pipeline register adds flip-flops (1 FF per bit) 면적각 파이프라인 레지스터마다 플립플롭 추가 (비트당 1 FF)
PowerMore FFs = more dynamic & leakage power 전력더 많은 FF = 더 많은 동적 및 누설 전력
LatencyEach stage adds 1 clock cycle of latency 레이턴시각 스테이지는 1 클록 사이클의 레이턴시 추가
Clock overheadtsetup + tclk-to-q added to each stage's delay budget 클럭 오버헤드각 스테이지의 지연 예산에 tsetup + tclk-to-q 추가
ThroughputIncreases — one result per clock cycle after pipeline fills 처리량증가 — 파이프라인이 차면 클록 사이클당 하나의 결과

⏱️ Diminishing Returns

You can't pipeline infinitely. Each register adds tsetup + tclk-to-q overhead (~100-200ps in modern processes). Eventually, the overhead dominates and adding more stages gives no benefit.

무한히 파이프라인할 수는 없습니다. 각 레지스터는 tsetup + tclk-to-q 오버헤드(~100-200ps)를 추가합니다. 결국 오버헤드가 지배적이 되어 더 많은 스테이지를 추가해도 이점이 없습니다.

5. Balanced vs. Unbalanced Stages

For maximum frequency, all stages should have roughly equal combinational delay:

최대 주파수를 위해 모든 스테이지의 조합 지연이 대략 같아야 합니다:

// BAD: Unbalanced — Stage 1 is bottleneck
// Stage 1: 15ns   Stage 2: 5ns
// Clock ≥ 15ns → 67 MHz (Stage 2 wastes 10ns!)

// GOOD: Balanced — move some logic from Stage 1 to Stage 2
// Stage 1: 10ns   Stage 2: 10ns
// Clock ≥ 10ns → 100 MHz (both stages fully utilized)

💡 Interview Tip

When asked "how would you improve timing?", pipelining is often the answer. But always mention: (1) where you'd cut the path, (2) what pass-through registers are needed, and (3) the latency cost.

면접에서 "타이밍을 어떻게 개선하겠습니까?"라는 질문에 파이프라이닝이 자주 답입니다. 하지만 항상 언급하세요: (1) 경로를 어디서 자를 것인지, (2) 어떤 패스스루 레지스터가 필요한지, (3) 레이턴시 비용.

6. Full Example: 3-Stage Pipelined Datapath

module pipe3_datapath (
    input  logic        clk, rst_n,
    input  logic [7:0]  a, b, c,
    input  logic [2:0]  shift_amt,
    output logic [16:0] result
);

    // ========== Pipeline Stage 1: Multiply ==========
    logic [15:0] s1_product;
    logic [7:0]  s1_c;           // pass-through
    logic [2:0]  s1_shift_amt;   // pass-through

    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) begin
            s1_product   <= '0;
            s1_c         <= '0;
            s1_shift_amt <= '0;
        end else begin
            s1_product   <= a * b;
            s1_c         <= c;
            s1_shift_amt <= shift_amt;
        end

    // ========== Pipeline Stage 2: Add ==========
    logic [16:0] s2_sum;
    logic [2:0]  s2_shift_amt;   // pass-through again

    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) begin
            s2_sum       <= '0;
            s2_shift_amt <= '0;
        end else begin
            s2_sum       <= s1_product + s1_c;
            s2_shift_amt <= s1_shift_amt;
        end

    // ========== Pipeline Stage 3: Shift ==========
    always_ff @(posedge clk or negedge rst_n)
        if (!rst_n) result <= '0;
        else        result <= s2_sum << s2_shift_amt;

endmodule
// Latency: 3 clock cycles
// Throughput: 1 result per clock cycle (after pipeline fills)

📛 Naming Convention

Use prefixes like s1_, s2_, s3_ for pipeline stage registers. This makes it instantly clear which stage a signal belongs to. Many companies enforce this convention.

파이프라인 스테이지 레지스터에 s1_, s2_, s3_ 같은 접두사를 사용하세요. 이렇게 하면 신호가 어떤 스테이지에 속하는지 즉시 알 수 있습니다. 많은 회사에서 이 규칙을 시행합니다.

7. Pipeline Valid Signal

Real pipelines need a valid bit traveling alongside data to indicate which stages contain real data vs. bubbles:

실제 파이프라인에는 어떤 스테이지가 실제 데이터를 가지고 있는지 표시하기 위해 데이터와 함께 이동하는 유효 비트(valid bit)가 필요합니다:

logic s1_valid, s2_valid, s3_valid;

always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
        s1_valid <= 1'b0;
        s2_valid <= 1'b0;
        s3_valid <= 1'b0;
    end else begin
        s1_valid <= input_valid;   // new data entering
        s2_valid <= s1_valid;      // flows with data
        s3_valid <= s2_valid;
    end

assign output_valid = s3_valid; // result is valid when s3 says so

Q1. What is the primary role of an address decoder in a bus interconnect?

버스 인터커넥트에서 주소 디코더의 주요 역할은?

  • A) Arbitrate between multiple initiators
  • B) Route requests to the correct target based on address
  • C) Buffer data between fast and slow modules
  • D) Convert between different data widths

✅ The address decoder looks at the address field and generates a select signal for the appropriate target. Arbitration is handled by the arbiter, buffering by FIFOs, and width conversion by separate adapters.

✅ 주소 디코더는 주소 필드를 보고 적절한 타겟에 대한 선택 신호를 생성합니다. 중재는 중재기가, 버퍼링은 FIFO가, 폭 변환은 별도의 어댑터가 처리합니다.

Q2. What happens if an address decoder has no default case for unmapped addresses?

주소 디코더에 매핑되지 않은 주소에 대한 default case가 없으면?

  • A) The request is silently discarded
  • B) The bus may hang because no target asserts ready
  • C) The request goes to target 0 by default
  • D) A synthesis error occurs

✅ If no target is selected, no target will assert ready, and the initiator will wait forever — the bus hangs. Always include a default path that generates an error response.

✅ 타겟이 선택되지 않으면 어떤 타겟도 ready를 assert하지 않아 이니시에이터가 영원히 대기합니다 — 버스가 멈춥니다. 항상 에러 응답을 생성하는 기본 경로를 포함하세요.

Q3. In the request multiplexer, when should the round-robin arbiter advance to the next initiator?

요청 멀티플렉서에서 라운드로빈 중재기는 언제 다음 이니시에이터로 전진해야 하나요?

  • A) Every clock cycle
  • B) When a new request arrives
  • C) When a handshake completes (valid & ready)
  • D) After a fixed timeout

✅ The arbiter should advance on successful handshake (tgt_valid & tgt_ready). This ensures the current transaction completes before switching to another initiator, preventing partial transfers.

✅ 중재기는 성공적인 핸드셰이크(tgt_valid & tgt_ready)에서 전진해야 합니다. 이렇게 하면 다른 이니시에이터로 전환하기 전에 현재 트랜잭션이 완료되어 부분 전송을 방지합니다.

Q4. What is the purpose of a transaction ID (e.g., tgt_id) in bus integration?

버스 통합에서 트랜잭션 ID(예: tgt_id)의 목적은?

  • A) To prioritize certain requests over others
  • B) To count the total number of transactions
  • C) To route responses back to the correct initiator
  • D) To encrypt the data payload

✅ Transaction IDs tag each request with its source. When the target responds, the ID is used to demux the response back to the originating initiator. In AXI, these are the AWID/ARID fields.

✅ 트랜잭션 ID는 각 요청에 출처를 태그합니다. 타겟이 응답할 때 ID를 사용하여 응답을 원래 이니시에이터로 역다중화합니다. AXI에서는 AWID/ARID 필드입니다.

Q5. In the response demux, why can data be "broadcast" to all initiators?

응답 역다중화기에서 데이터를 모든 이니시에이터에 "브로드캐스트"할 수 있는 이유는?

  • A) All initiators need to see every response for caching
  • B) Only the initiator with valid asserted will latch the data
  • C) Broadcasting reduces wire count
  • D) It improves bus throughput

✅ The data bus goes to all initiators, but resp_valid is only asserted for the correct one. Since initiators only latch data when their valid is high, the broadcast is safe and simplifies wiring.

✅ 데이터 버스는 모든 이니시에이터에 연결되지만, resp_valid는 올바른 것에 대해서만 assert됩니다. 이니시에이터는 valid가 high일 때만 데이터를 래치하므로 브로드캐스트는 안전하고 배선을 단순화합니다.

Q6. When connecting two modules in different clock domains, what must you add?

서로 다른 클럭 도메인의 두 모듈을 연결할 때 무엇을 추가해야 하나요?

  • A) A priority arbiter
  • B) A width converter
  • C) Clock domain crossing synchronizers (e.g., async FIFO)
  • D) Pipeline registers only

✅ Different clock domains require CDC synchronizers to prevent metastability. For multi-bit data, an async FIFO (with Gray code pointers) is the standard solution — exactly what we studied in Week 4!

✅ 서로 다른 클럭 도메인은 메타스태빌리티를 방지하기 위해 CDC 동기화기가 필요합니다. 멀티비트 데이터의 경우 비동기 FIFO(그레이 코드 포인터 포함)가 표준 솔루션입니다 — Week 4에서 배운 것입니다!

Q7. In the register block example, what value is returned when reading an unknown address?

레지스터 블록 예제에서 알 수 없는 주소를 읽을 때 어떤 값이 반환되나요?

  • A) All zeros (0x00000000)
  • B) 0xDEAD_BEEF
  • C) All ones (0xFFFFFFFF)
  • D) The last written value

✅ The default case returns 32'hDEAD_BEEF, a recognizable debug pattern. This makes it easy to spot when software accidentally reads from an unimplemented register address.

✅ 기본 케이스는 인식하기 쉬운 디버그 패턴인 32'hDEAD_BEEF를 반환합니다. 소프트웨어가 실수로 구현되지 않은 레지스터 주소에서 읽을 때 쉽게 발견할 수 있습니다.

Q8. Why does the register block set req_ready = 1'b1 always?

레지스터 블록이 req_ready = 1'b1을 항상 설정하는 이유는?

  • A) To prevent bus errors
  • B) Because register access is single-cycle and never needs to stall
  • C) To maximize arbitration fairness
  • D) Because targets cannot deassert ready

✅ Simple register blocks can handle a request every clock cycle — there's no latency or processing delay. So ready is always high. More complex targets (like memory controllers) may deassert ready when busy.

✅ 간단한 레지스터 블록은 매 클럭 사이클마다 요청을 처리할 수 있어 지연이나 처리 딜레이가 없습니다. 따라서 ready는 항상 high입니다. 메모리 컨트롤러와 같은 복잡한 타겟은 바쁠 때 ready를 deassert할 수 있습니다.

Q9. What causes a combinational loop in bus integration, and how do you fix it?

버스 통합에서 조합 논리 루프의 원인과 해결 방법은?

  • A) Using too many pipeline stages; remove some
  • B) Ready depends on valid which depends on ready; break with registers
  • C) Having more initiators than targets; add more targets
  • D) Using round-robin instead of priority arbitration

✅ A classic integration bug: module A's valid depends on module B's ready, but module B's ready depends on A's valid. This creates a combinational loop that causes simulation oscillation or synthesis failure. Break it by registering one of the signals.

✅ 고전적인 통합 버그: 모듈 A의 valid가 모듈 B의 ready에 의존하고, B의 ready가 A의 valid에 의존합니다. 이것은 시뮬레이션 발진이나 합성 실패를 유발하는 조합 논리 루프를 생성합니다. 신호 중 하나를 레지스터로 끊어 해결합니다.

Q10. In AXI, what is the equivalent of the addr_error signal from the address decoder?

AXI에서 주소 디코더의 addr_error 신호에 해당하는 것은?

  • A) BRESP = OKAY
  • B) BRESP/RRESP = DECERR
  • C) ARREADY = 0
  • D) AWVALID = 0

✅ In AXI, when a request goes to an unmapped address, the interconnect generates a DECERR (decode error) response. This is returned on BRESP (for writes) or RRESP (for reads).

✅ AXI에서 요청이 매핑되지 않은 주소로 갈 때 인터커넥트는 DECERR(디코드 에러) 응답을 생성합니다. 이것은 BRESP(쓰기용) 또는 RRESP(읽기용)에서 반환됩니다.

Q11. If you have 4 initiators, what is the minimum width of the transaction ID?

이니시에이터가 4개일 때 트랜잭션 ID의 최소 폭은?

  • A) 1 bit
  • B) 2 bits
  • C) 3 bits
  • D) 4 bits

✅ You need $clog2(4) = 2 bits to uniquely identify 4 initiators (values 0-3). Using fewer bits means you can't distinguish all sources; using more wastes silicon.

✅ 4개의 이니시에이터를 고유하게 식별하려면 $clog2(4) = 2비트가 필요합니다 (값 0-3). 더 적은 비트를 사용하면 모든 출처를 구분할 수 없고, 더 많으면 실리콘을 낭비합니다.

Q12. Which Week 6 concept would you apply when a fast CPU writes to a slow peripheral?

빠른 CPU가 느린 주변장치에 쓸 때 어떤 Week 6 개념을 적용하시겠습니까?

  • A) Address decoding (Day 30)
  • B) Round-robin arbitration (Day 28)
  • C) Flow control with buffering (Day 29)
  • D) AXI channel ordering (Day 27)

✅ When a fast producer (CPU) writes to a slow consumer (peripheral), you need flow control — typically a FIFO buffer that absorbs bursts and lets the peripheral drain at its own pace. This is exactly the Day 29 material!

✅ 빠른 생산자(CPU)가 느린 소비자(주변장치)에 쓸 때 흐름 제어가 필요합니다 — 일반적으로 버스트를 흡수하고 주변장치가 자체 속도로 소비할 수 있게 하는 FIFO 버퍼입니다. 이것이 바로 Day 29 자료입니다!

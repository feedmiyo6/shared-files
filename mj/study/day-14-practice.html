Exercise 1: Identify the Critical Path 연습 1: 크리티컬 패스 식별

Analyze this code and identify the critical path. What is the combinational depth?

이 코드를 분석하고 크리티컬 패스를 식별하세요. 조합 논리 깊이는 얼마인가요?

module datapath (
    input  logic        clk,
    input  logic [15:0] a, b, c, d,
    input  logic [1:0]  sel,
    output logic [15:0] result
);
    logic [31:0] prod;
    logic [15:0] mux_out, sum;

    // Combinational block
    always_comb begin
        // Step 1: Multiply
        prod = a * b;

        // Step 2: Select
        case (sel)
            2'b00: mux_out = prod[15:0];
            2'b01: mux_out = c;
            2'b10: mux_out = d;
            2'b11: mux_out = 16'h0;
        endcase

        // Step 3: Add
        sum = mux_out + d;
    end

    // Register the output
    always_ff @(posedge clk)
        result <= sum;
endmodule

💡 Hint

Trace each possible path from inputs to result. Which input path goes through the most operations?

입력에서 result까지 각 가능한 경로를 추적하세요. 어떤 입력 경로가 가장 많은 연산을 거치나요?

✅ Solution

Critical path: a/b → multiply → MUX → adder → result

크리티컬 패스: a/b → 곱셈 → MUX → 가산기 → result

The path through sel=2'b00 is the longest because it includes the multiplier. Other paths (c or d directly to MUX) skip the multiplier and are much shorter.

sel=2'b00을 거치는 경로가 곱셈기를 포함하므로 가장 깁니다. 다른 경로(c 또는 d가 직접 MUX로)는 곱셈기를 건너뛰어 훨씬 짧습니다.

Depth: Multiplier (~many gates) + 4:1 MUX (2 levels) + 16-bit Adder (~16 gates for ripple carry)

깊이: 곱셈기 (~많은 게이트) + 4:1 MUX (2 레벨) + 16비트 가산기 (~리플 캐리의 경우 ~16 게이트)

Exercise 2: Pipeline This Design 연습 2: 이 설계를 파이프라인화하기

Take the design from Exercise 1 and split it into a 2-stage pipeline to reduce the critical path. Write the pipelined SystemVerilog code.

연습 1의 설계를 가져와서 2단계 파이프라인으로 분할하여 크리티컬 패스를 줄이세요. 파이프라인된 SystemVerilog 코드를 작성하세요.

💡 Hint

Stage 1: Multiply + register. Stage 2: MUX + Add + register. Don't forget to pipeline the signals that are needed in later stages (like sel, c, d)!

스테이지 1: 곱셈 + 레지스터. 스테이지 2: MUX + 덧셈 + 레지스터. 이후 스테이지에서 필요한 신호(sel, c, d)를 파이프라인하는 것을 잊지 마세요!

✅ Solution

module datapath_pipelined (
    input  logic        clk,
    input  logic [15:0] a, b, c, d,
    input  logic [1:0]  sel,
    output logic [15:0] result
);
    // Stage 1 pipeline registers
    logic [31:0] prod_s1;
    logic [15:0] c_s1, d_s1;
    logic [1:0]  sel_s1;

    // Stage 2 signals
    logic [15:0] mux_out, sum;

    // ── Stage 1: Multiply ──
    always_ff @(posedge clk) begin
        prod_s1 <= a * b;
        c_s1    <= c;      // Pipeline c
        d_s1    <= d;      // Pipeline d
        sel_s1  <= sel;    // Pipeline sel
    end

    // ── Stage 2: MUX + Add ──
    always_comb begin
        case (sel_s1)
            2'b00: mux_out = prod_s1[15:0];
            2'b01: mux_out = c_s1;
            2'b10: mux_out = d_s1;
            2'b11: mux_out = 16'h0;
        endcase
        sum = mux_out + d_s1;
    end

    always_ff @(posedge clk)
        result <= sum;
endmodule

Key insight: We must pipeline c, d, and sel alongside the multiply so they arrive at stage 2 at the same time as prod_s1. Forgetting to pipeline these signals is the #1 pipelining bug!

핵심 포인트: 곱셈과 함께 c, d, sel을 파이프라인하여 prod_s1과 동시에 스테이지 2에 도착하게 해야 합니다. 이 신호들의 파이프라인을 잊는 것이 가장 흔한 파이프라이닝 버그입니다!

Exercise 3: Optimize with Precomputation 연습 3: 사전 계산으로 최적화

The following code has a critical path through the MUX and then the adder. Rewrite it using precomputation to move the adder off the MUX-select critical path.

다음 코드는 MUX를 거친 후 가산기를 통과하는 크리티컬 패스가 있습니다. 사전 계산을 사용하여 MUX 선택 크리티컬 패스에서 가산기를 제거하도록 다시 작성하세요.

always_comb begin
    case (sel)
        3'b000: val = in0;
        3'b001: val = in1;
        3'b010: val = in2;
        3'b011: val = in3;
        3'b100: val = in4;
        3'b101: val = in5;
        3'b110: val = in6;
        3'b111: val = in7;
    endcase
    result = val + bias;
end

✅ Solution

always_comb begin
    // Precompute ALL additions in parallel
    sum0 = in0 + bias;
    sum1 = in1 + bias;
    sum2 = in2 + bias;
    sum3 = in3 + bias;
    sum4 = in4 + bias;
    sum5 = in5 + bias;
    sum6 = in6 + bias;
    sum7 = in7 + bias;

    // MUX selects pre-computed result
    case (sel)
        3'b000: result = sum0;
        3'b001: result = sum1;
        3'b010: result = sum2;
        3'b011: result = sum3;
        3'b100: result = sum4;
        3'b101: result = sum5;
        3'b110: result = sum6;
        3'b111: result = sum7;
    endcase
end

Before: Critical path = 8:1 MUX (~3 levels) + Adder. The sel signal must propagate through MUX then adder.

이전: 크리티컬 패스 = 8:1 MUX (~3 레벨) + 가산기. sel 신호가 MUX를 거친 후 가산기를 통과해야 합니다.

After: Critical path = max(Adder, MUX). The adder and MUX delays don't stack — sel only needs to go through the MUX. Cost: 8 adders instead of 1.

이후: 크리티컬 패스 = max(가산기, MUX). 가산기와 MUX 지연이 겹치지 않음 — sel은 MUX만 통과하면 됩니다. 비용: 1개 대신 8개의 가산기.

Exercise 4: Tree Reduction 연습 4: 트리 축소

Rewrite this serial chain addition as a tree structure to minimize logic depth:

이 직렬 체인 덧셈을 트리 구조로 다시 작성하여 로직 깊이를 최소화하세요:

// Serial chain: depth = 5
total = v0 + v1 + v2 + v3 + v4 + v5;

💡 Hint

Group pairs first, then add the pairs. For 6 values, think about how to balance the tree (it won't be perfectly balanced, and that's okay).

먼저 쌍을 묶은 다음 쌍을 더하세요. 6개의 값의 경우 트리 균형을 어떻게 맞출지 생각하세요 (완벽히 균형잡히지 않아도 괜찮습니다).

✅ Solution

// Tree reduction: depth = 3 (instead of 5)

// Level 1: Three parallel additions
pair_01 = v0 + v1;
pair_23 = v2 + v3;
pair_45 = v4 + v5;

// Level 2: Two additions (one pair waits)
quad_03 = pair_01 + pair_23;

// Level 3: Final addition
total   = quad_03 + pair_45;

Depth reduced from 5 to 3! For 6 values, the tree can't be perfectly balanced (6 isn't a power of 2), but 3 levels is still much better than 5.

깊이가 5에서 3으로 줄었습니다! 6개의 값에서 트리는 완벽히 균형잡히지 않지만 (6은 2의 거듭제곱이 아님), 3 레벨은 5보다 훨씬 좋습니다.

Exercise 5: Timing Calculation 연습 5: 타이밍 계산

Given these delays, calculate the maximum clock frequency and slack:

다음 지연이 주어졌을 때 최대 클럭 주파수와 슬랙을 계산하세요:

  • T_cq = 0.15ns
  • 16-bit Multiplier = 2.5ns
  • 16-bit Adder = 0.8ns
  • 4:1 MUX = 0.3ns
  • T_setup = 0.1ns
  • Target clock = 300 MHz (3.33ns period)

Questions:

질문:

  1. What is the critical path delay for the unpipelined design (Ex. 1)?
  2. 파이프라인되지 않은 설계(연습 1)의 크리티컬 패스 지연은?
  3. What is the slack? Does it meet timing?
  4. 슬랙은? 타이밍을 충족하나요?
  5. After pipelining (Ex. 2), what is each stage's delay?
  6. 파이프라이닝 후(연습 2), 각 스테이지의 지연은?
  7. What maximum frequency can the pipelined design achieve?
  8. 파이프라인된 설계가 달성할 수 있는 최대 주파수는?

✅ Solution

1. Unpipelined critical path:

1. 파이프라인되지 않은 크리티컬 패스:

T_cq + Multiplier + MUX + Adder + T_setup

= 0.15 + 2.5 + 0.3 + 0.8 + 0.1 = 3.85ns

2. Slack:

2. 슬랙:

Slack = 3.33ns - 3.85ns = -0.52ns ❌ FAILS!

Negative slack — cannot run at 300 MHz. Max frequency = 1/3.85ns = 259 MHz.

음의 슬랙 — 300 MHz로 실행 불가. 최대 주파수 = 1/3.85ns = 259 MHz.

3. Pipelined stage delays:

3. 파이프라인 스테이지 지연:

Stage 1: T_cq + Multiplier + T_setup = 0.15 + 2.5 + 0.1 = 2.75ns

Stage 2: T_cq + MUX + Adder + T_setup = 0.15 + 0.3 + 0.8 + 0.1 = 1.35ns

4. Max pipelined frequency:

4. 최대 파이프라인 주파수:

Critical stage = Stage 1 at 2.75ns. Max freq = 1/2.75ns = 363 MHz ✅

크리티컬 스테이지 = 2.75ns의 스테이지 1. 최대 주파수 = 1/2.75ns = 363 MHz ✅

Slack at 300 MHz = 3.33 - 2.75 = +0.58ns ✅ Passes with margin!

300 MHz에서의 슬랙 = 3.33 - 2.75 = +0.58ns ✅ 마진과 함께 통과!

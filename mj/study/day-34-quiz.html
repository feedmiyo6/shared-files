Q1. Resource Sharing

You have a design with 4 independent multiplications. If you share a single multiplier using time-multiplexing, what changes?

4개의 독립적인 곱셈이 있는 설계가 있습니다. 시간 다중화를 사용하여 단일 곱셈기를 공유하면 무엇이 변하나요?

  • Area decreases, latency stays the same
  • Area decreases, latency increases to 4 cycles
  • Area increases, latency decreases
  • Both area and latency decrease

✅ B is correct. Sharing replaces 4 multipliers with 1 (area ↓) but now processes sequentially, taking 4 cycles (latency ↑). You also need a small control FSM and muxes, but net area still decreases since multipliers are expensive.

✅ B가 정답. 공유는 4개의 곱셈기를 1개로 대체(면적 ↓)하지만 순차적으로 처리하여 4 사이클이 걸립니다(지연 ↑). 작은 제어 FSM과 먹스도 필요하지만, 곱셈기가 비싸므로 순 면적은 여전히 감소합니다.

Q2. Pipelining Effect

Adding a pipeline register between a multiplier and adder in a MAC unit will:

MAC 유닛에서 곱셈기와 가산기 사이에 파이프라인 레지스터를 추가하면:

  • Reduce area and increase Fmax
  • Increase throughput and decrease latency
  • Increase Fmax and add 1 cycle of latency
  • Decrease Fmax but improve area efficiency

✅ C is correct. Pipelining splits the critical path: instead of Mult+Add in one cycle, each stage runs independently. This allows a higher clock frequency (Fmax ↑), but the total latency increases by 1 cycle. Throughput remains the same (1 result/cycle once the pipeline is full).

✅ C가 정답. 파이프라이닝은 임계 경로를 분할합니다: 한 사이클에서 곱셈+덧셈 대신, 각 단계가 독립적으로 실행됩니다. 이를 통해 더 높은 클록 주파수(Fmax ↑)가 가능하지만, 총 지연은 1 사이클 증가합니다.

Q3. Width Optimization

A counter counts from 0 to 59 (for seconds). What's the minimum bit width needed?

카운터가 0에서 59까지 셉니다(초). 필요한 최소 비트 폭은?

  • 6 bits (covers 0-63)
  • 5 bits (covers 0-31)
  • 7 bits (covers 0-127)
  • 8 bits (covers 0-255)

✅ A is correct. 2⁶ = 64, which covers 0-63 and thus 0-59. 5 bits only covers 0-31 (not enough). 7 or 8 bits would work but waste flip-flops. Always right-size your widths!

✅ A가 정답. 2⁶ = 64로, 0-63을 커버하므로 0-59를 포함합니다. 5비트는 0-31만 커버(부족). 7 또는 8비트는 작동하지만 플립플롭을 낭비합니다.

Q4. When to Share

Which resource is the BEST candidate for sharing?

어떤 자원이 공유에 가장 적합한 후보인가요?

  • 2-input AND gate
  • 4-to-1 multiplexer
  • 8-bit adder
  • 32-bit integer divider

✅ D is correct. Dividers are extremely expensive in area (hundreds to thousands of gates). Sharing one divider across multiple operations makes sense because: (1) it's costly to duplicate, (2) division is rarely needed every cycle. AND gates, muxes, and small adders are cheap — sharing them would add more control overhead than it saves.

✅ D가 정답. 나눗셈기는 면적이 매우 비쌉니다(수백~수천 게이트). 여러 연산에 하나의 나눗셈기를 공유하는 것은 합리적입니다: (1) 복제 비용이 높고, (2) 매 사이클마다 나눗셈이 필요하지 않습니다.

Q5. Parallel vs Serial

A serial CRC engine processes 1 bit/cycle. A parallel version processes 8 bits/cycle. For a 64-byte Ethernet frame, how many cycles does each need?

직렬 CRC 엔진은 1비트/사이클을 처리합니다. 병렬 버전은 8비트/사이클을 처리합니다. 64바이트 이더넷 프레임에 각각 몇 사이클이 필요한가요?

  • Serial: 64 cycles, Parallel: 8 cycles
  • Serial: 512 cycles, Parallel: 64 cycles
  • Serial: 512 cycles, Parallel: 512 cycles
  • Serial: 64 cycles, Parallel: 64 cycles

✅ B is correct. 64 bytes = 512 bits. Serial: 512 bits × 1 bit/cycle = 512 cycles. Parallel: 512 bits ÷ 8 bits/cycle = 64 cycles. The parallel version is 8x faster but uses significantly more combinational logic (XOR trees).

✅ B가 정답. 64바이트 = 512비트. 직렬: 512비트 × 1비트/사이클 = 512사이클. 병렬: 512비트 ÷ 8비트/사이클 = 64사이클. 병렬 버전이 8배 빠르지만 훨씬 더 많은 조합 논리를 사용합니다.

Q6. Logic vs Memory

You need a lookup table with 1024 entries of 16 bits each. What's the most area-efficient implementation?

16비트씩 1024개 항목의 룩업 테이블이 필요합니다. 가장 면적 효율적인 구현은?

  • Block RAM (BRAM) on FPGA
  • Case statement with 1024 entries
  • Combinational mux tree
  • 1024 parallel comparators

✅ A is correct. At 1024 entries, a case statement would generate a massive mux tree consuming thousands of LUTs. Block RAM is purpose-built for this — it stores the data efficiently with 1-cycle read latency. The tradeoff: you "spend" a BRAM resource but save enormous amounts of logic.

✅ A가 정답. 1024개 항목에서 case문은 수천 개의 LUT를 소비하는 거대한 먹스 트리를 생성합니다. Block RAM은 이를 위해 만들어졌으며 — 1사이클 읽기 지연으로 데이터를 효율적으로 저장합니다.

Q7. Pipeline Throughput

A 5-stage pipeline processes one instruction per stage per cycle. After the pipeline is full, how many clock cycles does it take to process 100 instructions?

5단계 파이프라인이 사이클당 단계별 하나의 명령어를 처리합니다. 파이프라인이 가득 찬 후, 100개의 명령어를 처리하는 데 몇 클록 사이클이 필요한가요?

  • 500 cycles
  • 100 cycles
  • 104 cycles
  • 105 cycles

✅ C is correct. Total cycles = pipeline depth + (N-1) = 5 + 99 = 104. The first instruction takes 5 cycles (fill the pipeline), then each subsequent instruction finishes 1 cycle later. Without pipelining, 100 instructions × 5 cycles = 500 cycles. Pipelining gives ~5x speedup!

✅ C가 정답. 총 사이클 = 파이프라인 깊이 + (N-1) = 5 + 99 = 104. 첫 번째 명령어가 5사이클 걸린 후, 각 후속 명령어는 1사이클 후에 완료됩니다. 파이프라이닝 없이는 500사이클이 필요합니다.

Q8. Optimization Priority

Your design fails timing closure by 2ns on the critical path. Which optimization should you try FIRST?

설계가 임계 경로에서 2ns 타이밍 클로저에 실패합니다. 어떤 최적화를 먼저 시도해야 하나요?

  • Reduce all signal widths by 50%
  • Add a pipeline register in the critical path
  • Replace all multipliers with serial implementations
  • Double the clock frequency

✅ B is correct. Pipelining is the first thing to try when failing timing — it directly breaks up the critical path with minimal impact. Reducing widths may not help if the critical path isn't width-related. Serializing multipliers would make timing worse. Doubling clock frequency would make the problem worse, not better!

✅ B가 정답. 타이밍 실패 시 파이프라이닝이 가장 먼저 시도할 것입니다 — 최소한의 영향으로 임계 경로를 직접 분할합니다. 폭 감소는 임계 경로가 폭과 관련없으면 도움이 안 됩니다.

Q9. Area Cost Awareness

Rank these operations from LEAST to MOST expensive in gate area: addition, comparison, multiplication, division.

게이트 면적에서 가장 저렴한 것부터 가장 비싼 것까지 순서를 매기세요: 덧셈, 비교, 곱셈, 나눗셈.

  • Division < Multiplication < Addition < Comparison
  • Comparison < Addition < Division < Multiplication
  • Addition < Comparison < Multiplication < Division
  • Comparison < Addition < Multiplication < Division

✅ D is correct. Comparison is essentially subtraction with only the flags (cheapest). Addition uses a carry chain. Multiplication requires partial products and addition trees (much larger). Division is iterative or uses massive combinational logic (most expensive). A 32-bit divider can be 10-50x the area of a 32-bit adder!

✅ D가 정답. 비교는 본질적으로 플래그만 있는 뺄셈(가장 저렴). 덧셈은 캐리 체인 사용. 곱셈은 부분곱과 덧셈 트리 필요(훨씬 큼). 나눗셈은 반복적이거나 거대한 조합 논리 사용(가장 비쌈).

Q10. Automotive Ethernet Application

In a 1000BASE-T1 Ethernet PHY, the CRC-32 engine processes data at line rate. Why must this be a PARALLEL implementation rather than serial?

1000BASE-T1 이더넷 PHY에서 CRC-32 엔진은 라인 레이트로 데이터를 처리합니다. 왜 직렬이 아닌 병렬 구현이어야 하나요?

  • Serial processing would be too slow to keep up with the data rate
  • Serial CRC is not mathematically possible for CRC-32
  • Parallel CRC uses less area than serial
  • Serial CRC would cause clock domain crossing issues

✅ A is correct. At 1 Gbps, data arrives at very high rates (e.g., 8 bits per clock at 125 MHz). A serial 1-bit CRC engine would need a clock 8x faster (1 GHz) to keep up — impractical. Parallel CRC processes 8+ bits per cycle at 125 MHz, matching the data rate. This is a classic case where performance requirements DEMAND the area cost of parallelism.

✅ A가 정답. 1 Gbps에서 데이터가 매우 빠르게 도착합니다 (예: 125 MHz에서 클록당 8비트). 직렬 1비트 CRC 엔진은 따라잡기 위해 8배 빠른 클록(1 GHz)이 필요 — 비실용적입니다. 병렬 CRC는 125 MHz에서 사이클당 8+ 비트를 처리하여 데이터 속도에 맞춥니다.

Q11. Pipeline Register Cost

You add pipeline registers to split a 64-bit datapath into 3 stages. Approximately how many extra flip-flops do you add?

64비트 데이터 경로를 3단계로 분할하기 위해 파이프라인 레지스터를 추가합니다. 대략 몇 개의 추가 플립플롭이 필요한가요?

  • 64 flip-flops (one set of pipeline registers)
  • 192 flip-flops (3 sets)
  • 128 flip-flops (2 sets of pipeline registers)
  • 3 flip-flops (one per stage)

✅ C is correct. 3 stages need 2 boundaries (between stages 1-2 and 2-3). Each boundary needs 64 flip-flops to capture the full datapath width. Total: 2 × 64 = 128 flip-flops. Note: in practice you may also need to pipeline control signals, adding more FFs.

✅ C가 정답. 3단계는 2개의 경계(1-2단계, 2-3단계 사이)가 필요합니다. 각 경계는 전체 데이터 경로 폭을 캡처하기 위해 64개의 플립플롭이 필요합니다. 총: 2 × 64 = 128개.

Q12. Design Tradeoff Scenario

Your FPGA is 90% full but meets timing easily with 5ns slack. A new feature needs ~15% more logic. What's the best approach?

FPGA가 90% 찼지만 5ns 슬랙으로 타이밍을 쉽게 충족합니다. 새 기능에 ~15% 더 많은 논리가 필요합니다. 가장 좋은 접근법은?

  • Move to a larger FPGA
  • Time-multiplex existing resources to free area, trading some timing slack
  • Reduce clock frequency to save power
  • Remove the existing pipeline stages

✅ B is correct. You have timing slack to spend! Time-multiplexing (resource sharing) trades performance for area — exactly what you need. With 5ns slack, you can afford extra mux delays from sharing. Moving to a larger FPGA is expensive and a last resort. Removing pipelines would hurt timing unnecessarily.

✅ B가 정답. 사용할 타이밍 슬랙이 있습니다! 시간 다중화(자원 공유)는 성능을 면적으로 교환합니다 — 정확히 필요한 것입니다. 5ns 슬랙으로 공유로 인한 추가 먹스 지연을 감당할 수 있습니다.

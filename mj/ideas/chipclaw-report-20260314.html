1. 🏭 Where ChipClaw Fits in the ASIC Design Flow 1. 🏭 ASIC 설계 흐름에서 ChipClaw의 위치

The ASIC design flow has ~8 major stages split into Frontend (logic), Mid-End (bridge), and Backend (physical). We're focusing on Frontend (Stages 1-4) and Mid-End (Stages 5-6) — where your Digital Design transfer puts you. ASIC 설계 흐름은 프런트엔드(로직), 미드엔드(브릿지), 백엔드(물리)로 나뉜 ~8개 주요 단계. 프런트엔드 (1-4단계)와 미드엔드 (5-6단계)에 집중 — 디지털 설계 이동이 놓이는 곳.

Stage 1

📐 Specification

Define functional, power, area requirements

ChipClaw: Parse specs, generate checklists, cross-ref prior designs
Stage 2

💻 RTL Design

Write Verilog/SystemVerilog behavioral models

ChipClaw: Code copilot, module gen, style enforcement, code explanation
Stage 3

🧪 Verification

UVM testbenches, assertions, coverage analysis

ChipClaw: Generate testbenches, SVA assertions, coverage gap analysis
Stage 4

⚙️ Synthesis

RTL → gate-level netlist via Design Compiler

ChipClaw: Run synth, parse reports, compare PPA, suggest fixes
Stage 5

⏱️ Static Timing

Verify setup/hold timing requirements (STA)

ChipClaw: Parse STA reports, explain violations, suggest ECO fixes
Stage 6

🔬 DFT

Scan chains, ATPG, Built-In Self-Test

ChipClaw: Generate scan configs, validate coverage, explain DFT
Stage 7

📦 Floorplan + P&R

Physical placement, clock tree, routing

Future: Phase 6+
Stage 8

✅ Signoff

DRC/LVS, final timing, IR drop, tapeout

Future: Phase 6+

2. 🛠️ Custom Tools — 11 Skills to Build 2. 🛠️ 커스텀 도구 — 구축할 11개 스킬

Each tool is an OpenClaw skill — a self-contained module with its own SKILL.md, scripts, and templates. Organized into 4 tiers by complexity. 각 도구는 OpenClaw 스킬 — SKILL.md, 스크립트, 템플릿을 갖춘 독립 모듈. 복잡도별 4개 티어로 구성.

Tier 1 — RAG & Knowledge (Foundation)

T0 Read

📋 spec-search — Internal Documentation RAG

Natural language Q&A over all internal docs: datasheets, register maps, Confluence, Jira, IEEE specs, app notes. The #1 time-saver — engineers spend hours digging through 500-page PDFs.모든 내부 문서에 대한 자연어 Q&A: 데이터시트, 레지스터 맵, Confluence, Jira, IEEE 스펙. 엔지니어들이 500페이지 PDF를 뒤지는 시간 절약.
"What's the register config for 1000BASE-T1 master mode on LAN8770?"
"Show me all known issues related to MDI crossover on VSC8541"
T0 Read

🐛 jira-intel — Smart Jira Integration

Semantic search over bug history (not just keywords). Link related bugs across products. Auto-generate bug reports from debug sessions. Track verification status.버그 이력에 대한 시맨틱 검색 (키워드가 아닌). 제품 간 관련 버그 연결. 디버그 세션에서 버그 리포트 자동 생성.
"What bugs on LAN8770 Rev B were related to BER at high temperatures?"
T0-T2

📝 confluence-sync — Wiki Read/Write

Read design docs, create pages from templates, update status pages. Template-based generation for test plans, design reviews, status reports.설계 문서 읽기, 템플릿으로 페이지 생성, 상태 페이지 업데이트.
T0 Read

📐 spec-diff — Specification Change Tracker

Diff two versions of any spec/datasheet. AI explains engineering impact: "Transmit template mask tightened by 2dB at 250MHz — PGA gain may need adjustment."스펙/데이터시트 두 버전 비교. AI가 엔지니어링 영향 설명.

Tier 2 — RTL & Design (Frontend)

T1 Generate

💻 rtl-assist — Verilog/SV Copilot

AI-assisted RTL coding. Generate modules from specs, explain legacy code, enforce Microchip coding standards, suggest CDC fixes. READ-ONLY by default — generates to stdout/clipboard, never writes to repo.AI 지원 RTL 코딩. 스펙에서 모듈 생성, 레거시 코드 설명, Microchip 코딩 표준 적용. 기본 읽기 전용.
"Generate a Verilog module for a FIFO with async read/write clocks, depth 16, width 32"
"Explain this FSM in ethernet_rx_ctrl.v lines 45-120"
T1 Generate

🧪 uvm-gen — UVM Testbench Generator

Scaffold UVM verification environments from module interfaces. Generate SVA assertions from natural language. Suggest coverage points from requirements.모듈 인터페이스에서 UVM 검증 환경 스캐폴딩. 자연어에서 SVA 어서션 생성.
"Generate a UVM agent for the SPI master: clk, rst_n, mosi, miso, cs_n, sclk"
T1-T2

🔄 reg-gen — Register Map Generator

Single source of truth: YAML/XML register definition → Verilog RTL + C headers + Python scripts + UVM register model + datasheet tables. Engineers currently maintain 5 separate files for the same register set. This generates ALL from one source.단일 진실 소스: YAML/XML 레지스터 정의 → Verilog RTL + C 헤더 + Python 스크립트 + UVM 레지스터 모델. 현재 엔지니어들이 같은 레지스터 셋을 5개 파일로 관리. 하나에서 전부 생성.

Tier 3 — Synthesis & STA (Mid-End)

T3 Execute

⚙️ synth-runner — Synthesis Automation

Launch synthesis in sandbox, parse area/timing/power reports, compare across runs, suggest SDC constraint fixes. All runs in isolated work directories — never touches source tree.샌드박스에서 합성 실행, 면적/타이밍/전력 보고서 파싱, 런 간 비교, SDC 제약조건 수정 제안. 모든 실행은 격리된 작업 디렉토리.
"Run synthesis on ethernet_mac with target frequency 500MHz and compare with run_47"
T0-T1

⏱️ sta-analyzer — STA Report Parser

Parse PrimeTime/Tempus timing reports. Explain violations in plain English. "Setup violation: slack = -0.15ns on clk→reg_A→mux_B→reg_C. The mux_B cell has fanout 47. Consider buffering." Suggest ECO fixes, track worst slack across runs.PrimeTime/Tempus 타이밍 보고서 파싱. 위반을 쉬운 말로 설명. ECO 수정 제안, 런 간 최악 슬랙 추적.
T0-T1

🔬 dft-assist — DFT Helper

Generate scan chain configurations, validate test coverage, explain DFT concepts, parse ATPG results, flag DFT rule violations in RTL.스캔 체인 구성 생성, 테스트 커버리지 검증, DFT 개념 설명, ATPG 결과 파싱.

Tier 4 — Lab & Cross-Cutting

T0-T1

📊 lab-data — Lab Data Analyzer

Ingest CSV/oscilloscope data, auto-generate plots, anomaly detection ("BER spike at 85°C"), compare across silicon revisions, generate IEEE 802.3 compliance reports.CSV/오실로스코프 데이터 수집, 자동 플롯, 이상 탐지 ("85°C에서 BER 스파이크"), 실리콘 리비전 간 비교.

Key Design Decisions핵심 설계 결정

  • Chunk size: 512 tokens — optimal for technical docs. Larger chunks lose precision; smaller lose context.청크 크기: 512 토큰 — 기술 문서에 최적. 큰 청크는 정밀도 손실, 작은 청크는 컨텍스트 손실.
  • Register tables get special treatment — each register extracted as a separate document with structured fields (address, bits, reset value, description).레지스터 테이블 특별 처리 — 각 레지스터를 구조화된 필드로 별도 문서 추출.
  • Hybrid retrieval — vector similarity catches semantic matches; BM25 keyword search catches exact register names/numbers that embeddings might miss.하이브리드 검색 — 벡터 유사도는 의미적 매칭; BM25 키워드 검색은 임베딩이 놓칠 수 있는 정확한 레지스터 이름/번호 포착.
  • On-prem option — if corporate policy blocks cloud APIs, use BGE embeddings + Llama 3 70B locally. Slower but no IP risk.온프레미스 옵션 — 기업 정책이 클라우드 API 차단 시, BGE 임베딩 + Llama 3 70B 로컬 사용. 느리지만 IP 위험 없음.

4. 🛡️ Guardrails & Safety System 4. 🛡️ 가드레일 & 안전 시스템

This is the most critical section. An AI agent that can run synthesis and write Verilog needs bulletproof safety. Here's how we prevent it from breaking things: 이것이 가장 중요한 섹션. 합성을 실행하고 Verilog를 작성할 수 있는 AI 에이전트에는 방탄 안전장치가 필요.

🚫
NEVER modify source code without explicit approval. All generated code goes to stdout or a .chipclaw.v scratch file. Never overwrites existing RTL.
📦
NEVER run EDA tools outside sandbox. All synthesis/simulation runs happen in a COPY of the work directory. Original source tree is read-only to ChipClaw.
🔒
NEVER exfiltrate IP outside corporate network. On-prem LLM option. If using cloud API, data classification tags prevent sending restricted docs.
📎
ALWAYS cite sources. Every factual claim must reference a document, page, and section. "I don't know" is better than hallucination.
📝
ALWAYS log every action. Full audit trail in JSONL format. Who asked what, what sources were used, what was generated.

🔒 Sandbox Architecture🔒 샌드박스 아키텍처

When ChipClaw runs synthesis or any EDA tool:
1. Copy the entire work directory to /tmp/chipclaw_sandbox_<hash>/
2. Execute in the sandbox — original files are untouched
3. Parse results and present to user
4. Discard sandbox after analysis (or keep if user requests)
5. Resource limits: max 2hr runtime, max 10GB disk, CPU nice level 10
6. Kill switch: "stop" command terminates any running job instantly

The source tree is NEVER writable by ChipClaw's EDA execution tools. ChipClaw이 합성이나 EDA 도구를 실행할 때:
1. 전체 작업 디렉토리를 /tmp/chipclaw_sandbox_<hash>/로 복사
2. 샌드박스에서 실행 — 원본 파일 미변경
3. 결과 파싱 후 사용자에게 제시
4. 분석 후 샌드박스 폐기 (사용자 요청 시 보존)
5. 리소스 제한: 최대 2시간, 최대 10GB, CPU nice 10
6. 킬 스위치: "stop" 명령으로 즉시 종료

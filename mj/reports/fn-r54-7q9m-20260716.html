01Executive summary요약

Three original user-reported problems in the recipe experience, and how Build 54 resolves each.

레시피 경험에서 사용자가 보고한 세 가지 원 문제와 빌드 54가 이를 각각 어떻게 해결했는지입니다.

Problem 1 · Regenerate
문제 1 · 재생성
Tapping "Refresh suggestions" flipped to a false "No results" state and never completed.
"추천 새로고침"을 누르면 잘못된 "결과 없음" 상태로 바뀌고 끝내 완료되지 않았습니다.
Cause
원인
The empty state was derived from dishes.isEmpty, which regeneration itself set true; there was no navigation contract, stale-response guard, or timeout, so a request could hang indefinitely.
dishes.isEmpty로 빈 상태를 판단했는데, 재생성이 스스로 이 값을 참으로 만들었습니다. 내비게이션 계약·오래된 응답 방어·타임아웃이 없어 요청이 무한정 멈출 수 있었습니다.
Resolved
해결
Replaced the heuristic with an explicit request state machine (idle · loading · success · empty · error · limit-reached). Prior dishes stay on screen under a loading overlay, the results screen is pushed at loading-start, a 25s client timeout guarantees resolution, and a request token rejects stale responses.
휴리스틱을 명시적 요청 상태 머신(대기·로딩·성공·빈결과·오류·한도초과)으로 교체했습니다. 기존 요리는 로딩 오버레이 아래 유지되고, 로딩 시작 시점에 결과 화면이 표시되며, 25초 클라이언트 타임아웃이 해소를 보장하고, 요청 토큰이 오래된 응답을 거부합니다.
Problem 2 · Requested ingredient ignored
문제 2 · 요청 재료 무시
"soup using tomato" was ignored when tomato was not in the pantry; unrelated dishes were returned.
토마토가 팬트리에 없을 때 "토마토로 만든 수프" 요청이 무시되고 무관한 요리가 반환됐습니다.
Cause
원인
Special instructions were prompt-only text; the model was steered toward in-stock ingredients and lowered its temperature, collapsing onto the modal pantry dish. There was no concept of "requested but absent."
특수 지시문은 프롬프트 텍스트로만 존재했고, 모델은 재고 재료 위주로 유도되며 온도가 낮아져 가장 흔한 팬트리 요리로 수렴했습니다. "요청했지만 없는 재료"라는 개념 자체가 없었습니다.
Resolved
해결
Special instructions are parsed into requested ingredients, type hints, and negations. Requested-but-absent items become planned purchases: the dish is centered on them, each is flagged as "not in your kitchen," and a "Shopping for" row adds them all to the shopping list at once.
특수 지시문을 요청 재료·유형 힌트·부정어로 파싱합니다. 요청했지만 없는 재료는 계획 구매로 처리되어, 해당 재료를 중심으로 요리가 구성되고 각 항목이 "냉장고에 없음"으로 표시되며, "장보기" 행에서 한 번에 장보기 목록에 추가됩니다.
Problem 3 · Cuisine coverage
문제 3 · 요리 스타일 커버리지
Selecting 3 cuisines returned only Korean (or Korean + Chinese); selected cuisines were silently dropped.
3개 요리 스타일을 선택해도 한식만(또는 한식+중식만) 반환되어 선택한 스타일이 조용히 누락됐습니다.
Cause
원인
Per-cuisine counts were an unenforced prompt instruction, a strict exact-match filter dropped fusion/near-match tags, and a global sort had no per-cuisine floor or top-up.
요리별 개수는 강제되지 않는 프롬프트 지시였고, 엄격한 정확 일치 필터가 퓨전·근접 태그를 버렸으며, 전역 정렬에 요리별 하한선이나 보충이 없었습니다.
Resolved
해결
Deterministic coverage: tolerant cuisine normalization, round-robin slot allocation, a guaranteed minimum of one dish per satisfiable cuisine, and one bounded top-up. If a cuisine truly cannot be filled, the app shows an honest missing-cuisine note instead of dropping it silently.
결정론적 커버리지: 관대한 요리 정규화, 라운드로빈 슬롯 배분, 충족 가능한 요리마다 최소 1개 보장, 그리고 제한된 1회 보충을 적용합니다. 어떤 요리가 정말로 채워질 수 없으면 조용히 버리지 않고 정직한 누락 안내를 표시합니다.
Also addressed: the underlying "results feel random and repetitive" complaint. A dedicated impression ledger now records every shown dish and suppresses recent repeats, so an unchanged pantry yields materially different suggestions between runs. 함께 해결: "결과가 무작위적이고 반복적"이라는 근본 불만도 다뤘습니다. 전용 노출 원장이 표시된 모든 요리를 기록하고 최근 반복을 억제하므로, 팬트리가 그대로여도 실행할 때마다 눈에 띄게 다른 추천이 나옵니다.

02Architecture아키텍처

The upgrade moves hard constraints out of prompt text and into deterministic, testable layers. The model proposes; the server disposes.

이번 개선은 하드 제약을 프롬프트 텍스트에서 결정론적이고 테스트 가능한 계층으로 옮깁니다. 모델은 제안하고, 서버가 결정합니다.

Request state machine

요청 상태 머신

The results-screen lifecycle is an explicit enum — idle · loading · success · empty · error · quotaBlocked — carried on RecipeAiState alongside an activeRequestId token. A request sets loading without clearing prior dishes, the results screen is presented at loading-start (so completion is always visible wherever the user is), a 25-second client timeout forces resolution, and any response whose id does not match the active token is rejected as stale. Backing out during a request marks it abandoned so a late response never mutates a screen the user has left.

RecipeAiState에 명시적 열거형 — 대기 · 로딩 · 성공 · 빈결과 · 오류 · 한도초과 — 과 activeRequestId 토큰이 함께 실립니다. 요청은 기존 요리를 지우지 않고 로딩으로 전환되며, 로딩 시작 시점에 결과 화면이 표시되어(사용자가 어디에 있든 완료가 항상 보임), 25초 클라이언트 타임아웃이 해소를 강제하고, 활성 토큰과 id가 다른 응답은 오래된 것으로 거부됩니다. 요청 중 뒤로 나가면 해당 요청을 폐기 처리하여 늦게 온 응답이 사용자가 떠난 화면을 바꾸지 못합니다.

Request idempotency & quota safety

요청 멱등성 및 할당량 안전성

Each generation mints a client_request_id that acts as an idempotency key. Request state is persisted server-side in a dedicated requests table and claimed atomically before the paid provider work runs. A retry with the same key returns the existing completed result rather than charging quota again, and impressions are written exactly once per generation. This closes the window where a client timeout/retry could double-charge the daily AI allowance or lose repeat-suppression events.

각 생성은 멱등성 키 역할을 하는 client_request_id를 발급합니다. 요청 상태는 전용 요청 테이블에 서버 측으로 보존되며, 유료 프로바이더 작업이 실행되기 전에 원자적으로 선점(claim)됩니다. 동일 키로 재시도하면 할당량을 다시 차감하지 않고 기존 완료 결과를 반환하며, 노출은 생성당 정확히 한 번만 기록됩니다. 이로써 클라이언트 타임아웃·재시도가 일일 AI 할당량을 이중 차감하거나 반복 억제 이벤트를 잃던 구멍이 닫힙니다.

Explicit requested ingredients as planned purchases

명시적 요청 재료를 계획 구매로 처리

Special instructions are parsed into requested_ingredients, and those items are added to an augmented inventory the model is told to center — with the "prioritize what the user already has" bias removed for requested items. Each returned dish carries requested and missing_requested flags. The client renders an honest planned-purchase line per dish and a top-level "Shopping for" affordance, so a lacking-but-requested ingredient drives the request instead of killing it.

특수 지시문은 requested_ingredients로 파싱되고, 해당 항목은 모델이 중심으로 삼도록 지시받는 증강 인벤토리에 추가됩니다 — 요청 항목에 대해서는 "이미 가진 것 우선" 편향을 제거합니다. 반환된 각 요리는 requested와 missing_requested 플래그를 지닙니다. 클라이언트는 요리별 정직한 계획 구매 문구와 최상단 "장보기" 기능을 렌더링하므로, 요청했지만 없는 재료가 요청을 무산시키는 대신 요청을 이끕니다.

Deterministic cuisine allocation

결정론적 요리 배분

After validation, cuisines are normalized tolerantly (fusion and near-match tags map to the closest selected cuisine). Target counts are computed by round-robin — three cuisines yield a 4/4/4 split — with a guaranteed minimum of one dish per satisfiable cuisine before any cuisine gets a second. If a cuisine has zero valid candidates, one bounded top-up re-ask runs; if still empty, it is recorded in coverage.missing_cuisines and surfaced to the user rather than silently dropped.

검증 후 요리는 관대하게 정규화됩니다(퓨전·근접 태그를 가장 가까운 선택 요리로 매핑). 목표 개수는 라운드로빈으로 계산되며 — 세 요리면 4/4/4 분배 — 어떤 요리가 두 번째를 받기 전에 충족 가능한 요리마다 최소 1개를 보장합니다. 어떤 요리에 유효 후보가 없으면 제한된 보충 재요청을 1회 실행하고, 그래도 비어 있으면 coverage.missing_cuisines에 기록하여 조용히 버리지 않고 사용자에게 알립니다.

Dietary, negation & type validation

식이·부정어·유형 검증

A deterministic server-side validator runs after generation, not by prompt hope. It drops dishes that conflict with active dietary restrictions (word-boundary matched, so "graham" never trips "ham"), enforces parsed negations ("no shrimp"), honors type hints (soup / stew / salad), removes blocked dishes, and enforces max_cook_time. Dietary safety is tier-1 hard: a request that conflicts with a restriction (for example pork while vegetarian) surfaces the conflict instead of returning an unsafe dish.

프롬프트에 기대는 대신, 생성 후 결정론적 서버 검증기가 실행됩니다. 활성 식이 제한과 충돌하는 요리를 제거하고(단어 경계 매칭이라 "graham"이 "ham"을 오탐하지 않음), 파싱된 부정어("새우 빼고")를 강제하며, 유형 힌트(수프·스튜·샐러드)를 존중하고, blocked 요리를 제거하며, max_cook_time을 강제합니다. 식이 안전은 1순위 하드 제약입니다: 제한과 충돌하는 요청(예: 채식인데 돼지고기)은 안전하지 않은 요리를 반환하는 대신 충돌을 드러냅니다.

Impression & repeat control

노출 및 반복 제어

A dedicated discover_suggestion_events ledger records a shown event for every returned dish, tagged with the request id for idempotency. Recent-dish lookback reads this ledger and suppresses repeats on the next call, with favorites capped and requested dishes exempted so novelty never overrides an explicit request. This replaces the previously dead, click-only history signal.

전용 discover_suggestion_events 원장이 반환된 모든 요리에 대해 멱등성을 위한 요청 id를 붙여 shown 이벤트를 기록합니다. 최근 요리 조회가 이 원장을 읽어 다음 호출에서 반복을 억제하되, 즐겨찾기는 상한을 두고 요청 요리는 제외하여 새로움이 명시적 요청을 결코 덮지 않습니다. 이는 사실상 작동하지 않던 클릭 전용 히스토리 신호를 대체합니다.

Server / client safety layers

서버/클라이언트 안전 계층

Safety is defense-in-depth. The server performs the authoritative deterministic validation and coverage enforcement; the client keeps its on-device dietary filter as a second line of defense. AI edge functions run with JWT verification enabled and resolve the user server-side; privileged security-definer functions were locked down so execute is granted only to the service role, revoked from public, anon, and authenticated. Telemetry logs structured counts and flags only — never raw pantry inventory or special-instruction text.

안전은 심층 방어입니다. 서버가 권위 있는 결정론적 검증과 커버리지 강제를 수행하고, 클라이언트는 기기 내 식이 필터를 2차 방어선으로 유지합니다. AI 엣지 함수는 JWT 검증을 켠 채 실행되며 서버 측에서 사용자를 확인합니다. 권한이 높은 security-definer 함수는 실행 권한을 service role에만 부여하고 public·anon·authenticated에서 회수하도록 잠갔습니다. 텔레메트리는 구조화된 개수와 플래그만 기록하며 — 팬트리 재고 원문이나 특수 지시문 텍스트는 절대 기록하지 않습니다.

동일한 client_request_id로 같은 요청을 재실행하자 캐시에서 의미적으로 동일한 페이로드가 반환됐습니다. 할당량은 다시 차감되지 않았고(사용량 1 유지) 추가 노출·요청 행도 생성되지 않았습니다(노출 12 유지, 요청 행 1 유지). 이중 차감 없음, 이중 노출 없음.

History upsert & security ACL
